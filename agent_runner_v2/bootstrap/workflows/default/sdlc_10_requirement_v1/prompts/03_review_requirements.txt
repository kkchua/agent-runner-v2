Objective

Review the requirements document for completeness, clarity, and compliance with governance standards.

Layer Boundary

- This workflow belongs to Layer 3 and operates on top of the Layer 2 platform contract.
- Review only the requirements document, not planning or implementation artifacts.
- Treat Layer 1 governance and Layer 2 platform constitution as read-only authority.

Reference Inputs

- Read `REQ_FILE` (the requirements document to review).
- Read `INIT_FILE` (approved initiative for traceability verification).
- Read codebase context from `docs/repo/codebase/current/` to validate scope understanding.
- Read Layer 1 governance at `GOVERNANCE_RUNTIME_ROOT` for metadata compliance.
- Read Layer 2 platform constitution at `PLATFORM_RUNTIME_ROOT` for platform contract compliance.

CRITICAL: Authorized Sections Only

The requirements document must contain exactly these sections (no more, no less):
1. Requirements Overview
2. Functional Requirements
3. Non-Functional Requirements
4. Scope Definition
5. Acceptance Criteria
6. Dependencies and Constraints
7. Risk Assessment

Do NOT reject for sections not in this list. Do NOT require sections like "Initiative Metadata", "Source Reference", "Stakeholder Analysis", or any other section not listed above.

Review Criteria

Evaluate the requirements document against these criteria:

1. **Completeness**:
   - All 7 required sections are present and substantive
   - Requirements Overview clearly summarizes what is required
   - Functional Requirements list specific capabilities with identifiers (FR-001, etc.)
   - Non-Functional Requirements list measurable constraints (NFR-001, etc.)
   - Scope Definition has explicit in-scope and out-of-scope items
   - Acceptance Criteria are measurable and testable
   - Dependencies and Constraints are identified
   - Risk Assessment identifies key risks

2. **Traceability**:
   - REQ preserves the intent of INIT_FILE
   - No scope creep or invented requirements not supported by the initiative
   - Each requirement traces back to the source initiative
   - Assumptions are explicitly recorded

3. **Clarity**:
   - Language is clear and unambiguous
   - No contradictory statements
   - Each requirement is specific and testable
   - Scope boundaries are explicit

4. **Metadata Compliance**:
   - YAML frontmatter includes all required fields
   - For each field, quote the ACTUAL value found in the document before judging compliance
   - template_id is "SYS-03-REQ"
   - lifecycle_status is "draft"
   - layer is "layer3"
   - platform is "agent-runner-v2"

5. **Technical Accuracy**:
   - Code snippets, API references, and file paths are verified against the actual codebase
   - Library/SDK usage matches the installed version (check source or docs, not training data)
   - Variable names, function signatures, and control patterns are consistent with existing code

6. **Encoding Compliance**:
   - ASCII-only content (no em-dashes, curly quotes, Unicode)
   - Plain text section headings (no backticks or formatting)

7. **Artifact Key Accuracy**:
   - Document uses correct artifact key names with _FILE suffix (REQ_FILE, INIT_FILE)
   - No references to deprecated _DOC suffix names (REQ_DOC, INIT_DOC)

8. **Governance Compliance**:
   - No Layer 1 governance redefinition
   - No Layer 2 platform contract redefinition
   - No solution architecture or design decisions (belongs to planning phase)
   - No implementation details or code

Review Output

Generate a review document with:

1. **Decision**: APPROVED or REJECTED
2. **Summary**: Brief overview of review findings
3. **Findings**: Detailed list of issues (if any), categorized as:
   - **Critical**: Must fix before approval (missing required sections, metadata errors)
   - **Major**: Should fix (unclear requirements, missing traceability)
   - **Minor**: Nice to fix (style issues, minor clarifications)
4. **Recommendations**: Specific actions to address findings

If APPROVED:
- All 7 required sections are present and substantive
- Metadata is compliant
- Encoding is ASCII-only
- No governance violations

If REJECTED:
- Provide specific, actionable feedback
- Cite exact sections or text that need changes
- Explain what must be fixed for approval
- Do NOT reject for sections not in the authorized list above

Output Instructions

- Write the review document to `REVIEW_FILE_SUGGESTED` path.
- Use ASCII-only characters.
- Use plain text section headings.
- Provide direct citations to offending text when rejecting.
- Be specific and actionable in feedback.
