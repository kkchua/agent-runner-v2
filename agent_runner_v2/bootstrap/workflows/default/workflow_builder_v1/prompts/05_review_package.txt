Objective

Review the generated workflow package for quality, consistency,
compliance with the workflow creation guide, and -- most importantly --
fulfillment of the spec objective. Produce a detailed review document
with an APPROVED or REJECTED verdict.

Reference Inputs

- Read {TEST_CRITERIA} for the acceptance criteria -- verify the generated
  package fulfills ALL criteria in the "Criteria for review_package step"
  section. This is the primary verification contract.
- Read {WORKFLOW_SPEC_FILE} for the original specification -- verify the
  generated workflow actually implements what the spec describes.
- Read {WORKFLOW_MANIFEST} for the generated workflow.toml.
- Read {WORKFLOW_EXTENSIONS} for the generated context_extensions.py.
- Read {WORKFLOW_ACTIONS} for the generated actions.py (if action steps
  were declared).
- Read {WORKFLOW_PROMPTS_INDEX} for the list of generated prompt files.
- Read {VALIDATION_REPORT} for automated validation results.
- Read {WORKFLOW_README} for the generated user guide.
- Read {WORKFLOW_ENV_SAMPLE} for the generated env template (if it exists).
- Read {WORKFLOW_CONFIG_SAMPLE} for the generated config template (if it
  exists).
- Read {GATEKEEP_REQUIREMENTS}, {GATEKEEP_ARTIFACTS}, {GATEKEEP_STEPS},
  {GATEKEEP_PACKAGE} to verify gatekeepers ran and their verdicts.
- Read {WORKFLOW_CREATION_GUIDE} Part E (Common Pitfalls) for the review
  checklist.

Review Checklist

1. workflow.toml checks:
   - stepCompletion terminal step is present as the last [[step]]
   - init_step matches the first step name
   - Every onsuccess target references a valid step name or stepCompletion
   - promotes key is at [[step]] top level, not inside [step.artifacts]
   - onsuccess is at step level, not inside [step.artifacts]
   - Every prompt step has [step.coder] with a valid role_policy
   - Every prompt step has [step.artifacts] with produces and result_meta_key
   - Review steps have requires_human_approval_after and [step.on_reject_refine]
   - Refine steps have loop_returns_to pointing to the review step
   - Step names are lowercase_with_underscores and unique

2. context_extensions.py checks:
   - WorkflowExtensions class is present and inherits correctly
   - workflow_name matches the workflow directory name
   - register_artifact_keys() returns relative paths with {job_id}, {seq},
     {slug} placeholders
   - build_context_extensions() returns absolute paths
   - install_to_global() method is present
   - sync_to_backend() method is present
   - All artifact keys from workflow.toml produces lists appear in
     register_artifact_keys()
   - Module, class, and methods have docstrings

3. Prompt file checks:
   - Every prompt file listed in the index exists
   - Placeholders use bare {KEY} format, never backtick-wrapped
   - All content is ASCII-only
   - Each prompt has Objective, Reference Inputs, and Output Instructions
   - Artifact key references in prompts match keys in the artifact contract

3b. Prompt Quality Evaluation (for prompt-driven steps):
   For each prompt-driven step, evaluate whether the prompt is clear and
   unambiguous enough for an LLM to follow correctly:
   - Output mechanism: Does the prompt EXPLICITLY instruct the LLM to use
     file-writing tools to create actual files on disk? Does it clarify that
     the meta.json result field is for status/summary ONLY?
   - Ambiguity check: Are there phrases that could be misinterpreted?
     (e.g., "Write the output to: {ARTIFACT_KEY}" is ambiguous -- it could
     mean write to file OR put in result field. The prompt must be explicit.)
   - Common LLM mistakes: Does the prompt guard against known failure modes?
     (e.g., putting JSON data in result field, forgetting to archive inputs,
     skipping index file creation)
   - Completeness: Does the prompt specify all required outputs, formats,
     file naming conventions, and the exact location of each artifact?
   - Would an LLM reading this prompt produce the expected output? If not,
     what is unclear?
   REJECT if any prompt-driven step has ambiguous output instructions that
   could cause the LLM to put artifact data in the result field instead of
   writing files to disk.

4. Supplementary file checks:
   - README.md exists and includes Overview, Prerequisites, Installation,
     Usage, Step Reference, and Artifact Keys sections
   - README.md workflow name matches the slug from the spec filename
   - README.md step reference table matches the steps in workflow.toml
   - .env.sample exists only if the workflow needs environment variables;
     each variable has a descriptive comment and placeholder value
   - config.json.sample exists only if the workflow needs runtime config;
     must be valid JSON with sensible defaults
   - If .env.sample or config.json.sample is not needed, verify they were
     correctly omitted (not generated as empty files)

5. Cross-file consistency:
   - Artifact keys are consistent between workflow.toml and
     context_extensions.py
   - Step names in workflow.toml match prompt file naming convention
   - Routing targets in workflow.toml reference existing step names
   - README.md artifact key table matches keys in context_extensions.py
   - Configuration section in README.md matches .env.sample and
     config.json.sample content (if those files exist)

6. Spec fulfillment verification (read {TEST_CRITERIA} and {WORKFLOW_SPEC_FILE}):
   - Does the generated workflow actually implement the spec objective?
   - For each step in the spec: does the corresponding generated step
     (prompt or action) actually do what the spec describes?
   - For action-driven steps: does actions.py contain actual implementation
     logic (API calls, data transformations, error handling), not stubs?
   - For prompt-driven steps: do the prompts instruct the LLM to produce
     what the spec requires?
   - Does the data flow between steps match the spec's pipeline?
   - Are there any hallucinated elements not in the spec (extra configs,
     wrong models, unnecessary required_inputs)?
   - Verify ALL criteria in the "Criteria for review_package step" section
     of {TEST_CRITERIA} pass

7. Gatekeeper effectiveness (read gatekeeper reports):
   - Did gatekeep_requirements run and approve? If it rejected, were issues
     fixed before reaching this review?
   - Did gatekeep_artifacts run and approve? Did it catch any missing
     artifacts (e.g., WORKFLOW_ACTIONS) early?
   - Did gatekeep_steps run and approve? Did it catch any routing or
     data flow issues early?
   - Did gatekeep_package run and approve? Did it catch any missing
     files or design mismatches early?
   - If any gatekeeper REJECTED but issues weren't fixed, note this as
     a process failure (gatekeepers should have blocked progression)

8. Audit Verification (if TEST_CRITERIA includes audit criteria):
   Read the "Audit Criteria (Conditional)" section of {TEST_CRITERIA} and
   verify the generated workflow addresses each audit concern:
   - Security Audit: Are API keys loaded from .env (not hardcoded)? Are
     credentials passed securely? Are there no credential values in generated
     files or logs? Does the workflow handle auth failures gracefully?
   - Logic Audit: Does retry logic handle all relevant failure modes? Are
     timeouts configured and reasonable? Does error handling distinguish
     recoverable vs fatal errors? Is state properly managed across steps?
   - Data Integrity Audit: Are file operations atomic? Are indexes updated
     correctly? Is archiving done correctly (copy then remove)? Are batch
     operations tracked? Is partial failure handled?
   For each audit criterion, state PASS or FAIL with evidence.
   REJECT if any audit criterion fails.

Output Instructions

- Write the review document to {REVIEW_FILE_SUGGESTED}.
- Output must be ASCII-only.
- Include YAML frontmatter with at minimum:
  - doc_type: "workflow_review"
  - lifecycle_status: "draft"
  - effective_version: "{job_id}"
- Include these sections:
  1. Summary: one-paragraph overall assessment.
  2. workflow.toml Findings: pass/fail for each check with evidence.
  3. context_extensions.py Findings: pass/fail for each check with evidence.
  4. Prompt File Findings: pass/fail for each check with evidence.
  4b. Prompt Quality Evaluation: for each prompt-driven step, evaluate clarity,
      ambiguity, output mechanism explicitness, and common mistake guards.
  5. Supplementary File Findings: pass/fail for README.md, .env.sample,
     and config.json.sample checks with evidence.
  6. Cross-File Consistency: pass/fail for each check with evidence.
  7. Spec Fulfillment: pass/fail for each test criteria item with evidence.
  8. Gatekeeper Effectiveness: pass/fail for each gatekeeper check.
  9. Audit Verification: if TEST_CRITERIA includes audit criteria, pass/fail
      for each audit item with evidence.
  10. Issues: numbered list of specific issues to fix (if any).
  11. Verdict: APPROVED or REJECTED on its own line at the end.
- If REJECTED, each issue must include the file, location, and specific fix
  required.

Decision Rules

- APPROVED: All checks pass or have only minor cosmetic notes that do not
  affect functionality. Spec fulfillment criteria all pass. Prompt quality
  evaluation passes (no ambiguous output instructions). Audit criteria pass
  (if applicable).
- REJECTED: Any missing required element, key mismatch, routing error,
  backtick-wrapped placeholders, non-ASCII content, spec fulfillment
  failure (generated workflow does not implement what spec describes),
  prompt quality failure (ambiguous output mechanism that could cause LLM
  to put data in result field instead of writing files), or audit criterion
  failure.

CRITICAL: The meta.json status field MUST match your review verdict exactly.
- If your review document says APPROVED, set meta.json status to "APPROVED".
- If your review document says REJECTED, set meta.json status to "REJECTED".

Forbidden Content

- Modifying workflow files directly (that is the refine step)
- Vague findings without specific file and location references
- Non-ASCII characters
