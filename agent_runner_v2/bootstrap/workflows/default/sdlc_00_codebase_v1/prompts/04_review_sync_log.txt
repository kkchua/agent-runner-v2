Objective

Review the codebase sync operation for accuracy, completeness, and
compliance with codebase documentation standards.

Layer Boundary

- This workflow belongs to Layer 3 and operates as a maintenance workflow.
- Review only the staged codebase documentation -- do not modify source code.
- Treat Layer 1 governance and Layer 2 platform constitution as read-only reference inputs.

Reference Inputs

- Read the sync log at SYNC_LOG.
- Read the staged codebase inventory at CODEBASE_INVENTORY.
- Read the staged change impact report at CODEBASE_CHANGE_IMPACT.
- Read codebase documentation standards at {CODEBASE_DOC_ROOT}/00_standards/.

Review Criteria

1. Sync Log Accuracy:
   - The sync log exists at the SYNC_LOG path
   - The sync log accurately documents what was scanned and synced
   - File counts match the actual repository state
   - The sync operation completed without errors

2. Codebase Inventory Completeness:
   - All Python modules are documented in the inventory
   - All markdown documentation files are listed
   - All configuration files are accounted for
   - Directory structure is accurately represented

3. Module Documentation Quality:
   - Each Python module has a corresponding doc in 02_modules/
   - Module docs accurately describe the module's purpose
   - Module docs list the correct public functions/classes

4. Component Documentation Quality:
   - Component docs in 03_components/ cover all major subsystems
   - Component docs accurately describe component responsibilities
   - Component docs reference the correct modules

5. Change Impact Report:
   - Docs created and docs updated are correctly distinguished
   - A doc that did not previously exist belongs in "Documentation Created" only
   - A doc that existed before belongs in "Documentation Updated" only
   - The same file must NOT appear in both "Documentation Created" and "Documentation Updated"
   - Stale docs (if any) are flagged

Required YAML Frontmatter Fields

Every staged document (module docs, component docs, inventory, change impact)
MUST include these exact YAML frontmatter fields with these exact values:

| Field            | Expected Value           |
|------------------|--------------------------|
| doc_type         | "system"                 |
| authority        | "workflow-generated"     |
| scan_policy      | "include"                |
| lifecycle_status | "approved"               |
| version          | "1.0.0"                  |

Check EVERY staged document for these fields. If any field is missing or has
a wrong value, REJECT the review.

Output Instructions

- Write the review document to REVIEW_FILE_SUGGESTED path.
- Include explicit findings for each review criterion above.
- Include direct citations to specific files or sections when reporting issues.
- Include an explicit decision: APPROVED or REJECTED.
- If REJECTED, include specific refinement instructions listing every file
  that needs changes and what changes are needed.

Decision Rules

- APPROVE only when ALL of these are true:
  - Sync log exists and is accurate
  - Inventory is complete (all modules accounted for)
  - All module and component docs have correct governance metadata
  - Change impact report correctly separates created vs updated docs

- REJECT when ANY of these is true:
  - Sync log is missing or inaccurate
  - Any module or component doc is missing
  - Any document lacks required metadata fields (doc_type, authority,
    scan_policy, lifecycle_status, version)
  - Change impact report lists the same file in both created and updated

CRITICAL: The meta.json status field MUST match your review decision exactly.
- If your review document says APPROVED, set meta.json status to "APPROVED".
- If your review document says REJECTED, set meta.json status to "REJECTED".
- Do NOT write APPROVED in the document and REJECTED in meta.json (or vice versa).

Forbidden Content

- Modifying source code files
- Layer 1 governance redefinition
- Layer 2 platform contract redefinition
- Vague findings without specific evidence
