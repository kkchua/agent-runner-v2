Objective

Generate the operational workflow design for the composition system. This
defines how the workflow operates on the three-layer architecture -- the
scan → resolve → generate pipeline that takes component libraries and
compositions as input and produces resolved outputs.

The operational workflow design must define:
- Workflow phases (scan, plan, generate, review)
- Step sequence with types (prompt-driven vs action-driven)
- Artifact contracts (input/output artifacts for each step)
- Action implementations needed (for deterministic operations)
- Routing (onsuccess, on_reject_refine)

Operational Workflow Design Principles

1. Follow the universal workflow pattern from the Composition System Standard:
   - Scan phase: Discover and validate all components in the library
   - Plan phase: Read compositions, resolve references, identify overrides
   - Generate phase: Resolve components and placeholders, assemble outputs
   - Review phase: Quality review of generated outputs
   - Refine phase: Fix issues found in review (conditional)

2. Step type classification:
   - Action-driven steps: Deterministic operations (file scanning, validation,
     data processing, API calls)
   - Prompt-driven steps: LLM judgment (generation, review, refinement)
   - Classify each step based on the nature of the task

3. Artifact flow:
   - Each step has required_inputs (what it reads) and produces (what it writes)
   - Artifact flow must be traceable from inputs to outputs
   - No step should read an artifact that no prior step produced

4. Routing design:
   - onsuccess: Next step in sequence (refine steps use this to return to review)
   - on_reject_refine: Review → refine → back to review loop
   - max_iterations: Limit refine loops (default 2)
   - exhausted_failure_code: Terminal failure when loops exhaust

5. Action specifications:
   - For each action-driven step, specify:
     - Action name (lowercase_with_underscores)
     - Purpose: what the action does
     - Inputs: what it reads
     - Outputs: what it produces
     - Logic: high-level description of the operation
   - Check if existing reusable actions cover the need before proposing new ones

Generation Tasks

Produce an operational workflow design document with these sections:

1. Overview
   - One-paragraph summary of the workflow's purpose
   - The end-to-end transformation (inputs → outputs)
   - Domain context (what kind of deliverables this workflow produces)

2. Workflow Phases
   - Scan phase: What components are scanned? What validation is performed?
   - Plan phase: What compositions are read? What references are resolved?
   - Generate phase: What outputs are generated? How are they assembled?
   - Review phase: What quality checks are performed?
   - Refine phase: What issues are fixed? (conditional)

3. Step Sequence
   For each step:
   - Step name (lowercase_with_underscores)
   - Step type: 'prompt' or 'action'
   - Purpose: what this step achieves
   - required_inputs: artifact keys this step reads
   - produces: artifact keys this step writes
   - Routing: onsuccess, on_reject_refine (if applicable)

4. Artifact Contract
   - Input artifacts: table with key, description, required/optional
   - Output artifacts: table with key, description, produced by which step
   - Traceability: can trace each output back to its producing step

5. Action Specifications
   For each action-driven step:
   - Action name
   - Purpose
   - Inputs (context variables, files)
   - Outputs (files, data structures)
   - Logic (high-level description)
   - reused_from: "existing_action_name" or "new"

6. Routing Diagram
   - Visual representation of step flow
   - Show onsuccess, on_reject_refine
   - Highlight review/refine loops

7. Review/Refine Loop Design
   - Which steps have review/refine loops?
   - What triggers refinement (REJECTED verdict)?
   - How many iterations allowed (max_iterations)?
   - What happens when loops exhaust (exhausted_failure_code)?

8. Package File Inventory
   Enumerate EVERY file the generate_package step must CREATE. This is a
   checklist for the package assembly step -- if a file is not listed here,
   it will not be generated. Include:
   - Core files: workflow.toml, context_extensions.py, README.md
   - Conditional files: actions.py (if action steps exist), .env.sample
     (if env vars needed), config.json.sample (if runtime config needed)
   - Prompt files: One prompts/NN_step_name.txt per prompt-driven step
   - Supplementary files: Domain-specific data files the workflow needs at
     runtime (e.g., audience definition files, template files, schema files,
     config files). These are files the scan step or other steps expect to
     find deployed with the workflow package. If the design mentions an
     "audiences/" directory or any runtime data directory, every file in
     that directory must be listed here.
   For each file, list: file name, relative path under the package root,
   and purpose (why this file must exist).

Context Verification (Before Self-Critic)

Verify consistency with ALL prior artifacts:

1. Component Schema Alignment: Does the scan phase validate components against
   {COMPONENT_SCHEMA_FILE} rules? Are all component types accounted for?
2. Composition Format Alignment: Does the plan phase resolve compositions
   following {COMPOSITION_FORMAT_FILE} rules (references, overrides,
   placeholders)?
3. Output Format Alignment: Does the generate phase produce outputs matching
   {OUTPUT_FORMAT_FILE} structure and quality requirements?
4. Three-Layer Traceability: Can you trace a component from schema -> composition
   -> output -> workflow step? No layer should be orphaned.
5. Test Criteria Alignment: Does the design satisfy {TEST_CRITERIA_FILE}
   sections 8-9? Check each criterion.
6. Artifact Flow Integrity: Does every step's required_inputs reference an
   artifact produced by a prior step (or an input artifact)? No dangling
   references.
7. Action Reuse: For each action-driven step, did you check if an existing
   reusable action (promote_workflow_package, step_completion) covers the need?
8. Package Inventory Traceability: Does the Package File Inventory reference
   every supplementary file mentioned in the Step Sequence or Artifact
   Contract? For example, if a scan step reads from "audiences/" at runtime,
   are the audience definition files individually listed in the inventory?

If any inconsistency is found, fix it before proceeding.

Self-Critic (Before Self-Validation)

Challenge your reasoning before checking completeness:

1. Am I introducing workflow phases not supported by the spec?
2. Are my step classifications (prompt vs action) appropriate?
3. If a downstream step reads this design, would it know what to implement?
4. Did I follow the Composition System Standard's workflow pattern?

If you find reasoning issues, fix them before proceeding to Self-Validation.

Self-Validation (Before Output)

Before reporting APPROVED, validate:

1. Phase Completeness: Does the design define all workflow phases (scan, plan,
   generate, review, refine)?

2. Step Sequence: Is the step sequence logical and complete? Can trace artifact
   flow from inputs to outputs?

3. Step Type Classification: Are step types (prompt vs action) appropriate?
   Are deterministic operations classified as actions?

4. Artifact Flow: Does each step read artifacts produced by prior steps? Are
   there any dangling references?

5. Action Specifications: Are action specifications complete (name, purpose,
   inputs, outputs, logic)? Were existing reusable actions checked?

6. Routing: Is routing correct (onsuccess, on_reject_refine)?
   Are review/refine loops properly designed?

7. Standard Conformance: Does the design follow the Composition System
   Standard's workflow pattern?

8. Package File Inventory: Does the design explicitly enumerate every file
   the package must contain? Are supplementary data files (like runtime
   audience definitions, templates, schemas) listed in the inventory?

If validation fails, report REJECTED with specific gaps found.
