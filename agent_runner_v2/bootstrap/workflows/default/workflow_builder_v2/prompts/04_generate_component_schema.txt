Objective

Generate the component schema for the composition system. This defines Layer 1
of the three-layer architecture -- the standardized building blocks (LEGO bricks)
that compositions will reference.

The component schema must define:
- All component types from the spec (e.g., hook, scene, voice_style for video
  manuscripts; ui_page, api_endpoint for software applications)
- Common properties shared by all components (component_id, component_type,
  name, version, description)
- Type-specific properties for each component type
- Validation rules for each component type
- Extensibility model for adding new types

Reference Inputs

- Read {WORKFLOW_SPEC_FILE} for the composition system specification.
  Section 2 (Component Schema) is the AUTHORITATIVE source for component types.
  It lists all component types, their type-specific properties, validation rules,
  and example components. Your task is to VALIDATE and EXPAND these into a full

  component types, your schema must define exactly those 7 types.
- Read {TEST_CRITERIA_FILE} for acceptance criteria -- sections 2 and 3

- Read {COMPOSITION_SYSTEM_STANDARD} Section 3 (Universal Component Schema)
  for the standard schema pattern -- defines common properties, type-specific
  properties, validation rules, and extensibility model.

Component Schema Design Principles

1. Follow the universal component schema from the Composition System Standard:
   - Common properties: component_id, component_type, name, version,
     duration_range (optional), platforms (optional), tags (optional),
     description
   - Type-specific properties: defined per component_type, with type,
     required/optional, description

2. Component types must be domain-appropriate:
   - Read the spec to understand what kind of deliverables this system produces
   - Identify the natural building blocks for that domain
   - Each type should represent a distinct concern (e.g., "hook" for opening
     sequence, "scene" for content segment, not "content_block" for everything)

3. Type-specific properties must be concrete and actionable:
   - BAD: "properties: { ... }" (too vague)
   - GOOD: "hook_style: enum [dramatic_reveal, question_hook, statistic_hook]
     -- the opening technique used"
   - Each property should have: name, type, required/optional, description,
     example value

4. Validation rules must be enforceable:
   - Required fields present
   - Valid component_type
   - Unique component_id
   - Type-specific schema conformance
   - Semantic version format

5. Extensibility model must be clear:
   - New types can be added without breaking existing compositions
   - Common properties remain stable
   - Type-specific properties can evolve (MINOR: add optional, MAJOR: change
     required)

Generation Tasks

Produce a component schema document with these sections:

1. Overview
   - One-paragraph summary of the component library's purpose
   - Domain context (what kind of deliverables this system produces)
   - Number of component types defined

2. Common Properties
   - Table of properties shared by all components
   - For each property: name, type, required/optional, description
   - Follow the Composition System Standard's common properties

3. Component Types
   For each component type:
   a. Type Overview: name, purpose, when to use
   b. Type-Specific Properties: table with name, type, required/optional,
      description, example value
   c. Validation Rules: type-specific validation (beyond common rules)
   d. Example Component: one complete example in YAML frontmatter format

4. Validation Rules (Global)
   - Required fields present (component_id, component_type, name, version,
     description)
   - Valid component_type (must be in the defined type list)
   - Unique component_id (no duplicates within the library)
   - Type-specific schema conformance
   - Semantic version format (MAJOR.MINOR.PATCH)

5. Extensibility Model
   - How to add new component types
   - Backward compatibility rules
   - Versioning rules (MAJOR/MINOR/PATCH)

6. Component File Format
   - Markdown with YAML frontmatter
   - Example of a complete component file

Context Verification (Before Self-Critic)

Verify consistency with prior artifacts:

1. Spec Alignment: Does every component type trace back to a requirement in
   {WORKFLOW_SPEC_FILE}? No invented types.
2. Test Criteria Alignment: Does the schema satisfy the test criteria in
   {TEST_CRITERIA_FILE} sections 2-3? Check each criterion.
3. Standard Conformance: Does the common property list match the Composition
   System Standard's universal component schema?
4. Naming Consistency: Are component_type names lowercase_with_underscores?
   Are property names consistent with the spec's terminology?

If any inconsistency is found, fix it before proceeding.

Self-Critic (Before Self-Validation)

Challenge your reasoning before checking completeness:

1. Am I introducing component types not supported by the spec?
2. Are my type-specific properties concrete and actionable, or vague?
3. If a downstream composition references these components, would the
   schema be clear enough to validate against?
4. Did I follow the Composition System Standard's universal schema pattern?

If you find reasoning issues, fix them before proceeding to Self-Validation.

Self-Validation (Before Output)

Before reporting APPROVED, validate:

1. Type Completeness: Does the schema define ALL component types implied
   by the spec? Are there missing types?

2. Property Completeness: Does each type have complete type-specific
   properties with types, required/optional, descriptions, examples?

3. Validation Rules: Are validation rules present and enforceable? Can
   a gatekeeper use them to pass/fail components unambiguously?

4. Example Quality: Is there at least one example component per type?
   Are examples realistic and complete?

5. Standard Conformance: Does the schema follow the Composition System
   Standard's universal component schema pattern?

If validation fails, report REJECTED with specific gaps found.

Output Instructions

- Write the component schema to {COMPONENT_SCHEMA_FILE}.
- Output must be ASCII-only.
- Include YAML frontmatter with at minimum:
  - doc_type: "component_schema"
  - lifecycle_status: "draft"
  - effective_version: "{job_id}"
  - domain: "{domain_name}" (from spec)
  - component_type_count: {number}
- Use tables for property definitions.
- Use YAML code blocks for example components.
- Each component type must have its own section.

Forbidden Content

- Non-ASCII characters
- Vague property descriptions like "some value" or "varies"
- Component types not supported by the spec
- Missing type-specific properties
- Properties without type declarations
