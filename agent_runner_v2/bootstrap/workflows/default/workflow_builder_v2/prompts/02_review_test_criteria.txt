Objective

Review the generated test criteria document for completeness, clarity, and
alignment with the Composition System Standard. This review ensures the
acceptance contract is sound before downstream steps consume it.

The review asks: "Are these criteria specific enough to verify unambiguously?
Do they cover all three layers of the composition system? Will they catch
real quality issues?"

Reference Inputs

- Read {TEST_CRITERIA_FILE} for the criteria to review.
- Read {WORKFLOW_SPEC_FILE} for the original specification -- verify the
  criteria cover all spec objectives.
- Read {COMPOSITION_SYSTEM_STANDARD} for the standard -- verify the criteria
  align with the three-layer architecture (components, compositions, outputs).
- Read {META_WORKFLOW_BUILDER_ARCHITECTURE} for the builder architecture --
  verify the criteria cover all phases of the meta-workflow.

Review Checklist

1. Spec Coverage:
   - Does the test criteria cover ALL objectives from the spec?
   - Are there spec requirements not reflected in any criterion?
   - Does the Spec Objective Summary accurately capture the composition
     system's purpose?

2. Three-Layer Coverage:
   - Layer 1 (Components): Are there criteria for component schema quality,
     type completeness, validation rules, extensibility?
   - Layer 2 (Compositions): Are there criteria for composition format
     clarity, reference integrity, override mechanism, placeholder resolution?
   - Layer 3 (Outputs): Are there criteria for output completeness, reference
     expansion, self-containment, downstream contracts?

3. Phase Coverage:
   - Are there criteria for each of the 7 phases in workflow_builder_v2?
   - Are there gatekeeper criteria for each of the 5 gatekeeper steps?
   - Are there review/refine criteria for the review/refine loops?

4. Criterion Quality:
   - Is each criterion specific and verifiable (not vague like "must be
     correct")?
   - Can a reviewer determine pass/fail unambiguously from the criterion?
   - Are negative criteria marked with "MUST NOT" prefix?
   - Are there criteria that cannot be verified by reading generated files?

5. Gatekeeper Criteria Quality:
   - Does each gatekeeper step have dedicated criteria?
   - Do gatekeeper criteria cover the specific validation questions the
     gatekeeper must answer?
   - Do gatekeeper criteria require evidence-based verdicts?

6. Prompt Quality Criteria:
   - Are there criteria for prompt-driven step quality?
   - Do prompt criteria check for output mechanism clarity, ambiguity,
     common LLM mistakes?

7. Structural Quality:
   - Is the document organized by phase/step?
   - Are criteria numbered within sections?
   - Is YAML frontmatter present with correct fields?

Self-Critic (Before Final Verdict)

Challenge your review before committing to a verdict:

1. Am I rubber-stamping, or did I actually verify each criterion against
   the spec and standard?
2. Did I find at least one substantive finding, or am I just saying
   "looks good"?
3. If I missed a gap that a later step catches, what would it be?
4. Is my verdict based on evidence from the documents, or on assumptions?

If your review is superficial, go back and dig deeper before reporting.

Decision Rules

- APPROVED: The test criteria are complete, specific, verifiable, and cover
  all three layers of the composition system. All review checklist items pass.

- REJECTED: The test criteria have gaps (missing layers, vague criteria,
  uncovered spec objectives), will not catch real quality issues, or need
  significant revision. Include specific findings for each failed checklist item.

Output Instructions

- Write the review to {REVIEW_TEST_CRITERIA_FILE}.
- Include YAML frontmatter with doc_type: "review_report".
- Structure:
  1. Summary: Overall assessment (1-2 sentences)
  2. Review Results: Table with columns: Checklist Item, Status (PASS/FAIL),
     Evidence
  3. Issues (if any): Numbered list of specific gaps found
  4. Recommendations: Specific suggestions to fix issues
  5. Verdict: APPROVED or REJECTED on its own line
- All content must be ASCII-only.
- The result field in meta.json must match the verdict exactly.

Forbidden Content

- Non-ASCII characters
- Vague findings without specific evidence
- Approving criteria with known gaps
