# Attack Protocol

## Step 1: Attack Every Action Function

For each action function described in the runtime impl:

- Read the pseudocode/algorithm. Trace it line by line.
- What happens with EMPTY input? Does the function handle it or crash?
- What happens with MALFORMED input? (e.g., a .pdf file that's actually a renamed .txt)
- What happens with VERY LARGE input? (e.g., 10,000-page document)
- Does the function claim to support a format it cannot actually handle? (e.g., "reads .pdf" but the pseudocode only works for text-based PDFs, not scanned PDFs)
- Are there code paths where ALL branches return the same value (dead code)?
- Are there error paths that silently swallow errors and return success?

## Step 2: Attack Every Prompt-Driven Step

For each prompt-driven step:

- The design describes algorithms as pseudocode to be encoded in prompts. Can an LLM actually follow these instructions precisely?
- What happens when the LLM doesn't follow the algorithm? What fallback exists?
- Are the invariants CHECKABLE by the validation step? Or are they aspirational?
- Is the prompt instruction ambiguous in any way? Could two different LLMs interpret it differently?

## Step 3: Attack the Data Flow

Trace every artifact through the pipeline:

- Is every intermediate artifact actually produced in the format the next step expects?
- Are there serialization/deserialization gaps? (e.g., Step 3 produces a Python dict, Step 4 expects JSON)
- What happens when a step produces unexpected output? Does the next step crash or handle it gracefully?
- Are there circular dependencies or forward references?

## Step 4: Attack the Override Pattern

For each implementation variant:

- Can the impl.yaml override actually change what it claims to change?
- Are there shared actions that the variant needs to override but can't?
- Does the variant's override create inconsistencies with non-overridden steps?
- What happens when the variant's action function has a different signature than the shared action?

## Step 5: Attack the Constraint Enforcement

For each constraint:

- WHERE in the code is this constraint actually enforced? Point to the specific function and line.
- Is the enforcement DETERMINISTIC? Or does it rely on LLM judgment?
- What happens when enforcement FAILS? Does the workflow reject, retry, or silently continue?
- Can the constraint be bypassed by a specific input pattern?
