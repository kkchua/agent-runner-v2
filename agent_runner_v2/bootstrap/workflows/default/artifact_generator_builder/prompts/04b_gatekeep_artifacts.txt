# Self-Challenge Protocol

## Step 1: Runtime Execution Test

Mentally simulate the runtime processing this artifact contract:
- For each input artifact — can the runner resolve its path? Does the key follow naming conventions (`_FILE` for documents, `_DIR` for directories)?
- For each output artifact — does some step produce it? Is the path pattern unambiguous?
- For each intermediate artifact — is it produced before it is consumed? Does any step reference an artifact that does not exist?

Note every point where the simulation fails.

## Step 2: Devil's Advocate

Argue REJECT. Find the strongest case against approving this contract:
- Are there duplicate or conflicting artifact keys?
- Are there artifacts that are declared but never produced or consumed?
- Do the naming conventions break anywhere (`_FILE` suffix missing on inputs, or wrongly applied to outputs)?
- Would the runtime fail to resolve any path?

## Step 3: Cross-Reference Check

Compare the artifact contract against the runtime implementation:
- Does every artifact referenced in the runtime impl exist in the contract?
- Does every contract artifact have a corresponding reference in the runtime impl?

## Step 4: Verdict

After challenging, give your final verdict:
- **APPROVE** — The contract survived all challenges. All artifacts are consistent, complete, and resolvable.
- **REJECT** — The contract has unresolved defects. State what must be fixed.
