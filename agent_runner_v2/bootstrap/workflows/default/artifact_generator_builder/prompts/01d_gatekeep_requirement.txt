# Objective

Final gatekeep of the requirement analysis. Before approving, you must try to find reasons to REJECT.

# Reference Inputs

- REQUIREMENT_ANALYSIS_FILE: {REQUIREMENT_ANALYSIS_FILE}
- REVIEW_REQUIREMENT_FILE: {REVIEW_REQUIREMENT_FILE}

# Self-Challenge Protocol

## Step 1: Runtime Execution Test

Mentally simulate the next phase (composition spec design) consuming this requirement analysis:
- Read each input artifact declaration — could the runtime resolve it?
- Read each output artifact declaration — is the format specific enough to validate?
- Read each transformation requirement — is it unambiguous?

Note every point where the simulation stalls or requires a guess.

## Step 2: Devil's Advocate

Argue REJECT. Find the strongest case against approving this analysis:
- What ambiguities could lead to misinterpretation?
- What missing information will force the next phase to make assumptions?
- Are there contradictions between the analysis and the original requirement?

## Step 3: Review Feedback Check

Read the review ({REVIEW_REQUIREMENT_FILE}). Were all identified issues addressed? If the review said REJECT, are the specific defects fixed?

## Step 4: Verdict

After challenging, give your final verdict:
- **APPROVE** — The analysis survived all challenges. It is complete, accurate, and actionable.
- **REJECT** — The analysis has unresolved defects. State what must be fixed.

# Output Instructions

Write to: {GATEKEEP_REQUIREMENT_FILE}
Markdown with YAML frontmatter: doc_type: "gatekeep_requirement", verdict: "APPROVE" or "REJECT", identity_locked: true. ASCII-only.

Structure your gatekeep as:
1. Runtime Simulation Results (where it stalled or succeeded)
2. Devil's Advocate Argument
3. Review Feedback Resolution (issues addressed or not)
4. Final Verdict + reasoning

# Forbidden Content

- Do NOT approve if the devil's advocate found genuine blocking issues
- Do NOT include non-ASCII characters
