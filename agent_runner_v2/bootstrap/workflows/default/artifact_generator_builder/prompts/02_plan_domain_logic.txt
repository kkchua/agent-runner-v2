# Objective

Review the Analysis JSON and produce a detailed **Domain Plan** — the blueprint
that implement_domain (step 4) will follow to write actions.py and prompt files.

You are NOT designing infrastructure. workflow.toml and context_extensions.py
are assembled mechanically. You are planning the **domain logic only**: what
each action function does, what each prompt instructs, how data flows between
steps, and what validations each action performs.

# Reference Inputs

- ANALYSIS_JSON_FILE: {ANALYSIS_JSON_FILE}
  The Analysis JSON produced by step 1. Contains identity, domain_steps,
  artifact_keys, and implementations. Check for "extend_mode": true flag.

- REQUIREMENT_DOC: {REQUIREMENT_DOC}
  The original requirement document. Use this to understand domain context
  and validate that the plan covers all requirements.

- BASE_COMPOSITION_STANDARD: {BASE_COMPOSITION_STANDARD}
  Reference for action interface contract (Section 5) and multi-impl model
  (Section 4).

- EXISTING_WORKFLOW_DIR: {EXISTING_WORKFLOW_DIR}
  OPTIONAL — If provided, you are in EXTEND MODE. The existing workflow's
  actions.py and prompts/ are already implemented. Plan ONLY the new
  implementation's overrides.

# Mode Detection

**Check if Analysis JSON has "extend_mode": true:**

- **If extend_mode is false or absent** → NEW WORKFLOW MODE
  Follow the full Planning Protocol below. Plan all action steps, prompt steps,
  and implementation overrides.

- **If extend_mode is true** → EXTEND MODE
  1. The domain_steps and artifact_keys are ALREADY IMPLEMENTED in the existing
     workflow. Do NOT plan them again.
  2. Read the existing workflow's actions.py and prompts/ to understand what
     already exists: `{EXISTING_WORKFLOW_DIR}/actions.py` and
     `{EXISTING_WORKFLOW_DIR}/prompts/`
  3. Plan ONLY the new implementation's overrides:
     - Which steps are overridden by the new impl?
     - For each override: what changes (different prompt instructions? different
       action logic?)?
     - What files need to be written? (impls/{new_name}/actions.py,
       impls/{new_name}/prompts/)
  4. Skip Step 2 (Plan Each Action Step) and Step 3 (Plan Each Prompt Step) —
     those are already implemented.
  5. Go directly to Step 4 (Plan Implementation Overrides) and focus ONLY on
     the new implementation.

# Planning Protocol (NEW WORKFLOW MODE)

## Step 1: Validate Analysis JSON Against Requirement

Before planning, verify the Analysis JSON is complete and correct:

- Does every requirement in the doc map to at least one domain_step?
- Are the artifact keys sufficient to carry data through the pipeline?
- Do the implementations represent genuinely different strategies?
- Is the step ordering logical (dependencies flow forward)?

Report any gaps or inconsistencies before proceeding.

## Step 2: Plan Each Action Step

For every domain_step with type="action", specify:

### Function Design
- **Function name**: Must match action_name from Analysis JSON.
- **Purpose**: One sentence describing what this function does.
- **Input artifacts**: Which artifact keys it reads from state["artifacts"].
- **Output artifacts**: Which artifact keys it writes.
- **Core logic**: Describe the algorithm in pseudocode or detailed steps.
- **Format handling**: If the action processes files, specify which formats
  are supported and how each is parsed. Do NOT claim format support without
  real parsing logic. If a format requires an external library, declare it
  in requirements.txt.

### Validation Rules
- What input validations does this action perform at its boundary?
- What conditions cause REJECTED vs APPROVED?
- What reject_codes are defined?

### Error Handling
- What can go wrong in this action?
- How does the action signal failure (ActionResult status, reject_code)?

## Step 3: Plan Each Prompt Step

For every domain_step with type="prompt", specify:

### Prompt Design
- **Prompt filename**: Must match prompt_file from Analysis JSON.
- **Purpose**: What the LLM should accomplish when executing this prompt.
- **Input sections**: What context the prompt receives (artifact placeholders).
- **Output instructions**: What the LLM must produce and where to write it.
- **Validation checklist**: Self-check items the LLM must verify before
  completing.

### Data Flow
- What artifact placeholders does the prompt reference? (e.g., {PARSED_DOCUMENT})
- What does the LLM write, and which artifact key captures the output?

### Role Policy Justification
- Why is this role_policy appropriate for this step?

## Step 4: Plan Implementation Overrides

For each alternative implementation in the Analysis JSON:

- Which steps are overridden?
- What changes in the override (different prompt instructions? different
  action logic?)?
- What stays shared with the default?
- Where do impl-specific files go? (impls/{name}/actions.py,
  impls/{name}/prompts/)

## Step 5: Map the Complete Data Flow

Produce a data flow diagram (text-based) showing:

```
INPUT ARTIFACTS
    |
    v
[Step 1: action_name] -- produces --> INTERMEDIATE_A
    |
    v
[Step 2: prompt_file] -- consumes INTERMEDIATE_A -- produces --> INTERMEDIATE_B
    |
    v
...
    |
    v
[Step N: ...] -- produces --> OUTPUT ARTIFACTS
```

# Self-Validation

Before writing the output, verify:

- [ ] Every domain_step from the Analysis JSON has a corresponding plan section
- [ ] Every action function has defined input/output artifacts, core logic, and validation rules
- [ ] Every prompt has defined input placeholders, output instructions, and validation checklist
- [ ] Data flow is complete — no step consumes an artifact that no prior step produces
- [ ] Implementation overrides are specific — each lists exactly which steps differ and how
- [ ] All artifact key references match the Analysis JSON's artifact_keys definitions
- [ ] No infrastructure planning (workflow.toml, context_extensions.py) is included
- [ ] No format is silently dropped — all required input types have a plan

# Forbidden Content

- Do NOT write workflow.toml, context_extensions.py, or impl.yaml — the assembler handles those.
- Do NOT include non-ASCII characters.
- Do NOT reference old AGB concepts (composition spec, runtime impl, artifact contract).
- Do NOT plan infrastructure concerns (routing, step_completion, terminal steps).
