# Objective

Write the **domain logic** for the workflow package: the action functions in
actions.py and the prompt templates in prompts/. You are following the Domain
Plan as your blueprint — you are NOT designing, you are implementing.

The infrastructure files (workflow.toml, context_extensions.py, impl.yaml) are
assembled mechanically by the _assemble_package action. You do NOT write those.

# Mode Detection

**Check if Analysis JSON has "extend_mode": true:**

- **If extend_mode is false or absent** → NEW WORKFLOW MODE
  Follow the full Implementation Protocol below. Write Part A (actions.py),
  Part B (prompts/), and Part C (impl-specific files).

- **If extend_mode is true** → EXTEND MODE
  1. The shared actions.py and prompts/ are ALREADY IMPLEMENTED in the existing
     workflow at `{EXISTING_WORKFLOW_DIR}`. Do NOT rewrite them.
  2. Skip Part A and Part B entirely.
  3. Go directly to Part C and write ONLY the new implementation's files:
     - `impls/{new_impl_name}/actions.py` (if action overrides exist)
     - `impls/{new_impl_name}/prompts/{prompt_filename}` (if prompt overrides exist)
  4. Read the existing workflow's code to ensure your overrides are compatible
     with the shared actions and prompts.

# Implementation Protocol

## Part A: Write actions.py

Write to: {WORKFLOW_ACTIONS_FILE}

### Required Structure

```python
"""Domain actions for {workflow_name}.

Auto-generated by AGB v3. Implements domain-specific action functions.
"""
from __future__ import annotations

import json
from pathlib import Path
from typing import Any

from agent_runner_v2.action_result import ActionResult
from agent_runner_v2.workflow_packages.actions import action


@action("action_name_here")
def action_name_here(*, context, state, step_cfg, project_root):
    """One-line description of what this action does."""
    project_root = Path(project_root)

    # Read input paths from context (resolved by context_extensions.py)
    input_path = context.get("INPUT_KEY")

    # Resolve output path from context (NOT state["artifacts"])
    output_path_str = context.get("OUTPUT_KEY")
    if not output_path_str:
        return ActionResult(
            status="REJECTED",
            remark="OUTPUT_KEY output path not found in context",
            artifacts={},
            reject_code="MISSING_OUTPUT_PATH",
        )
    output_path = Path(output_path_str)
    output_path.parent.mkdir(parents=True, exist_ok=True)

    # ... implementation ...

    return ActionResult(
        status="APPROVED",
        remark="Description of what was done",
        artifacts={"OUTPUT_KEY": str(output_path)},
    )
```

### MANDATORY Action Rules

1. **Decorator**: Every action function MUST be decorated with
   `@action("action_name")` where action_name matches the Analysis JSON's
   domain_steps[].action_name.

2. **Signature**: Every action function MUST use keyword-only arguments:
   `(*, context, state, step_cfg, project_root)`.

3. **Return type**: Every action function MUST return an `ActionResult` with
   status ("APPROVED" or "REJECTED"), remark (string), and artifacts (dict).

4. **Boundary validation**: Every action MUST validate its inputs at the
   function boundary. Check that required artifact paths exist, are readable,
   and contain parseable data. Return REJECTED with a descriptive reject_code
   on validation failure.

5. **Complete implementations**: Every function MUST contain a COMPLETE,
   WORKING implementation. No stubs, no placeholder fallbacks, no
   "TODO: implement" comments. If a function claims to support a format,
   it MUST contain real extraction logic for that format.

6. **No false format claims**: If the function cannot genuinely parse a format
   (e.g., binary PDF with no text layer), do NOT claim to support it. If a
   format requires an external library, implement real parsing logic using
   that library and declare the dependency in requirements.txt. Do NOT
   silently drop formats that the requirement doc asks for.

7. **Meaningful error paths**: Every branch MUST produce a meaningful result.
   No dead-code branches where all paths return the same value. Every REJECTED
   path MUST have a distinct reject_code.

8. **Artifact writes**: When writing output artifacts, the function MUST read
   the output path from `context` (not `state["artifacts"]`). The context dict
   contains resolved absolute paths for all artifact keys (set by
   context_extensions.py). Use `context.get("OUTPUT_KEY")` to get the output
   path. Create parent directories as needed.

## Part B: Write Prompt Files

Write each prompt template to: {WORKFLOW_PROMPTS_DIR}{prompt_filename}

### MANDATORY Prompt Rules

1. **Input section**: Every prompt MUST clearly list what inputs the LLM
   receives, using curly-brace syntax for artifact paths (e.g., `{ARTIFACT_KEY_NAME}`).
   Example: `PARSED_DOCUMENT: {PARSED_DOCUMENT}`

2. **Output section**: Every prompt MUST specify exactly where to write the
   output and what format to use.
   Example: `Write to: {TRANSFORMED_CONTENT}`

3. **Domain instructions**: The prompt MUST contain all domain-specific
   instructions from the Domain Plan. Do not assume the LLM knows the domain.

4. **Validation checklist**: Every prompt MUST include a self-validation
   section before the output instructions. The checklist items MUST be
   specific to the domain (not generic "check your work").

5. **Placeholder consistency**: Every artifact placeholder (text in curly braces
   like `{ARTIFACT_KEY}`) referenced in the prompt MUST correspond to an actual
   artifact key in the Analysis JSON's artifact_keys. Do not use generic example
   text like `{PLACEHOLDER}` — only reference real artifact keys that exist.

6. **Forbidden content in prompts**:
   - Do NOT reference infrastructure files (workflow.toml, context_extensions.py)
   - Do NOT reference old AGB concepts (composition spec, runtime impl)
   - Do NOT include non-ASCII characters

## Part C: Write Implementation-Specific Files

For each alternative implementation in the Analysis JSON that has overrides:

### Impl-specific actions
If an override specifies a different action, write the function to:
`impls/{impl_name}/actions.py`

Use the same action contract (decorator, signature, return type). The function
name MUST match the override's action name.

### Impl-specific prompts
If an override specifies a different prompt, write the file to:
`impls/{impl_name}/prompts/{prompt_filename}`

Follow the same prompt rules as Part B. The prompt MUST implement the variant
strategy described in the Domain Plan.

## Part D: Write requirements.txt

Write to: {WORKFLOW_REQUIREMENTS_FILE}

You MUST always create a requirements.txt file, even if the workflow has no
external dependencies. This file is a declared artifact and the validator
will check for its existence.

If external libraries are used in actions.py, list ALL of them — one package
per line, with version pins where appropriate.

Example (with dependencies):
```
PyPDF2>=3.0.0
python-docx>=1.0.0
openpyxl>=3.1.0
```

If no external dependencies are needed, write a file with a single comment:
```
# No external dependencies required — all imports are from the Python standard library.
```

Rules:
- Only include packages that are actually imported in actions.py
- Do NOT include Python standard library modules (json, pathlib, shutil, etc.)
- Use `>=` version pins for minimum versions when known
- The file MUST exist at {WORKFLOW_REQUIREMENTS_FILE} even if empty/commented

# meta.json Reporting

When writing your meta.json sidecar, report ONLY these artifact keys:

- `WORKFLOW_ACTIONS_FILE` — path to the shared actions.py
- `WORKFLOW_PROMPTS_DIR` — path to the prompts/ directory
- `WORKFLOW_REQUIREMENTS_FILE` — path to requirements.txt (only if external deps exist)

Do NOT report implementation-specific files (impls/*/actions.py, impls/*/prompts/)
in meta.json. Those are tracked by the assemble_package step (step 6) under
`IMPL_OVERRIDE_FILES`. Reporting undeclared artifact keys causes a
STEP_CONTRACT_MISMATCH rejection.
