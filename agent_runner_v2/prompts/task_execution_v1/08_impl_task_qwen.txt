Speculative Design Guardrails (QWEN-SPECIFIC — MANDATORY):

YOU ARE WRITING AN IMPLEMENTATION PLAN, NOT SPECULATIVE DESIGN DOCUMENT.

An implementation plan translates task requirements into technical design guidance. It must NOT invent design decisions about unverified codebase state, prescribe workaround patterns, or assume dependency APIs exist with specific signatures.

MUST NOT include in implementation plans:
- ❌ No assumed method signatures for dependency APIs (e.g., "Repository must have `update_status()`, `update_metrics()`")
- ❌ No exact parameter lists for methods that call unverified repository/service APIs
- ❌ No pseudo-code data flow diagrams with exact enum values, return types, or constructor fields
- ❌ No speculative test fixture names (e.g., "fixture `mock_repo`", "fixture `mock_build_run`")
- ❌ No predicted test case counts (e.g., "25 tests total: 19 for X, 6 for Y")
- ❌ No design decisions about workarounds (e.g., "in-memory filtering is acceptable for current scope")
- ❌ No assumed ORM column names or constructor required fields without reconciliation language
- ❌ No exception class names for dependencies unless explicitly defined in upstream task/plan
- ❌ No exact enum value specifications beyond what the task/plan explicitly requires
- ❌ No speculating about upstream API design choices (e.g., "contract_id may not exist yet — reconcile whether to use placeholder")
- ❌ No inspecting irrelevant layers (e.g., "inspect ORM constructor" in a service-integration task that doesn't touch persistence)
- ❌ No prescribing internal error context shapes for downstream services (e.g., "error context must include step name, exception type, message")
- ❌ No exact method signatures in data flow diagrams — use logical calls like `create_build_run(...)` or `mark_failed(build_run_id, exception)`
- ❌ No listing multiple architectural redesign options for uncertain APIs (e.g., "options: (a) placeholder UUID, (b) add parameter, (c) delay creation") — state the uncertainty and instruct "inspect upstream service contract"

MUST DO in implementation plans:
- ✅ Use "INSPECT/RECONCILE" language for uncertain dependency APIs (e.g., "Inspect `build_run_repo.py` to confirm method signatures")
- ✅ Frame dependency calls as "verify then use" not "use directly"
- ✅ Describe data flow as logical sequences (A → B → C) without pseudo-code parameter details
- ✅ Specify test behaviors to validate, not fixture setups or mock configurations
- ✅ Ground risks in actual codebase uncertainty, not hypothetical scenarios

Dependency API Reconciliation rule (MANDATORY):
Before specifying any call to a dependency API (repository, service, enum, exception):
- If the dependency is from an UPSTREAM TASK that is not yet completed: use reconciliation language
  - ✅ "Inspect `X` to confirm available methods and signatures before implementation"
  - ✅ "Adapt service calls to match actual repository API"
  - ❌ "Delegate to `Repository.update_status()`" (assumes method exists)
- If the dependency is from COMPLETED upstream task or existing codebase: reference the actual code
  - ✅ "Use `list_documents_by_source()` from `document_repo.py` (confirmed existing)"
  - ❌ "Use `get_by_contract_id()`" (unverified — may not exist)
