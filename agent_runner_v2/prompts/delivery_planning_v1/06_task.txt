OUTPUT QUALITY STANDARD (MANDATORY)

A task document is a DETERMINISTIC EXECUTION CONTRACT — not a high-level assignment.
Every section must remove ambiguity, not describe it.

SPECIFICITY RULES:

1. Execution Steps — no discovery steps
   - Forbidden: "Examine router.py to understand current patterns"
   - Required: Each step names the exact file, the exact action, and ends with a verifiable artifact or state.
   - If you do not know an exact symbol name, derive it from the dependent task documents listed in the task graph (read them if referenced). Do NOT leave it as "the router".

2. Scope disambiguation
   - If the task graph mentions a vague deliverable (e.g. "update documentation", "wire X", "register routers"):
     - State explicitly what the deliverable IS and what it is NOT.
     - Example: "OpenAPI exposure is automatic from router metadata — no manual documentation strings are required" or "The following summary strings must be added: [list them]."
   - Do not pass vague scope through to the implementor.
   - For any task that involves repository calls, service calls, or lifecycle ordering, state the allowed call order and the forbidden calls explicitly.

3. Integration tasks — route and import precision
   - For any task that registers, wires, or connects components:
     - List every import statement needed (exact `from ... import ...` form, using symbol names from dependent task docs).
     - Enumerate every route path being added with its full prefix (e.g. `GET /contracts/{id}/build-runs`).
     - If multiple routers share a path prefix, explicitly state whether paths are distinct or collide and what the correct registration order is.

4. Validation Criteria — concrete checklist only
   - Forbidden: "All endpoints are accessible via HTTP"
   - Required: "[ ] GET /openapi.json contains path `/contracts` with tag `contracts`"
   - Required: "[ ] App import succeeds: `python -c 'from ukbe.app.api.router import api_router'`"
   - Every item must be independently verifiable with a specific expected outcome.
   - Every validation item must correspond to at least one execution step and one output artifact.

5. Outputs Completeness — every deliverable must be listed in Outputs section
   - Every file, module, migration, or test file mentioned in Execution Steps, Implementation Details, or Validation Criteria MUST also appear in the formal Outputs / Expected Artifacts list.
   - Forbidden: describing a deliverable in execution steps (e.g. "Create `GenerationRunRepository` at `ukbe/app/storage/repositories/generation_run_repo.py`") without listing it in the Outputs section.
   - This prevents executor/validator/reviewer scope mismatches where one agent treats a deliverable as in-scope and another treats it as undocumented drift.
