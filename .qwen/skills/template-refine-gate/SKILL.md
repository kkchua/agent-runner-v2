# Template Refine Gate Procedure

## When to use
This skill applies when a template generation step receives a `REJECTED` review and enters a refine loop (e.g., `refine_templates`, `refine_sop`, `refine_agents`).

## Governing rules
- Do NOT change fundamental template structure (metadata block, required sections, placeholder variables) unless explicitly flagged.
- Only modify what the review flagged as incorrect or incomplete.
- Every template must have a metadata block with `Doc Type` and `Template Version`.
- Do NOT add agent master prompt templates — they are deprecated.
- Re-read all input files from disk before refining.

## Required inputs
1. **Review feedback** — the rejection document with numbered findings (e.g., `RTEMPL-001`, `SOP-002`)
2. **Current templates** — the existing template files at their original paths
3. **Governing references** — SOP (`WORKFLOW_SOP_v1.md`) and status rules (`DELIVERY_STATUS_RULES_v1.md`)
4. **Project analysis** — the project context file

## Execution sequence

### Step 1: Read all inputs
- Read the review feedback document to identify each numbered finding
- Read each current template file
- Read the SOP and status rules for authoritative lifecycle enums, folder structure, and traceability requirements

### Step 2: Cross-reference findings against current state
- For each review finding, verify whether the issue still exists in the current files
- Review findings may reference an earlier version of the templates — do NOT apply fixes for issues already resolved
- Check each finding against the SOP and status rules as the authoritative source

### Step 3: Apply targeted changes
- Make minimal edits to address only the verified issues
- Use `edit` tool for surgical changes, not full rewrites
- Preserve all required sections from the original template definitions

### Step 4: Verify and write meta.json
- Confirm all affected files exist at their original paths on disk
- Write the `meta.json` sidecar alongside the primary output artifact (e.g., `docs/delivery/00_templates/template_registry.meta.json` for the template registry refine step)
- The sidecar must include: `status`, `remark`, `artifacts` map, `schema_version`, `runner_data`

### Step 5: Return final JSON
- Return only valid JSON matching the required schema
- No markdown, no explanation, no text before or after

## Common review finding categories
| Category | What to check | Authoritative source |
|---|---|---|
| SOP state machine alignment | Registry flow diagram and stage descriptions must match the SOP state machine ordering (e.g., Code before Implementation Record before Review, not after). Stage descriptions should reflect the correct gate sequence. Validation stage descriptions must cover the full governed scope: behavior, contracts, deterministic outputs, evidence, tests, traceability, sidecar presence, and approved state transitions — NOT just "structural validation against templates" | SOP "Workflow State Machine" section |
| Registry description accuracy | Stage descriptions in the registry must correctly attribute artifact ownership/role (e.g., "generated by the Validator through the runner-invoked validation action and accepted by the runner", NOT "generated by runner validation action, not a coder"). The SOP assigns artifact authorship to agent roles; the runner enforces/accepts — it does not author. | SOP agent role assignments and artifact contracts |
| Sidecar completeness | Registry must document ALL sidecar-required artifacts and decisions, not just markdown templates — include snapshot manifests, gate decisions, folder maps, and non-markdown outputs | SOP sidecar contract and runner data model |
| Naming convention accuracy | Documented naming patterns must cover every actual template file name, including variants like `02b_task_graph` where alphanumeric sub-prefixes denote sub-artifacts | Current template files in the registry |
| Folder mappings | Registry entries match SOP folder structure | SOP "Folder Structure" section |
| Lifecycle statuses | Template status enums match allowed lifecycle — keep review lifecycle status separate from its APPROVED/REJECTED decision | Status rules "Artifact Lifecycles" table |
| Traceability metadata | All required fields present: **ID + upstream source path + artifact version** for every linked artifact. IDs alone are insufficient — the status rules require paths and versions too (e.g., plan must have initiative ID, initiative path, and initiative version; task graph must have plan/initiative IDs, paths, and versions; task must have graph/plan IDs, paths, and versions). Check metadata blocks, reference sections, and any lists that name related artifacts | Status rules "Traceability Rule" — every artifact must preserve upstream IDs, source paths, versions, contract references, and relevant snapshot hashes |
| Review/validation target revision | Validation and review templates include `{{ARTIFACT_REVISION}}` in the Target table — revision traceability is mandatory | Status rules "Review and Validation Decision Rule" (target must include revision) |
| Review contract | Target, decision, findings, evidence, follow-up all present | Status rules "Review and Validation Decision Rule" |
| Missing templates | All SOP-required artifact types have templates | SOP "Workflow Phases" table |
| Placeholder consistency | No duplicate placeholders for the same value. Check ALL locations where a concept appears: metadata blocks, body sections, naming contracts, code-block examples. For example, if a review template uses `{{DOC_TYPE}}` in metadata for "Related Doc Type" but `{{RELATED_DOC_TYPE}}` in its naming contract section, unify to one name | Current template files — grep for the concept across the entire file |
| Cross-template ID consistency | Linked IDs (e.g., task IDs) use the same canonical shape across plan, task-graph, and task templates — not just within one file. Check ALL occurrences: metadata blocks, table cells, section headers, code-block examples, dependency lists, and scope mappings | Task template defines the authoritative shape |
| Registry ID accuracy | Registry documents actual per-type canonical ID rules, not a generic pattern that conflicts with generated templates | Each template's metadata block |
| Doc Type alignment | Each template's `Doc Type` in its metadata block matches the value declared for it in the registry table. Mismatches cause routing failures | Registry Document Type Mapping table vs each template's metadata |
| Flow/governance completeness | Registry flow diagram and governance notes cover all runner-enforced approval gates (initiative, plan, task-graph, impl-plan, per-task review, dependency release, aggregate review, validation, completion) | SOP "Workflow State Machine" and "Workflow Phases" |
| Task-graph execution flow | Execution examples show: per-task review → runner records Task: Implemented → Approved → dependency release → aggregate implementation review → final validation gate. Do NOT show tasks advancing directly to validator without per-task approval and aggregate review in between. | SOP "Workflow State Machine", "Per-Task Review and Dependency Release" |
| Dependency placeholder semantics | Dependency placeholders must clearly convey prerequisite IDs (e.g., `{{DEPENDENCY_TASK_IDS}}`), not downstream dependents | Task template Inputs section |
| Malformed HTML comments | All `<!-- ... -->` comment placeholders are properly closed. Unclosed comments will hide the remainder of the document in markdown renderers | Current template files — grep for `<!--` without matching `-->` |
| Registry workflow artifacts | Registry lists all mandatory workflow phases including implementation records, validation gates, and sidecar expectations — not just template-generated artifacts | SOP "Workflow Phases" and runner sidecar contract |

## Anti-patterns to avoid
- Rewriting templates that were not flagged as problematic
- Applying fixes for review findings that no longer apply to the current version
- Adding sections that the SOP and status rules do not require
- Changing placeholder variable names that are already consistent
