# Codebase Documentation SOP

## Purpose

This Standard Operating Procedure defines the codebase documentation lifecycle for governed repositories. It covers documentation coverage across all file types, freshness rules, supersession rules, and integration with the delivery workflow.

The codebase SOP applies universally to every repository governed by the scaffold. It defines a **universal ecosystem baseline** that applies to all repositories, then explains how repo-selected architecture profiles and migration modes refine that baseline.

### Key Distinctions

- **DDD, EDA, and similar architecture standards are conditional profile choices** — they are NOT universal defaults. A repository adopts them only when its architecture posture warrants it.
- The universal baseline applies to every repository regardless of architecture profile.
- `07_master_prompts` is deprecated and MUST NOT appear in any governed repository.

## Universal Ecosystem Baseline

Every governed repository MUST satisfy the universal baseline, regardless of its architecture profile or migration mode.

### Universal Baseline Requirements

1. **Inventory Coverage**: Every source module, configuration file, and script in the repository MUST be represented in the codebase inventory or module documentation.

2. **Freshness Contract**: Documentation MUST be updated in the same delivery cycle as the code it describes. No delivery completes with stale documentation in touched modules.

3. **Status Tracking**: Every codebase document carries a status (`active`, `stale`, `superseded`, `archived`) governed by `CODEBASE_DOC_STATUS_RULES_v1.md`.

4. **Workflow Integration**: Codebase documentation is not optional — it is a deliverable in every task graph. `20_initiative_intake_v1` captures documentation scope; `30_delivery_planning_v1` converts it into plan obligations; `31_task_execution_v1` executes and validates doc updates.

5. **Reconciliation**: `40_documentation_sync_v1` reconciles current code against active documentation and flags stale guidance. This workflow runs after delivery and periodically.

6. **Architecture Communication**: `50_architecture_site_v1` publishes browsable HTML views for stakeholders, developers, operators, and functional consumers — after the repository posture and docs are synchronized.

7. **Protection**: Workflow-generated documents are protected from manual edits via frontmatter and banner.

8. **No Deprecated Artifacts**: `07_master_prompts` is deprecated and MUST NOT be referenced, generated, or relied upon.

## Freshness Rules

### Freshness Definition

A codebase document is **fresh** when:
1. It accurately describes the current state of the code it documents
2. It was updated in the same delivery cycle as the last code change to the described module
3. Its status is `active` (not `stale` or `superseded`)

### Freshness Enforcement

- **On every delivery**: `validate_codebase_docs` checks that touched modules have fresh docs
- **On bundle-map change**: `scan_repo_codebase` triggers inventory reconciliation
- **On documentation sync**: `40_documentation_sync_v1` flags stale guidance across the corpus

### Staleness Detection

A document is considered **stale** when:
- The code it describes has changed since the document was last updated
- The document references APIs, functions, or configurations that no longer exist
- The document's information conflicts with the current codebase state
- The document has not been updated in more than one delivery cycle while the code changed

## Stale Content Policy

### Stale Content Handling

1. **Detection**: `40_documentation_sync_v1` identifies stale documents
2. **Flagging**: Stale documents are marked with `status: stale` in their frontmatter
3. **Repair**: Stale documents MUST be repaired in the next delivery that touches the described code
4. **Escalation**: If stale content is not repaired within two delivery cycles, it is escalated to the reviewer
5. **Supersession**: If a document is fundamentally outdated, it is superseded — see `CODEBASE_DOC_STATUS_RULES_v1.md`

### Stale Guidance Risk

The initiative intake phase (`20_initiative_intake_v1`) MUST assess stale-guidance risk:
- Which existing documents may become stale as a result of this initiative?
- What is the impact of stale guidance on developers, operators, or consumers?
- What is the mitigation plan for stale guidance?

## File-Type Rules

### Python Source Modules
- Every `.py` file in `agent_runner_v2/` MUST have a corresponding module doc
- Module docs follow the codebase module template
- Module docs MUST be updated when the module's public API changes
- Internal refactors that don't change public API require doc review but not necessarily doc update

### JSON Configuration Files
- Configuration files are referenced from module docs
- Schema changes require updating the referencing module doc
- `meta.json` sidecars are documented by the delivery SOP, not the codebase SOP

### Prompt Templates
- Prompt templates are inventoried but not individually documented
- Changes to prompt templates require inventory update
- Prompt templates are protected artifacts — changes require scaffold re-run

### Batch and PowerShell Scripts
- Scripts are referenced from `README.md` or `scripts/README.md`
- New scripts require README update
- Script removal requires README update and inventory reconciliation

### Architecture-Site Outputs
- Generated by the Pandoc + Mermaid pipeline
- Validated via `publish_architecture_site` action
- Not manually edited — regenerated from source
