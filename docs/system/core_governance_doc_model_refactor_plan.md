# Core Governance Doc Model Refactor Plan

## Purpose

This document defines a replacement target for the Layer 1 core governance
docs generated by `00_core_governance_bootstrap_v1`.

The current generated set is structurally consistent, but it does not yet
behave like the durable governance authority for the `agent-runner`
ecosystem. The main weakness is that one of the four permanent governance
docs is currently a migration document:

- `BUNDLE_MIGRATION_PLAN.md`

That file is transitional by nature. It is useful during refactor, but it is
not a stable long-term governance artifact.

## Problem Statement

The current four-doc set answers these questions:

- `README.md`: what the documentation model is
- `DOCUMENTATION_STANDARD.md`: what rules the docs must follow
- `BUNDLE_TAXONOMY.md`: what bundle ownership boundaries exist
- `BUNDLE_MIGRATION_PLAN.md`: how to move from old state to new state

The first three are durable governance concerns.

The fourth is not.

Once migration is complete, `BUNDLE_MIGRATION_PLAN.md` becomes one of:

- stale historical context
- a document that must be artificially kept alive
- a pseudo-governance file that does not define steady-state operations

For a true Layer 1 governance set, every document should answer a permanent
ecosystem control question.

## Core Decision

`BUNDLE_MIGRATION_PLAN.md` should not remain part of the permanent Layer 1
governance set.

It should be replaced by a durable runtime governance document.

Recommended replacement:

- `RUNTIME_GOVERNANCE.md`

This replacement should define how the ecosystem operates in steady state,
not how it migrates from a previous state.

## Target Layer 1 Doc Set

The proposed permanent Layer 1 governance set is:

1. `README.md`
2. `DOCUMENTATION_STANDARD.md`
3. `BUNDLE_TAXONOMY.md`
4. `RUNTIME_GOVERNANCE.md`

These four docs together should define:

- documentation authority
- documentation structure rules
- bundle classes and ownership boundaries
- runtime packaging, install, registry, resolution, and validation rules

Layer 1 must also define the universal contract for plugin workflow bundles.

That means the Layer 1 governance model must explicitly support both:

- a single-workflow bundle
- a multi-workflow bundle

## Role Of Each Document

### `README.md`

Primary purpose:

- canonical overview of the ecosystem documentation model

Owns:

- the Layer 1 / Layer 2 / Layer 3 model
- authority boundaries
- high-level audience framing
- canonical map of the governance doc set

Does not own:

- detailed validation rules
- bundle packaging rules
- runtime resolution details

### `DOCUMENTATION_STANDARD.md`

Primary purpose:

- canonical documentation contract for Layer 1 docs

Owns:

- required frontmatter
- required sections
- wording constraints
- downstream reference rules
- update triggers
- validation rules for governance docs

Does not own:

- bundle taxonomy classification
- workflow packaging behavior
- runtime registry behavior

### `BUNDLE_TAXONOMY.md`

Primary purpose:

- canonical ownership and bundle-class model

Owns:

- bundle class definitions
- ownership boundaries
- packaging scope boundaries
- artifact authority boundaries
- the distinction between core governance bundles and plugin workflow bundles
- the fact that a plugin bundle may contain one or many workflows

Does not own:

- per-connection model resolution
- coder invocation behavior
- daemon/manual execution flow details

### `RUNTIME_GOVERNANCE.md`

Primary purpose:

- canonical runtime operating model for workflow bundles in the ecosystem

Owns:

- global vs repo-local vs job-local scope boundaries
- publish/install/runtime behavior expectations
- `_registry` governance and resolution model
- plugin bundle control-plane expectations
- multi-workflow bundle sequencing and handoff contract shape
- role policy / coder role / connection registry responsibilities
- artifact ownership enforcement at runtime
- validation gates before publish, install, submit, and execute
- manual-mode and daemon-mode shared execution expectations

Does not own:

- repo-derived analysis outputs
- step-specific workflow business logic
- provider authentication flows

## Why `RUNTIME_GOVERNANCE.md` Is Better

`RUNTIME_GOVERNANCE.md` is durable because it answers real steady-state
questions that the ecosystem must always govern.

Those questions include:

- what lives in repo root vs global runner home vs job folder
- what gets published with a bundle
- what gets installed into the global home
- how a plugin bundle is structured when it contains multiple workflows
- how `_registry` participates in runtime resolution
- how semantic roles are resolved to coder/connection/model selection
- what constraints apply before a workflow step may run
- what daemon mode must share with manual mode
- what artifact ownership checks are authoritative

These questions remain valid after migration is complete.

## Proposed `RUNTIME_GOVERNANCE.md` Outline

Required sections:

1. `Purpose`
2. `Runtime Scope Model`
3. `Bundle Publish And Install Model`
4. `Registry Control Plane`
5. `Plugin Bundle Control Model`
6. `Role And Connection Resolution`
7. `Artifact Ownership Enforcement`
8. `Execution Mode Parity`
9. `Validation Gates`
10. `Change Control`

Expected section intent:

- `Purpose`
  defines why the runtime governance document exists
- `Runtime Scope Model`
  defines global home, repo-local, bundle-local, and job-local boundaries
- `Bundle Publish And Install Model`
  defines what travels with a bundle and what must not
- `Registry Control Plane`
  defines the responsibility of `_registry` files
- `Plugin Bundle Control Model`
  defines how a bundle may contain one or many workflows and what bundle-level
  control files and sequencing rules are required generically
- `Role And Connection Resolution`
  defines how `role_policy -> role -> coder/connection/model_id` is resolved
- `Artifact Ownership Enforcement`
  defines runtime scope checks and ownership rejection rules
- `Execution Mode Parity`
  defines that manual and daemon must share the same workflow execution logic
- `Validation Gates`
  defines publish/install/run-time validation checkpoints
- `Change Control`
  defines who may update runtime governance and when

## Scope Rules For The New Fourth Doc

`RUNTIME_GOVERNANCE.md` should explicitly define these boundaries:

- `_registry` is part of the workflow runtime control plane
- a plugin workflow bundle is a first-class runtime object
- a plugin bundle may contain one or many workflows
- bundle-level SOP and guardrails belong to Layer 2 bundle-local governance
- Layer 1 defines the required generic contract for those bundle-local control
  files
- workflow packages may ship bundle-local runtime metadata
- global install state is distinct from repo-local source state
- job execution state is distinct from bundle registry state
- artifact ownership checks are authoritative at runtime
- daemon mode must not invent a second workflow execution engine
- backend persists state and routing outcomes but does not own workflow logic
- coder adapters translate resolved runtime config into coder-specific CLI
  invocation rules

It should explicitly avoid:

- repo-derived artifact inventories
- historical migration narration
- temporary transition-phase details
- provider credential handling
- repository-specific analysis outputs
- hardcoding a specific plugin bundle workflow inventory

## Layer 1 Plugin Bundle Contract

Layer 1 should define the universal contract for plugin workflow bundles
without embedding repo-specific lifecycle inventories.

At minimum, Layer 1 should establish that:

- a plugin workflow bundle may contain one or many workflows
- a bundle may define workflow sequence, branching, and handoff rules
- a bundle may carry bundle-local SOP, artifact ownership, and operating
  guardrails
- bundle-local governance is authoritative inside the bundle's scope
- workflow prompts and runtime behavior must stay inside bundle-declared
  boundaries

Layer 1 should define these concepts generically, while each concrete bundle
defines its own exact lifecycle in Layer 2.

## Layer 2 Relationship

Layer 2 bundle-local governance should carry the concrete operating details
for a specific bundle.

Examples of Layer 2 bundle-local docs may include:

- `BUNDLE_OVERVIEW.md`
- `WORKFLOW_SEQUENCE.md`
- `WORKFLOW_SOP.md`
- `ARTIFACT_OWNERSHIP.md`
- `OPERATING_GUARDRAILS.md`

These are not Layer 1 ecosystem docs. They are bundle-local governance docs
that conform to the Layer 1 contract.

## Required Workflow Changes

`00_core_governance_bootstrap_v1` should be refactored so that:

1. the generated four-doc set changes from:
   - `README.md`
   - `DOCUMENTATION_STANDARD.md`
   - `BUNDLE_TAXONOMY.md`
   - `BUNDLE_MIGRATION_PLAN.md`

2. to:
   - `README.md`
   - `DOCUMENTATION_STANDARD.md`
   - `BUNDLE_TAXONOMY.md`
   - `RUNTIME_GOVERNANCE.md`

3. prompt constraints are rewritten around steady-state governance instead of
   migration wording

4. validation checks are updated to require runtime governance sections and
   ban migration-centric framing in the permanent Layer 1 doc set

## Prompt Refactor Implications

The workflow prompt for `generate_core_governance_docs` should be updated so
that it instructs the model to:

- define the ecosystem control plane, not the migration journey
- explain `_registry` governance generically
- explain plugin workflow bundles generically, including multi-workflow bundles
- explain bundle publish/install/runtime boundaries
- explain manual/daemon shared execution expectations
- explain artifact ownership and validation gates
- avoid long transitional narratives

The prompt should stop treating "migration from legacy mixed docs" as a core
output purpose.

## Transitional Handling

If historical migration notes still matter, they should move out of the
permanent Layer 1 set.

Better options:

- a system plan doc under `docs/system/`
- a one-time migration note owned by the refactor effort
- a backend/runtime refactor appendix

They should not occupy one of the four canonical ecosystem governance slots.

## Acceptance Criteria

This refactor is complete when:

1. the Layer 1 governance set contains only durable steady-state docs
2. `BUNDLE_MIGRATION_PLAN.md` is no longer part of the permanent governance
   contract
3. `RUNTIME_GOVERNANCE.md` clearly defines runtime control plane and scope
   boundaries
4. `BUNDLE_TAXONOMY.md` and `RUNTIME_GOVERNANCE.md` both recognize plugin
   workflow bundles and multi-workflow bundles generically
5. the prompt for `00_core_governance_bootstrap_v1` is updated accordingly
6. deterministic validation checks the new fourth doc instead of the migration
   plan
7. the resulting docs read as ecosystem operating governance, not transition
   notes

## Recommended Next Steps

1. Approve the permanent four-doc model
2. Replace the migration-plan contract in the workflow prompt
3. Define the exact required sections for `RUNTIME_GOVERNANCE.md`
4. Update workflow validation rules and review criteria
5. Regenerate the core governance docs and review them again as Layer 1
   ecosystem authority
