# Metadata Standard

## Overview

This document defines the cross-ecosystem metadata standard for governed
documents. The purpose of metadata is to make document ownership,
classification, and scan behavior machine-readable without forcing every
layer to share the same content model.

Metadata serves three primary purposes:

- To distinguish human-authored reference material from generated outputs.
- To distinguish governance documents from operational artifacts.
- To allow scanners, validators, and workflows to include or exclude
  documents deterministically.

## Required Metadata Fields

Every governed document that participates in workflow scanning,
classification, review, or publication must support the following
baseline metadata fields.

### Baseline Required Fields

| Field | Required | Description |
|-------|----------|-------------|
| `doc_type` | Yes | Functional class of the document. |
| `authority` | Yes | Who owns the truth of the document. |
| `scan_policy` | Yes | Default scanner treatment. |
| `scan_reason` | Yes | Why the scan policy was chosen. |

### Layer 1 Extended Fields

For Layer 1 permanent governance documents, the following additional
fields are required:

| Field | Required | Description |
|-------|----------|-------------|
| `template_id` | Yes | The template identifier for the document (e.g., `SYS-00-IDX`). |
| `version` | Yes | Document version string. |
| `layer` | Yes | The owning layer (`layer1`, `layer2`, or `layer3`). |
| `lifecycle_status` | Yes | Current lifecycle state (see `GOVERNANCE_LIFECYCLE.md`). |
| `effective_version` | Yes | The run or change identifier that produced this version. |
| `managed_by` | Yes | Declares whether the document is `workflow-generated` or `human-authored` for governance tracking. |

Layer 2 and Layer 3 may add additional fields for platform-specific or
bundle-specific needs, but must preserve the Layer 1 baseline fields.

### Field Semantics

- `doc_type` answers: what is this document?
- `authority` answers: who owns the truth of this document?
- `scan_policy` answers: should scanners consider it by default?
- `scan_reason` answers: why was this scan policy chosen?

## Allowed Scan Policy Values

### Scan Policy Vocabulary

| Value | Meaning |
|-------|---------|
| `include` | Include in normal operational scans. |
| `exclude` | Exclude from normal operational scans unless explicitly targeted. |
| `conditional` | Include only when a scanner is running under rules that explicitly request this class. |

### Scan Policy Rule

Document scanners must honor explicit scan metadata when present:

- Documents marked `scan_policy: "exclude"` are excluded from normal
  operational scans.
- Excluded documents may still be read deliberately by a workflow or a
  human when they are the intended source.
- Absence of scan metadata does not automatically make a document
  authoritative.

This gives the ecosystem a deterministic control point similar in intent
to search-engine exclusion, but implemented as repo-local governance
metadata rather than a web crawler protocol.

### Scan Policy by Document Class

| Document Class | Recommended `scan_policy` |
|---------------|--------------------------|
| Master plans and blueprints | `exclude` |
| Permanent governance standards | `include` |
| Platform operating standards | `include` |
| Bundle definitions | `include` |
| Workflow outputs | `include` or `conditional` |
| Review artifacts | `conditional` or `exclude` |
| Validation artifacts | `conditional` or `exclude` |
| Audit artifacts | `conditional` or `exclude` |

### `scan_reason` Requirement

When `scan_policy` is `exclude` or `conditional`, the `scan_reason` field
must be non-empty and must explain the exclusion or condition. This
ensures exclusions remain auditable and intentional.

Examples of valid `scan_reason` values:

- `"reference blueprint; exclude from operational document scans"`
- `"run-scoped evidence artifact; not part of permanent governance set"`
- `"design specification; exclude from operational scans"`

## Scanner Compliance Rules

### Mandatory Scanner Behavior

Any scanner, validator, or workflow component that performs document
discovery must obey the following rules:

1. **Honor explicit metadata**: If a recognized `scan_policy` is present,
   honor it.
2. **Respect exclusion**: If `scan_policy` is `exclude`, skip the document
   unless the caller explicitly requested it.
3. **Require inclusion rule**: If `scan_policy` is `conditional`, require
   an explicit inclusion rule before including the document in results.
4. **Report non-compliance**: If metadata is malformed, treat the document
   as non-compliant and report it.
5. **No assumed authority**: If metadata is absent, the scanner may apply
   fallback behavior, but the document must not be assumed authoritative
   solely because it was found.

### Scanner Implementation Note

Layer 1 defines the metadata contract and scanner compliance rules.
The actual parser, discovery logic, and fallback behavior belong in
Layer 2 platform design and code. This separation ensures the metadata
standard remains stable while allowing platform-specific scanner
implementations.

### Validation Rules

Document validators must enforce at least the following:

1. Required metadata fields are present where the standard applies.
2. Values belong to the allowed vocabulary or an allowed extension set.
3. `scan_reason` is non-empty when `scan_policy` is `exclude` or
   `conditional`.
4. Generated documents do not claim `human-authored` authority.
5. Derived documents do not present themselves as the root authority
   (must not use `authority` values reserved for canonical sources).

### Review Rules for Metadata

Review steps must treat metadata misuse as a governance defect.
Examples of metadata defects:

- A master plan without `scan_policy: "exclude"`.
- A generated artifact claiming `human-authored`.
- A review artifact marked as a system authority document.
- A platform-specific standard labeled with `layer: "layer1"`.
- A document with `scan_policy: "exclude"` but an empty `scan_reason`.

### Inheritance Rules

Metadata conventions inherit downward across layers:

- Layer 1 defines the common field names and baseline vocabulary.
- Layer 2 may extend value sets for platform-specific needs.
- Layer 3 may apply platform-specific values defined by its parent Layer 2.
- No lower layer may redefine the meaning of Layer 1 baseline values.

This preserves interoperability while allowing platform-specific detail
where needed.
