# Metadata Standard

## Overview

This document defines the required metadata fields, baseline vocabularies,
scan policy rules, and scanner compliance expectations for governed
documents across all layers.

The purpose of this metadata standard is to:

- distinguish human-authored reference material from generated outputs
- distinguish governance documents from operational artifacts
- allow scanners, validators, and workflows to include or exclude
  documents deterministically
- make document ownership and scan behavior machine-readable without
  forcing every layer to share the same content model

## Required Metadata Fields

Every governed document that participates in workflow scanning,
classification, review, or publication must support the following
metadata fields.

| Field | Required | Description |
|---|---|---|
| `doc_type` | Yes | Functional class of the document. |
| `authority` | Yes | Who owns the truth of the document. |
| `scan_policy` | Yes | Default scanner treatment. |
| `scan_reason` | Yes | Why the scan policy was chosen. |
| `layer` | Conditional | The owning layer (`layer1`, `layer2`, `layer3`). Required for permanent governance and platform documents. |
| `lifecycle_status` | Conditional | The current lifecycle state. Required for permanent governance and platform documents. |
| `effective_version` | Conditional | The version or run identifier for the active document. Required for published permanent documents. |
| `managed_by` | Conditional | Indicates the document is workflow-generated and protected. Required for workflow-generated documents. |

### Field Semantics

- `doc_type` answers what this document is
- `authority` answers who owns the truth of this document
- `scan_policy` answers whether scanners should consider it by default
- `scan_reason` explains the intended use so exclusions remain auditable
- `layer` declares which architectural layer owns the document
- `lifecycle_status` declares the current lifecycle state
- `effective_version` identifies the specific version or run that
  produced the document
- `managed_by` marks the document as workflow-generated and protected
  from manual edits

## Allowed Scan Policy Values

| Value | Meaning |
|---|---|
| `include` | Include in normal operational scans. |
| `exclude` | Exclude from normal operational scans unless explicitly targeted. |
| `conditional` | Include only when a scanner is running under rules that explicitly request this class. |

This vocabulary avoids ambiguous interpretations such as using blank
metadata to mean either include or exclude.

### Scan Policy Rule

Document scanners must honor explicit scan metadata when present:

- documents marked with `scan_policy: "exclude"` are excluded from normal
  operational scans
- excluded documents may still be read deliberately by a workflow or a
  human when they are the intended source
- absence of scan metadata does not automatically make a document
  authoritative

### Layer-Specific Expectations

Expected defaults by layer:

| Layer | Typical `doc_type` | Typical `authority` | Typical `scan_policy` |
|---|---|---|---|
| Layer 1 | `system` or `masterplan` | `human-authored` or `workflow-generated` | `include` or `exclude` |
| Layer 2 | `platform_standard` or `system` | `platform-owned` or `workflow-generated` | `include` |
| Layer 3 | `bundle_definition`, `workflow_output`, `review_artifact`, `validation_artifact`, or `audit_artifact` | `bundle-owned`, `workflow-generated`, or `derived` | `include` or `conditional` |

These are expectations, not hardcoded restrictions. Deviations should be
intentional and reviewable.

## Scanner Compliance Rules

Any scanner, validator, or workflow component that performs document
discovery must obey these rules:

1. **Honor explicit metadata:** If a recognized `scan_policy` is present,
   honor it.
2. **Respect exclusions:** If `scan_policy` is `exclude`, skip the
   document unless the caller explicitly requested it.
3. **Require explicit inclusion for conditional:** If `scan_policy` is
   `conditional`, require an explicit inclusion rule before scanning.
4. **Report malformed metadata:** If metadata is malformed, treat the
   document as non-compliant and report it.
5. **Do not assume authority from discovery:** If metadata is absent, the
   scanner may apply fallback behavior, but the document must not be
   assumed authoritative solely because it was found.

### Validation Expectations

Validation should enforce at least the following:

- required metadata fields are present where the standard applies
- values belong to the allowed vocabulary or an allowed extension set
- `scan_reason` is non-empty when `scan_policy` is `exclude` or
  `conditional`
- generated documents do not claim `human-authored` authority
- derived documents do not present themselves as the root authority

### Review Expectations

Review steps should treat metadata misuse as a governance defect.
Examples of metadata misuse include:

- a master plan without `scan_policy: "exclude"`
- a generated artifact claiming `human-authored`
- a review artifact marked as a system authority document
- a platform-specific standard presenting itself as Layer 1 governance

## Inheritance Rules

The metadata convention inherits downward across layers:

- Layer 1 defines the common field names and baseline vocabulary
- Layer 2 may extend value sets for platform-specific needs
- Layer 3 may apply platform-specific values defined by its parent Layer 2
- no lower layer may redefine the meaning of Layer 1 baseline values

This preserves interoperability while allowing platform-specific detail
where needed.

## Implementation Note

Layer 1 defines the metadata contract, but it does not define the scanner
implementation. The actual parser, discovery logic, and fallback behavior
belong in Layer 2 platform design and code.
