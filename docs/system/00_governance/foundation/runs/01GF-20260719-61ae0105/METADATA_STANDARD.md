# Metadata Standard

## Purpose

This standard defines the cross-ecosystem metadata rules for governed
documents. It establishes required fields, baseline vocabularies, scan
policy rules, scanner compliance expectations, and validation
expectations.

The purpose of metadata is not presentation. The purpose is:

- to distinguish human-authored reference material from generated outputs
- to distinguish governance documents from operational artifacts
- to allow scanners, validators, and workflows to include or exclude
  documents deterministically

## Required Metadata Fields

Every governed document that participates in workflow scanning,
classification, review, or publication must support these fields:

| Field | Required | Description |
|---|---|---|
| `doc_type` | Yes | Functional class of the document. |
| `authority` | Yes | Who owns the truth of the document. |
| `scan_policy` | Yes | Default scanner treatment. |
| `scan_reason` | Yes | Why the scan policy was chosen. |

Additional fields may be added by Layer 2 or Layer 3, but these Layer 1
fields form the common minimum contract.

Permanent governed documents should also carry:

| Field | Required | Description |
|---|---|---|
| `template_id` | Yes (permanent only) | The artifact key identifying this document in the workflow artifact registry. |
| `version` | Yes (permanent only) | Semantic version of the document content. |
| `layer` | Yes (permanent only) | The owning layer. |
| `lifecycle_status` | Yes (permanent only) | Current lifecycle state per `GOVERNANCE_LIFECYCLE.md`. |
| `effective_version` | Yes (permanent only) | The run or change identifier that produced this version. |
| `managed_by` | Recommended | Declares the managing workflow or bundle. |

Layer 2 may extend this vocabulary for platform needs, but it must not
change the meaning of Layer 1 values.

### `authority` Values

| Value | Meaning |
|---|---|
| `human-authored` | Canonical content is maintained directly by humans. |
| `workflow-generated` | Canonical content is produced and maintained by a workflow. |
| `bundle-owned` | Canonical content is owned by a specific Layer 3 bundle. |
| `platform-owned` | Canonical content is owned by a specific Layer 2 platform core. |

Layer 2 and Layer 3 may introduce narrower authority values, but they

## Field Semantics

- `doc_type` answers what this document is.
- `authority` answers who owns the truth of this document.
- `scan_policy` answers whether scanners should consider it by default.
- `scan_reason` explains the intended use so exclusions remain auditable.
- `layer` declares which layer owns the document.
- `lifecycle_status` declares the current lifecycle state.
- `effective_version` identifies the run or change that produced this
  state.
- `managed_by` declares the managing workflow or bundle.

## Scan Policy Rule

Document scanners must honor explicit scan metadata when present.

The scan policy rule is:

1. Documents marked with `scan_policy: "exclude"` are excluded from normal
   operational scans.
2. Excluded documents may still be read deliberately by a workflow or a
   human when they are the intended source.
3. Documents marked with `scan_policy: "conditional"` require an explicit
   inclusion rule to be scanned.
4. Documents marked with `scan_policy: "include"` participate in normal
   operational scans.
5. Absence of scan metadata does not automatically make a document
   authoritative.

This gives the ecosystem a deterministic control point similar in intent
to search-engine exclusion, but implemented as repo-local governance
metadata rather than a web crawler protocol.

## Scanner Compliance Rules

Any scanner, validator, or workflow component that performs document
discovery must obey these rules:

1. **Honor scan policy**: If a recognized `scan_policy` is present, honor
   it.
2. **Exclude on `exclude`**: If `scan_policy` is `exclude`, skip the
   document unless the caller explicitly requested it.
3. **Conditional on `conditional`**: If `scan_policy` is `conditional`,
   require an explicit inclusion rule.
4. **Report malformed metadata**: If metadata is malformed, treat the
   document as non-compliant and report it.
5. **No assumption on absence**: If metadata is absent, the scanner may
   apply fallback behavior, but the document must not be assumed
   authoritative solely because it was found.

## Layer-Specific Expectations

Expected defaults by layer:

| Layer | Typical `doc_type` | Typical `authority` | Typical `scan_policy` |
|---|---|---|---|
| Layer 1 | `system` or `masterplan` | `human-authored` or `workflow-generated` | `include` or `exclude` |
| Layer 2 | `platform_standard` or `system` | `platform-owned` or `workflow-generated` | `include` |
| Layer 3 | `bundle_definition`, `workflow_output`, `review_artifact`, `validation_artifact`, or `audit_artifact` | `bundle-owned`, `workflow-generated`, or `derived` | `include` or `conditional` |

These are expectations, not hardcoded restrictions, but deviations should
be intentional and reviewable.

## Inheritance Rules

The metadata convention inherits downward across layers:

1. Layer 1 defines the common field names and baseline vocabulary.
2. Layer 2 may extend value sets for platform-specific needs.
3. Layer 3 may apply platform-specific values defined by its parent
   Layer 2.
4. No lower layer may redefine the meaning of Layer 1 baseline values.

This preserves interoperability while still allowing platform-specific
detail where needed.

## Validation Expectations

Validation must enforce at least:

1. Required metadata fields are present where the standard applies.
2. Values belong to the allowed vocabulary or an allowed extension set.
3. `scan_reason` is non-empty when `scan_policy` is `exclude` or
   `conditional`.
4. Generated documents do not claim `human-authored` authority.
5. Derived documents do not present themselves as the root authority.
6. Permanent documents carry `template_id`, `version`, `layer`,
   `lifecycle_status`, and `effective_version`.
7. Evidence artifacts are not classified as permanent system documents.
8. `doc_type` and `authority` values are consistent with the document's
   actual content scope and owning layer.

## Review Expectations

Review should treat metadata misuse as a governance defect:

- a master plan without `scan_policy: "exclude"`
- a generated artifact claiming `human-authored`
- a review artifact marked as a system authority document
- a platform-specific standard pretending to be Layer 1 governance
- a document with `lifecycle_status: "published"` that has not been
  through approval

## Implementation Rule

Layer 1 defines the metadata contract. It does not define the scanner
implementation. The actual parser, discovery logic, and fallback behavior
belong in Layer 2 platform design and code.
