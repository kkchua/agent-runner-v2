# Metadata Standard

## Purpose

This standard defines the cross-ecosystem metadata rules for all governed
documents. The purpose of metadata is not presentation. The purpose is:

- To distinguish human-authored reference material from generated outputs
- To distinguish governance documents from operational artifacts
- To allow scanners, validators, and workflows to include or exclude
  documents deterministically
- To make document ownership and classification machine-readable across
  all three layers

## Required Metadata Fields

Every governed document that participates in workflow scanning,
classification, review, or publication must include YAML frontmatter
with the following fields.

### Baseline Required Fields

| Field | Required | Description |
|---|---|---|
| `doc_type` | Yes | Functional class of the document. |
| `authority` | Yes | Who owns the truth of the document. |
| `scan_policy` | Yes | Default scanner treatment. |
| `scan_reason` | Yes | Why the scan policy was chosen. |

### Layer-Specific Fields

| Field | Required | Applies To | Description |
|---|---|---|---|
| `layer` | Yes (permanent docs) | Layer 1, 2, 3 | The layer the document belongs to. |
| `lifecycle_status` | Yes (permanent docs) | Layer 1, 2, 3 | Current lifecycle state. |
| `effective_version` | Yes (permanent docs) | Layer 1, 2, 3 | The workflow run or version identifier that produced this document. |
| `platform` | Yes (Layer 2 only) | Layer 2 | The platform or domain this document governs. |
| `template_id` | Yes (generated docs) | All layers | The document template identifier. |
| `managed_by` | Yes (generated docs) | All layers | Indicator that this file is workflow-managed. |

### Field Semantics

- `doc_type` answers: what is this document?
- `authority` answers: who owns the truth of this document?
- `scan_policy` answers: should scanners consider it by default?
- `scan_reason` answers: why was the scan policy chosen (so exclusions
  remain auditable)?
- `layer` answers: which layer does this document belong to?
- `lifecycle_status` answers: what is the current lifecycle state?
- `effective_version` answers: which workflow run produced this version?

## Allowed Scan Policy Values

### Scan Policy Rules

The `scan_policy` field controls how scanners, validators, and automated
discovery tools treat a document.

| Policy | Behavior |
|---|---|
| `include` | Document is included in normal operational scans. It is discoverable without explicit targeting. |
| `exclude` | Document is excluded from normal operational scans. It may still be read deliberately by a workflow or human when it is the intended source. |
| `conditional` | Document is included only when a scanner is running under rules that explicitly request this document class. Generic scans skip it. |

### Scan Policy Assignment Guidance

- `scan_policy: "include"`: for permanent governance standards, platform
  constitutions, bundle definitions, and workflow outputs that are part of
  a governed document set
- `scan_policy: "exclude"`: for human-authored reference blueprints
  (`masterplan` documents) that guide design but are not themselves
  operational outputs
- `scan_policy: "conditional"`: for temporary evidence artifacts (review,
  validation, audit) that should only appear when a scanner is explicitly
  looking for evidence

### Scan Reason Requirement

When `scan_policy` is `exclude` or `conditional`, the `scan_reason` field
must be non-empty and must explain the intended use so exclusions remain
auditable.

### Absence of Metadata

Absence of scan metadata does not automatically make a document
authoritative. A document without recognized metadata is neither included
nor excluded by default: it is treated as non-compliant until metadata is
added.

## Scanner Compliance Rules

Any scanner, validator, or workflow component that performs document
discovery must obey these rules:

1. **Honor explicit metadata**: If a recognized `scan_policy` is present,
   honor it.
2. **Exclude on `exclude`**: If `scan_policy` is `exclude`, skip the
   document unless the caller explicitly requested it by path.
3. **Conditional on `conditional`**: If `scan_policy` is `conditional`,
   require an explicit inclusion rule that matches the document class.
4. **Report malformed metadata**: If metadata is malformed (required
   fields missing, unknown values), treat the document as non-compliant
   and report it.
5. **No implicit authority from absence**: If metadata is absent, the
   scanner may apply fallback behavior, but the document must not be
   assumed authoritative solely because it was found.

### Scanner Implementation Note

Layer 1 defines the metadata contract and scanner compliance rules.
The actual scanner implementation (parser, discovery logic, and
fallback behavior) belongs in Layer 2 platform design and code.

## Validation Expectations

### Required Field Validation

Future validators must enforce at minimum:

1. Required metadata fields are present where this standard applies
2. Values belong to the allowed vocabulary or an allowed extension set
3. `scan_reason` is non-empty when `scan_policy` is `exclude` or
   `conditional`
4. Generated documents do not claim `human-authored` authority
5. Derived documents do not present themselves as the root authority

### Classification Consistency Validation

Validators should detect metadata misuse:

- A `masterplan` without `scan_policy: "exclude"` is a defect
- A generated artifact claiming `human-authored` is a defect
- A review artifact marked as a system authority document is a defect
- A platform-specific standard labeled with `layer: "layer1"` is a defect

### Inheritance Rules

Metadata conventions inherit downward across layers:

- Layer 1 defines the common field names and baseline vocabulary
- Layer 2 may extend value sets for platform-specific needs (e.g.,
  additional `doc_type` values, platform-specific frontmatter fields)
- Layer 3 may apply platform-specific values defined by its parent
  Layer 2
- No lower layer may redefine the meaning of Layer 1 baseline values

This preserves interoperability while allowing platform-specific detail
where needed.
