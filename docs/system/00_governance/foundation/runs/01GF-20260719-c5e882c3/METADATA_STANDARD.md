# Metadata Standard

## Purpose

This document defines the cross-ecosystem metadata standard for all
governed documents. It establishes the required metadata fields, baseline
vocabularies, scan policy rules, scanner compliance expectations, and
validation rules.

The purpose of this metadata is not presentation. The purpose is:

- to distinguish human-authored reference material from generated outputs
- to distinguish governance documents from operational artifacts
- to allow scanners, validators, and workflows to include or exclude
  documents deterministically

## Required Metadata Fields

Every governed document that participates in workflow scanning,
classification, review, or publication must support the following
Layer 1 metadata fields.

### Core Fields

| Field | Required | Description |
|---|---|---|
| `doc_type` | Yes | Functional class of the document. |
| `authority` | Yes | Who owns the truth of the document. |
| `scan_policy` | Yes | Default scanner treatment. |
| `scan_reason` | Yes | Why the scan policy was chosen. |

### Extended Fields

| Field | Required | Description |
|---|---|---|
| `template_id` | Yes (permanent docs) | Template identifier for structural compliance checking. |
| `version` | Yes (permanent docs) | Document version identifier. |
| `layer` | Yes (permanent docs) | The owning layer: `layer1`, `layer2`, or `layer3`. |
| `lifecycle_status` | Yes (permanent docs) | Current lifecycle state (see Governance Lifecycle). |
| `effective_version` | Conditional | Run or change identifier for version tracking. Required for workflow-generated permanent documents. |
| `managed_by` | Conditional | Indicator that the document is workflow-managed. Required for workflow-generated documents. |

### Field Semantics

- `doc_type`: What this document is (its functional class).
- `authority`: Who owns the canonical truth of this document.
- `scan_policy`: Whether scanners should consider it by default.
- `scan_reason`: The intended use; ensures exclusions remain auditable.
- `template_id`: Stable identifier for structural validation.
- `version`: The document's own version number.
- `layer`: The layer that owns this document.
- `lifecycle_status`: Where this document sits in the governance
  lifecycle.
- `effective_version`: The workflow run or change identifier that produced
  this version.
- `managed_by`: Declares that the document is workflow-managed and
  protected from manual edits.

## Scan Policy Rules

### Core Rule

Document scanners must honor explicit scan metadata when present.

### Exclusion Rule

Documents marked with `scan_policy: "exclude"` are excluded from normal
operational scans.

Excluded documents may still be read deliberately by a workflow or a
human when they are the intended source. Exclusion prevents accidental
inclusion in bulk operations, not deliberate access.

### Conditional Rule

Documents marked with `scan_policy: "conditional"` require an explicit
inclusion rule from the scanner. They are not included by default.

### Absence Rule

Absence of scan metadata does not automatically make a document
authoritative. Scanners may apply fallback behavior, but the document
must not be assumed authoritative solely because it was found.

## Scanner Compliance Rules

Any scanner, validator, or workflow component that performs document
discovery must obey these rules:

1. **Honor explicit metadata**: If a recognized `scan_policy` is present,
   honor it.
2. **Respect exclusion**: If `scan_policy` is `exclude`, skip the
   document unless the caller explicitly requested it.
3. **Require inclusion rule**: If `scan_policy` is `conditional`,
   require an explicit inclusion rule from the scanner configuration.
4. **Report non-compliance**: If metadata is malformed (missing required
   fields, unrecognized values), treat the document as non-compliant and
   report it. Do not silently skip or include it.
5. **Assume nothing from absence**: If metadata is absent, the scanner
   may apply fallback behavior, but the document must not be assumed
   authoritative solely because it was found.

### Fallback Behavior

When metadata is absent, scanners should apply a reasonable default based
on the document's location and context, but must not:

- treat an unscanned document as authoritative governance
- include unscanned documents in a governed document set without explicit
  classification
- suppress warnings about absent metadata unless configured to do so

## Validation Expectations

### Structural Validation

Validation must enforce at minimum:

1. **Required fields present**: All required metadata fields are present
   where the standard applies.
2. **Valid values**: Field values belong to the allowed vocabulary or an
   allowed extension set defined by a higher layer.
3. **Non-empty `scan_reason`**: `scan_reason` is non-empty when
   `scan_policy` is `exclude` or `conditional`.
4. **No false authority**: Generated documents do not claim
   `human-authored` authority.
5. **No false root**: Derived documents do not present themselves as the
   root authority.
6. **Template ID present**: Permanent documents carry a valid
   `template_id`.
7. **Layer declared**: Permanent documents declare their owning layer.

### Content Validation

Beyond metadata, validation should check:

1. **Layer scope consistency**: The document's declared layer is
   consistent with its actual content scope.
2. **No forbidden content**: Layer 1 documents do not contain runtime
   architecture, install procedures, or platform-specific operational
   detail.
3. **Required sections present**: Documents carrying a `template_id`
   include the required section headings defined for that template.

### Review Validation

Review steps should treat metadata misuse as a governance defect:

- a master plan without `scan_policy: "exclude"`
- a generated artifact claiming `human-authored` authority
- a review artifact marked as a system authority document
- a platform-specific standard pretending to be Layer 1 governance
- a permanent document missing required frontmatter fields

## Inheritance Rules

Metadata conventions inherit downward across layers:

1. Layer 1 defines the common field names and baseline vocabulary.
2. Layer 2 may extend value sets for platform-specific needs but must not
   redefine Layer 1 baseline values.
3. Layer 3 may apply platform-specific values defined by its parent
   Layer 2.
4. No lower layer may redefine the meaning of Layer 1 baseline values.

This preserves interoperability while allowing platform-specific detail
where needed.

## Layer-Specific Defaults

Expected metadata defaults by layer:

| Layer | Typical `doc_type` | Typical `authority` | Typical `scan_policy` |
|---|---|---|---|
| Layer 1 | `system` or `masterplan` | `human-authored` or `workflow-generated` | `include` or `exclude` |
| Layer 2 | `platform_standard` or `system` | `platform-owned` or `workflow-generated` | `include` |
| Layer 3 | `bundle_definition`, `workflow_output`, `review_artifact`, `validation_artifact`, or `audit_artifact` | `bundle-owned`, `workflow-generated`, or `derived` | `include` or `conditional` |

These are expectations, not hardcoded restrictions. Deviations must be
intentional and reviewable.

## Implementation Note

Layer 1 defines the metadata contract. The actual parser, discovery logic,
scanner implementation, and fallback behavior belong in Layer 2 platform
design and code. Layer 1 does not specify how a scanner reads YAML
frontmatter, which library to use, or how to traverse a directory tree.
