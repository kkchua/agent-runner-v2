Objective

Review the initiative document for completeness, clarity, and compliance with governance standards.

Layer Boundary

- This workflow belongs to Layer 3 and operates on top of the Layer 2 platform contract.
- Review only the initiative document, not planning or implementation artifacts.
- Treat Layer 1 governance and Layer 2 platform constitution as read-only authority.

Reference Inputs

- Read {INIT_FILE} (the initiative document to review).
- Read {CRITIQUE_FILE_SUGGESTED} (the technical critique findings).
- Read {DRAFT_INIT_FILE} (original draft for traceability verification).
- Read codebase context from {CODEBASE_DOC_ROOT} to validate scope understanding.
- Read Layer 1 governance at {GOVERNANCE_RUNTIME_ROOT} for metadata compliance.
- Read Layer 2 platform constitution at {PLATFORM_RUNTIME_ROOT} for platform contract compliance.

CRITICAL: Authorized Sections Only

The initiative document is required to contain EXACTLY these sections and no others.
Do NOT reject for missing sections that are NOT in this list.
Do NOT require sections like "Risk Assessment", "Initiative Metadata", "Source Reference",
"Executive Summary", or any other section not explicitly listed below.

  - template_id: "SYS-03-IN"
  - version: "1.0.0"
  - doc_type: "workflow_output"

  - scan_policy: "include"

Required Body Sections (in this order, ALL must be present):
  1. Title
  2. Objective
  3. Problem Statement
  4. Expected Outcomes
  5. Scope (must contain: In Scope, Out of Scope, Boundary Conditions)
  6. Constraints
  7. Dependencies
  8. Success Criteria
  9. Stakeholders
  10. Notes (OPTIONAL - do not reject if missing)

Review Criteria

Evaluate the initiative document against these criteria ONLY:

1. Section Completeness:
   - All 9 required body sections are present (Notes is optional)
   - Scope section contains all three sub-sections
   - Each section has substantive content (not just headers)

2. Frontmatter Compliance:
   - All required frontmatter fields are present
   - For each field, quote the ACTUAL value found in the document before judging compliance
   - template_id is exactly "SYS-03-IN"
   - source_document references the draft filename

3. Artifact Key Accuracy:
   - Input artifact referenced as DRAFT_INIT_FILE
   - Output artifact referenced as INIT_FILE
   - All artifact keys use _FILE suffix
   - Reject if any _DOC suffix is found in artifact key references

4. Traceability:
   - Content preserves the intent of {DRAFT_INIT_FILE}
   - No scope creep or invented requirements not supported by the draft

5. Technical Accuracy:
   - Code snippets, API references, and file paths are verified against the actual codebase
   - Library/SDK usage matches the installed version (check source or docs, not training data)
   - Variable names, function signatures, and control patterns are consistent with existing code

6. Encoding Compliance:
   - ASCII-only content (no em-dashes, curly quotes, Unicode)
   - Plain text section headings (no backticks or formatting in headings)

7. Governance Compliance:
   - No Layer 1 governance redefinition
   - No Layer 2 platform contract redefinition
   - No implementation details or technical solutions
   - No task breakdowns or scheduling

8. Critique Resolution:
   - The document contains a "Critique Resolution" section
   - Each finding from {CRITIQUE_FILE_SUGGESTED} has a corresponding resolution
   - Resolutions are substantive (not just "acknowledged" without action)
   - The resolutions actually address the technical concerns raised in the critique
   - If a finding was not addressed, there is a valid justification for why

Review Output

Generate a review document with:

1. Decision: APPROVED or REJECTED
2. Summary: Brief overview of review findings
3. Findings: Detailed list of issues (if any), categorized as:
   - Critical: Must fix (missing required sections from the list above, frontmatter errors)
   - Major: Should fix (unclear scope, missing success criteria)
   - Minor: Nice to fix (style issues, minor clarifications)
4. Recommendations: Specific actions to address findings

APPROVED when:
- All 9 required sections are present with substantive content
- Frontmatter is compliant
- Artifact keys use _FILE suffix (no _DOC suffix found)
- Encoding is ASCII-only
- No governance violations
- Critique Resolution section is present and addresses all findings from the critique

REJECTED when:
- Any of the 9 required sections is missing or empty
- Frontmatter has errors
- Artifact keys use _DOC suffix instead of _FILE
- Encoding violations found
- Governance violations found
- Critique Resolution section is missing or does not address the critique findings

Output Instructions

- Write the review document to {REVIEW_FILE_SUGGESTED}.
- Use ASCII-only characters.
- Use plain text section headings.
- Provide direct citations to offending text when rejecting.
- Be specific and actionable in feedback.
