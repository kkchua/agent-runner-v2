Objective

Validate the generated operational workflow design for correctness, completeness,
and conformance to the Composition System Standard. This is a quality control
checkpoint before the package assembly step consumes the design.

The gatekeeper asks: "Does this design define a logical workflow that operates
on the three-layer architecture? Are the step sequence, artifact flow, and
routing correct? Can the package assembly step generate a complete workflow
from this design?"

Reference Inputs

- Read {OPERATIONAL_WORKFLOW_FILE} for the design to validate.
- Read {COMPONENT_SCHEMA_FILE} for the component types -- the workflow
  operates on these components.
- Read {COMPOSITION_FORMAT_FILE} for the composition format -- the workflow
  resolves these compositions.
- Read {OUTPUT_FORMAT_FILE} for the output format -- the workflow generates
  outputs in this format.
- Read {TEST_CRITERIA_FILE} for acceptance criteria -- sections 8 and 9
  define what makes a good operational workflow and what the gatekeeper must
  check.
- Read {COMPOSITION_SYSTEM_STANDARD} Section 6 (Universal Workflow Pattern)
  for the standard workflow pattern.
- Read {WORKFLOW_SPEC_FILE} for the original specification -- verify the
  design aligns with the spec's workflow requirements.

Validation Questions

Answer each question with specific evidence from the documents:

1. Phase Completeness: Does the design define all workflow phases (scan, plan,
   generate, review, refine)? Are there missing phases?

2. Step Sequence: Is the step sequence logical and complete? Does it implement
   all workflow phases? Are there steps that don't belong?

3. Step Type Classification: Are step types (prompt vs action) appropriate?
   Are deterministic operations (file scanning, validation, data processing)
   classified as actions? Are LLM-judgment tasks (generation, review) classified
   as prompts?

4. Artifact Flow: Does each step read artifacts produced by prior steps? Are
   there dangling references (reading artifacts no prior step produced)? Can
   trace complete chain from inputs to outputs?

5. Action Specifications: For each action-driven step, is the action
   specification complete (name, purpose, inputs, outputs, logic)? Were
   existing reusable actions checked before proposing new ones?

6. Routing: Is routing correct?
   - onsuccess: Next step in sequence (refine steps use this to return to review)
   - on_reject_refine: Review → refine → back to review loop
   - max_iterations: Limit refine loops
   - exhausted_failure_code: Terminal failure when loops exhaust

7. Review/Refine Loop Design: Are review/refine loops properly designed?
   What triggers refinement? How many iterations allowed? What happens when
   loops exhaust?

8. Standard Conformance: Does the design follow the Composition System
   Standard's workflow pattern (scan → plan → generate → review → refine)?
   Are there deviations?

9. Package File Inventory: Does the design explicitly enumerate every file the
   package must contain? For each file, is the name, relative path, and
   purpose specified? Cross-check against the test criteria -- are there
   files the spec requires (e.g., supplementary data files, runtime
   configuration) that the inventory misses? A file mentioned as a runtime
   dependency in the step sequence but NOT listed in the inventory WILL NOT
   be generated by the package assembly step -- REJECT if any such files are
   found.

Self-Critic (Before Final Verdict)

Challenge your review before committing to a verdict:

1. Am I rubber-stamping, or did I actually verify each step against the
   standard and spec?
2. Did I find at least one substantive finding, or am I just saying
   "looks good"?
3. If I missed an issue that the package assembly step catches, what would
   it be?
4. Is my verdict based on evidence from the design, or on assumptions
   about what the generator "probably" did?
5. Did the Package File Inventory list every file the generate_package step
   needs to create, including supplementary data files (audiences/,
   templates/, config/)? Are there runtime dependencies in the step sequence
   that aren't listed as files to create?

If your review is superficial, go back and dig deeper before reporting.

Decision Rules

- APPROVED: The operational workflow design is complete, correct, and conforms
  to the Composition System Standard. All validation questions have satisfactory
  answers. Step sequence is logical, artifact flow is traceable, routing is
  correct.

- REJECTED: The operational workflow design has gaps (missing phases, incorrect
  routing, dangling artifact references), does not conform to the standard, or
  will cause package assembly failures. Include specific findings for each
  failed validation question.

Output Instructions

- Write the gatekeeper report to {GATEKEEP_OPERATIONAL_WORKFLOW_FILE}.
- Include YAML frontmatter with doc_type: "gatekeep_report".
- Structure:
  1. Summary: Overall assessment (1-2 sentences)
  2. Validation Results: Table with columns: Question, Status (PASS/FAIL),
     Evidence
  3. Issues (if any): Numbered list of specific gaps found
  4. Recommendations: Specific suggestions to fix issues
  5. Verdict: APPROVED or REJECTED on its own line
- All content must be ASCII-only.
- The result field in meta.json must match the verdict exactly.

Forbidden Content

- Non-ASCII characters
- Vague findings without specific evidence
- Approving designs with known gaps
