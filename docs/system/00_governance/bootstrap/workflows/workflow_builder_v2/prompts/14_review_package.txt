Objective

Comprehensive quality review of the generated composition system workflow
package. Check component schema quality, composition format clarity, output
format completeness, operational workflow correctness, and -- most importantly
-- fulfillment of the spec objective.

Reference Inputs

- Read {TEST_CRITERIA_FILE} for the acceptance criteria -- verify the generated
  package fulfills ALL criteria in the "Criteria for review_package step"
  section. This is the primary verification contract.
- Read {WORKFLOW_SPEC_FILE} for the original specification -- verify the
  generated workflow actually implements what the spec describes.
- Read {WORKFLOW_MANIFEST_FILE} for the generated workflow.toml.
- Read {WORKFLOW_EXTENSIONS_FILE} for the generated context_extensions.py.
- Read {WORKFLOW_ACTIONS_FILE} for the generated actions.py (if action steps
  were declared).
- Read {WORKFLOW_PROMPTS_INDEX_FILE} for the list of generated prompt files.
- Read {WORKFLOW_README_FILE} for the generated README.md.
- Read {WORKFLOW_ENV_SAMPLE_FILE} for the generated .env.sample (if it exists).
- Read {WORKFLOW_CONFIG_SAMPLE_FILE} for the generated config.json.sample (if
  it exists).
- Read {COMPONENT_SCHEMA_FILE} for the component schema design.
- Read {COMPOSITION_FORMAT_FILE} for the composition format design.
- Read {OUTPUT_FORMAT_FILE} for the output format design.
- Read {OPERATIONAL_WORKFLOW_FILE} for the operational workflow design.
- Read {GATEKEEP_COMPONENT_SCHEMA_FILE}, {GATEKEEP_COMPOSITION_FORMAT_FILE},
  {GATEKEEP_OUTPUT_FORMAT_FILE}, {GATEKEEP_OPERATIONAL_WORKFLOW_FILE},
  {GATEKEEP_PACKAGE_FILE} to verify gatekeepers ran and their verdicts.

Review Checklist

1. workflow.toml checks:
   - stepCompletion terminal step is present as the last [[step]]
   - init_step matches the first step name
   - Every onsuccess target references a valid step name or stepCompletion
   - Every prompt step has [step.coder] with a valid role_policy
   - Every prompt step has [step.artifacts] with produces and result_meta_key
   - Review steps have [step.on_reject_refine] with proper configuration
   - Refine steps have onsuccess pointing to the review step
   - Step names are lowercase_with_underscores and unique
   - Step sequence matches {OPERATIONAL_WORKFLOW_FILE} exactly

2. context_extensions.py checks:
   - WorkflowExtensions class is present and inherits correctly
   - workflow_name matches the workflow directory name
   - register_artifact_keys() returns relative paths with {job_id}, {seq}
   - build_context_extensions() returns absolute paths
   - install_to_global() and sync_to_backend() methods are present
   - All artifact keys from workflow.toml produces AND required_inputs appear
     in register_artifact_keys()
   - Module, class, and methods have docstrings

3. Prompt file checks:
   - Every prompt file listed in the index exists
   - Placeholders use bare {KEY} format, never backtick-wrapped
   - All content is ASCII-only
   - Each prompt has Objective, Reference Inputs, Output Instructions
   - Artifact key references match keys in the artifact contract
   - Prompts explicitly instruct the LLM to write files (not put data in
     result field)

4. Action implementation checks (if actions.py exists):
   - All declared actions are implemented with @action decorator
   - Actions return ActionResult (APPROVED/REJECTED)
   - Actions have error handling and input validation
   - Actions use type hints and docstrings
   - Existing reusable actions were referenced, not duplicated

5. Supplementary file checks:
   - README.md exists with Overview, Prerequisites, Usage, Step Reference,
     Artifact Keys sections
   - README.md step reference matches workflow.toml steps
   - .env.sample exists only if needed; each variable has comment and placeholder
   - config.json.sample exists only if needed; valid JSON with defaults

6. Cross-file consistency:
   - Artifact keys consistent between workflow.toml and context_extensions.py
   - Step names match prompt file naming convention
   - Routing targets reference existing step names
   - README.md matches actual package contents

7. Spec fulfillment verification:
   - Does the generated workflow actually implement the spec objective?
   - For each phase in the spec: does the corresponding generated step do
     what the spec describes?
   - For action-driven steps: does actions.py contain actual implementation
     logic, not stubs?
   - For prompt-driven steps: do the prompts instruct the LLM to produce
     what the spec requires?
   - Does the data flow between steps match the spec's pipeline?
   - Are there any hallucinated elements not in the spec?
   - Verify ALL criteria in {TEST_CRITERIA_FILE} pass

8. Gatekeeper effectiveness:
   - Did all gatekeepers run and approve?
   - If any gatekeeper REJECTED, were issues fixed before reaching this review?
   - If gatekeepers missed issues that this review catches, note this as a
     process failure

9. Composition system quality:
   - Component schema: Are components truly reusable? Well-defined?
   - Composition format: Are compositions clear? Resolvable?
   - Output format: Are outputs self-contained? Complete?
   - Three-layer integrity: Do the layers work together correctly?

Output Instructions

- Write the review document to {REVIEW_FILE_SUGGESTED}.
- Output must be ASCII-only.
- Include YAML frontmatter with at minimum:
  - doc_type: "workflow_review"
  - lifecycle_status: "draft"
  - effective_version: "{job_id}"
- Include these sections:
  1. Summary: one-paragraph overall assessment
  2. workflow.toml Findings: pass/fail for each check with evidence
  3. context_extensions.py Findings: pass/fail for each check with evidence
  4. Prompt File Findings: pass/fail for each check with evidence
  5. Action Implementation Findings: pass/fail for each check with evidence
  6. Supplementary File Findings: pass/fail for each check with evidence
  7. Cross-File Consistency: pass/fail for each check with evidence
  8. Spec Fulfillment: pass/fail for each test criteria item with evidence
  9. Gatekeeper Effectiveness: pass/fail for each gatekeeper check
  10. Composition System Quality: assessment of three-layer integrity
  11. Issues: numbered list of specific issues to fix (if any)
  12. Verdict: APPROVED or REJECTED on its own line at the end
- If REJECTED, each issue must include the file, location, and specific fix
  required.

Self-Critic (Before Final Verdict)

Challenge your review before committing to a verdict:

1. Am I rubber-stamping, or did I actually read each generated file and
   verify it against the spec and test criteria?
2. Did I find at least one substantive finding, or am I just saying
   "looks good"?
3. If I missed an issue that the operator discovers later, what would it be?
4. Is my verdict based on evidence from the files, or on assumptions
   about what the generator "probably" produced?

If your review is superficial, go back and dig deeper before reporting.

Decision Rules

- APPROVED: All checks pass or have only minor cosmetic notes that do not
  affect functionality. Spec fulfillment criteria all pass. Composition system
  quality is good.

- REJECTED: Any missing required element, key mismatch, routing error,
  backtick-wrapped placeholders, non-ASCII content, spec fulfillment failure,
  or composition system quality issue.

CRITICAL: The meta.json status field MUST match your review verdict exactly.

Forbidden Content

- Modifying workflow files directly (that is the refine step)
- Vague findings without specific file and location references
- Non-ASCII characters
