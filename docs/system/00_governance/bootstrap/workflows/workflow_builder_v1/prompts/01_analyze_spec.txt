Objective

Analyze the user-provided workflow specification and produce a comprehensive
requirements document. The spec may be declarative (what to achieve) rather than
prescriptive (how to achieve it). Your job is to INFER the implementation:
- Infer workflow type from spec content (not just explicit declaration)
- Infer step sequence from the problem domain
- Infer action vs prompt steps from task nature
- Propose custom actions where deterministic operations are needed

Reference Inputs

- Read {WORKFLOW_SPEC_FILE} for the user-provided specification.
- Read {WORKFLOW_CREATION_GUIDE} for reference on workflow patterns and file types.
- Read {WORKFLOW_BUILDER_SOP} for storage conventions and naming rules.

Analysis Tasks

1. Identify the workflow purpose and scope.

2. Infer the workflow type:
   - prompt-driven: primarily LLM reasoning, synthesis, generation
   - action-only: primarily deterministic file ops, API calls, data processing
   - mixed: combination of both
   Base this on the nature of tasks described, not just explicit declaration.

3. Propose step sequence with types:
   For each step, determine:
   - Step name (lowercase_with_underscores)
   - Step type: 'prompt' (needs LLM judgment) or 'action' (deterministic code)
   - Purpose: what this step achieves
   - Inputs: what artifacts it reads
   - Outputs: what artifacts it produces

4. Identify custom actions (if any):
   For each action step, specify:
   - Action name (lowercase_with_underscores)
   - Purpose: what the action does
   - Inputs: what it reads (context variables, files)
   - Outputs: what it produces
   - Logic: high-level description of the operation

5. Identify all input artifacts (external files the workflow reads).

6. Identify all output artifacts (files the workflow writes).

7. Identify constraints: governance layer, naming rules, dependencies.

8. Flag any open questions or ambiguities needing resolution.

Self-Validation (Before Output)

Before reporting APPROVED, validate:

1. Completeness: Does this requirements document define ALL elements needed
   to achieve the spec objectives? Could a downstream step use this to
   implement the workflow?

2. Inference Soundness: Are the inferred workflow type, step sequence, and
   step types appropriate? Would a reasonable alternative be better?

3. Action Specifications: If action steps are proposed, are they truly
   deterministic operations that can be implemented in Python? Are inputs,
   outputs, and logic clearly specified?

4. Feasibility: Can the artifact definition step consume this and produce
   a complete artifact contract? Are all implied artifacts declared?

5. Constraint Compliance: Does the solution respect all constraints from
   the spec?

If validation fails, report REJECTED with specific gaps found.

Output Instructions

- Write the structured requirements document to {WORKFLOW_REQUIREMENTS}.
- Output must be ASCII-only.
- Include YAML frontmatter with at minimum:
  - doc_type: "workflow_design"
  - lifecycle_status: "draft"
  - effective_version: "{job_id}"
- Include these sections in order:
  1. Overview: one-paragraph summary of purpose.
  2. Workflow Type: inferred type with justification.
  3. Proposed Steps: numbered list of steps with name, type, purpose, inputs, outputs.
  4. Custom Actions: table of action specifications (if any action steps proposed).
     Columns: action_name, purpose, inputs, outputs, logic_description.
  5. Input Artifacts: table of artifact keys, descriptions, required/optional.
  6. Output Artifacts: table of artifact keys, descriptions, required/optional.
  7. Constraints: governance, naming, dependencies.
  8. Open Questions: numbered list (or "None").
- Use UPPER_SNAKE_CASE for all artifact keys.
- Do not define file paths -- handled by define_artifacts step.

Forbidden Content

- File path assignments (handled by define_artifacts step)
- workflow.toml content (handled by generate_package step)
- Implementation code (handled by generate_package step)
- Non-ASCII characters
