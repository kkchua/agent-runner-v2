Objective

Generate ALL files required by the workflow design. Do NOT follow a fixed
numbered list. Instead, read the design documents and INFER what files are
needed based on the steps, artifacts, and workflow type declared.

The fundamental principle: generate EVERY file the design requires.

Reference Inputs

- Read {STEP_ARCHITECTURE_FILE} for the step sequence, types, and routing.
- Read {ARTIFACT_CONTRACT_FILE} for artifact keys and path patterns.
- Read {WORKFLOW_REQUIREMENTS_FILE} for action specifications (if any).
- Read {WORKFLOW_CREATION_GUIDE} for file structure and conventions.

Inference-Based Generation

Instead of "Generate files 1-6", follow this principles-based approach:

1. Identify Step Types from {STEP_ARCHITECTURE_FILE}:
   - For EACH prompt-driven step: generate a prompt file in prompts/
   - For EACH action-driven step: add action implementation to actions.py

2. Generate Core Files (always required):
   - workflow.toml: step definitions, routing, artifact bindings
   - context_extensions.py: WorkflowExtensions class, register_artifact_keys(),
     build_context_extensions()
   - README.md: user guide with step reference and artifact keys

3. Generate Conditional Files (if design requires them):
   - prompts/*.txt: one per prompt-driven step
   - actions.py: if ANY action-driven steps exist, implement ALL actions
   - .env.sample: if environment variables needed
   - config.json.sample: if runtime config needed

4. For actions.py specifically:
   - Read {WORKFLOW_REQUIREMENTS_FILE} Custom Actions section
   - Before implementing each action, check if it maps to an existing
     reusable action (validate_workflow_bundle, promote_workflow_package,
     step_completion). If reused, reference it in workflow.toml with
     action = "existing_name" — do NOT duplicate the implementation.
   - Implement ONLY truly new actions with @action decorator
   - Include proper ActionResult returns (APPROVED/REJECTED)
   - Include error handling and input validation
   - Use type hints and docstrings

5. For workflow.toml:
   - Match step sequence exactly from {STEP_ARCHITECTURE_FILE}
   - Use artifact keys exactly from {ARTIFACT_CONTRACT_FILE}
   - Place onsuccess at [[step]] top level (not under [step.artifacts])
   - Place promotes at [[step]] top level for promote steps

6. For context_extensions.py:
   - Use path patterns from {ARTIFACT_CONTRACT_FILE}
   - register_artifact_keys() must include ALL artifacts — both outputs
     (from produces) AND inputs (from required_inputs in the init step).
     The backend needs input registrations to resolve bare filenames.
   - Resolve to absolute paths in build_context_extensions()
   - Handle {slug}, {seq}, {iter} placeholder resolution

7. For prompts/:
   - Name: prompts/NN_step_name.txt where NN is step order
   - Include Objective, Reference Inputs, Output Instructions sections
   - Use bare {ARTIFACT_KEY} placeholders (never backtick-wrapped)
   - ASCII-only content

8. Meta-workflow gatekeeper auto-placement (when is_meta_workflow is true
   in {WORKFLOW_REQUIREMENTS_FILE}):
   The generated workflow.toml MUST include 4 gatekeeper steps:
   - gatekeep_requirements: validates WORKFLOW_REQUIREMENTS, rejects to
     analyze_spec, produces GATEKEEP_REQUIREMENTS
   - gatekeep_artifacts: validates ARTIFACT_CONTRACT, rejects to
     define_artifacts, produces GATEKEEP_ARTIFACTS
   - gatekeep_steps: validates STEP_ARCHITECTURE, rejects to design_steps,
     produces GATEKEEP_STEPS
   - gatekeep_package: validates generated package, rejects to
     generate_package, produces GATEKEEP_PACKAGE
   Each gatekeeper uses role_policy = "validation_standard" and must have
   exhausted_failure_code and exhausted_failure_class on its on_reject_refine.

Self-Critic (Before Self-Validation)

Challenge your reasoning before checking completeness:

1. Am I generating files or code that the design documents don't actually
   require?
2. Am I introducing assumptions not supported by {STEP_ARCHITECTURE_FILE} or
   {ARTIFACT_CONTRACT_FILE}?
3. If a downstream validator reads this package, what would fail?
4. Did I reuse existing framework actions where possible, or did I
   unnecessarily duplicate them?

If you find reasoning issues, fix them before proceeding to Self-Validation.

Self-Validation (Before Output)

Before reporting APPROVED, validate:

1. File Completeness: Does the package contain ALL files implied by the design?
   - If {STEP_ARCHITECTURE_FILE} declares action steps, does actions.py exist?
   - Does prompts/ contain one file per prompt-driven step?
   - Are core files (workflow.toml, context_extensions.py, README.md) present?

2. Design Fidelity: Do generated files match {STEP_ARCHITECTURE_FILE} and
   {ARTIFACT_CONTRACT_FILE} exactly? Any scope shrink or scope creep?

3. Action Implementation: If actions.py exists, are ALL declared actions
   implemented? Do they have proper @action decorators? Do they return
   ActionResult? Were existing reusable actions referenced instead of
   duplicated?

4. Artifact Reporting: Are ALL generated file paths reported in meta.json
   artifacts dict? Including WORKFLOW_ACTIONS if generated?

5. Meta-Workflow Compliance: If is_meta_workflow is true in
   {WORKFLOW_REQUIREMENTS_FILE}, does workflow.toml include all 4 gatekeeper
   steps (GATEKEEP_REQUIREMENTS, GATEKEEP_ARTIFACTS, GATEKEEP_STEPS,
   GATEKEEP_PACKAGE) with proper on_reject_refine routing?

If validation fails, report REJECTED with specific gaps found.

Output Instructions

- Write files to the run directory (parent of {WORKFLOW_MANIFEST_FILE}).
- Create prompts/ subdirectory for prompt files.
- All files must be ASCII-only.
- Report ALL generated file paths in meta.json using their declared artifact
  keys from {ARTIFACT_CONTRACT_FILE}. Read the artifact contract to determine
  which keys correspond to the files you generated.
- Individual prompt files (prompts/*.txt) are NOT separate artifacts — they are
  covered by WORKFLOW_PROMPTS_INDEX_FILE.
- Always report these standard keys when the corresponding files are generated:
  - WORKFLOW_MANIFEST_FILE: path to workflow.toml
  - WORKFLOW_EXTENSIONS_FILE: path to context_extensions.py
  - WORKFLOW_ACTIONS_FILE: path to actions.py (if generated)
  - WORKFLOW_PROMPTS_INDEX_FILE: path to prompts index document
  - WORKFLOW_README_FILE: path to README.md
  - WORKFLOW_ENV_SAMPLE_FILE: path to .env.sample (if generated)
  - WORKFLOW_CONFIG_SAMPLE_FILE: path to config.json.sample (if generated)
- For meta-workflows: if {WORKFLOW_REQUIREMENTS_FILE} declares is_meta_workflow
  as true, also report any supplementary specification documents that the design
  requires (e.g. BUILDER_SPEC_TEMPLATE_FILE, BUILDER_SOP_FILE,
  BUILDER_STANDARD_FILE). Check {ARTIFACT_CONTRACT_FILE} for the full list of
  declared keys and their path patterns.

Forbidden Content

- Non-ASCII characters
- Backtick-wrapped placeholders like `{ARTIFACT_KEY}`
- Hardcoded absolute paths in register_artifact_keys()
- Missing stepCompletion terminal step
- Omitting WORKFLOW_ACTIONS_FILE from meta.json when actions.py exists
- Inventing artifact keys not in {ARTIFACT_CONTRACT_FILE} (e.g.
  WORKFLOW_PROMPT_01, WORKFLOW_PROMPT_02). Prompt files belong under
  WORKFLOW_PROMPTS_INDEX_FILE, not as individual artifact keys.
