Objective

Critique the execution document and code changes for technical correctness, runtime verification, and test completeness before formal review.

Layer Boundary

- This workflow belongs to Layer 3 and operates on top of the Layer 2 platform contract.
- Critique only the execution document and actual code changes, not validation artifacts.
- Treat Layer 1 governance and Layer 2 platform constitution as read-only reference inputs.

Reference Inputs

- Read `EXEC_FILE` (the execution document to critique).
- Read `IMPL_FILE` (approved implementation plan for traceability verification).
- Read codebase context from `docs/repo/codebase/current/` to validate changes.
- Read Layer 1 governance at `GOVERNANCE_RUNTIME_ROOT` for metadata requirements.
- Read Layer 2 platform constitution at `PLATFORM_RUNTIME_ROOT` for platform contract.

Critique Criteria

Evaluate the execution against these criteria:

1. **Code Implementation Correctness**:
   - Do the actual code changes match what the IMPL specified?
   - Are all changes complete -- nothing missing or partially implemented?
   - Are APIs used correctly? Verify against the installed library version by reading source code or documentation in the virtual environment.
   - Do not rely on training data for library APIs -- they may have changed.

2. **Runtime Verification**:
   - Actually run the code. Execute modified modules and check for runtime errors.
   - Verify imports resolve correctly and no circular dependencies were introduced.
   - Confirm that the code executes without unexpected exceptions or tracebacks.

3. **Test Execution**:
   - Run the test suite. Verify all tests from the sdlc_50 task test scope actually executed.
   - Check that test commands match what the implementation plan specified.
   - Confirm no tests were skipped without justification.

4. **Results Accuracy**:
   - Are test results recorded accurately in the EXEC document (not fabricated)?
   - Do results match expectations from the TASK test scope?
   - Are there unexplained failures or discrepancies between expected and actual results?

5. **Regression Check**:
   - Run the full test suite to check for regressions introduced by the changes.
   - Verify that previously passing tests still pass.
   - Identify any side effects on unrelated modules.

Critique Output

Generate a critique document with YAML frontmatter and the following sections:

YAML Frontmatter:
  template_id: "SYS-03-CR"
  version: "1.0.0"
  doc_type: "review_artifact"
  lifecycle_status: "draft"

Document Sections:
1. **Decision**: APPROVED or REJECTED
2. **Summary**: Brief overview of critique findings
3. **Findings**: Detailed list of issues (if any), categorized as:
   - **Critical**: Must fix (code does not match IMPL, runtime errors, fabricated results)
   - **Major**: Should fix (missing test coverage, unexplained failures, regressions)
   - **Minor**: Nice to fix (style issues, minor clarifications)
4. **Recommendations**: Specific actions to address findings

If APPROVED:
- Code changes match the implementation plan
- Runtime verification succeeded
- All tests executed and results are accurate
- No regressions detected

If REJECTED:
- Provide specific, actionable feedback
- Cite exact files, functions, or test cases that need attention
- Explain what must be fixed before formal review

Output Instructions

- Write the critique document to `CRITIQUE_FILE_SUGGESTED` path.
- Use ASCII-only characters (no em-dashes, curly quotes, or Unicode).
- Include YAML frontmatter with the fields specified above.
- Use plain text section headings (no backticks or formatting in headings).
- Provide direct citations to offending code or test output when rejected.
- Be specific and actionable in feedback.
