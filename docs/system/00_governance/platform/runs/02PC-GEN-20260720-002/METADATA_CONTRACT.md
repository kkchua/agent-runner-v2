# Metadata Contract

## Overview

This document defines the platform-specific metadata extensions for the
agent-runner-v2 platform. It extends the Layer 1 Metadata Standard
(`METADATA_STANDARD.md`, template `SYS-00-MS`) with platform-specific
`doc_type` values, `authority` values, additional frontmatter fields,
inheritance rules, and scan-policy expectations.

This contract does not modify or contradict Layer 1 baseline values.
Layer 1 defines the common field names and baseline vocabulary. This
document extends them for the agent-runner-v2 platform.

## Platform doc_type Values

Layer 1 defines eight baseline `doc_type` values. This platform extends
them with two additional platform-specific values.

### Layer 1 Baseline Values (Inherited)

| Value | Meaning |
|---|---|
| `masterplan` | Human-authored reference blueprint used to guide design decisions. |
| `system` | System-level governance or platform document intended to be part of a governed doc set. |
| `workflow_output` | Concrete output generated by a workflow execution. |
| `review_artifact` | Review result, critique, or recommendation artifact. |
| `validation_artifact` | Deterministic validation result or compliance artifact. |
| `audit_artifact` | Audit or verification artifact created after review or validation. |
| `bundle_definition` | A bundle-local definition or control document owned by a workflow bundle. |
| `platform_standard` | A Layer 2 operating standard for a specific platform or domain. |

### Platform-Specific Extensions

| Value | Meaning |
|---|---|
| `bundle_definition` | A bundle-local definition or control document. Owned by a specific Layer 3 workflow bundle. Distinct from `platform_standard` which is owned by the platform core. |
| `platform_standard` | A permanent Layer 2 operating standard. Owned by the agent-runner-v2 platform core. These documents define the platform constitution and may be `workflow-generated` or `platform-owned`. |

### Usage Guidance

**`platform_standard`**: Use for all six permanent platform constitution
documents (README, RUNTIME_MODEL, BUNDLE_AUTHORING_CONTRACT,
SHARED_SERVICES, METADATA_CONTRACT, VALIDATION_CONTRACT).

**`bundle_definition`**: Use for bundle-local governance documents
(`core_governance.md`, `prompt_sop.md`, etc.) and bundle-owned control
files that are not part of the platform constitution.

Layer 3 bundles should apply `doc_type: "workflow_output"` to their
generated outputs and reserve `doc_type: "bundle_definition"` for their
governance package files.

## Platform authority Values

Layer 1 defines five baseline `authority` values. This platform extends
them with two additional platform-specific values.

### Layer 1 Baseline Values (Inherited)

| Value | Meaning |
|---|---|
| `human-authored` | Canonical content is maintained directly by humans. |
| `workflow-generated` | Canonical content is produced and maintained by a workflow. |
| `bundle-owned` | Canonical content is owned by a specific Layer 3 bundle. |
| `platform-owned` | Canonical content is owned by a specific Layer 2 platform core. |
| `derived` | Content is generated from another authoritative source and is not itself the root authority. |

### Platform-Specific Extensions

| Value | Meaning |
|---|---|
| `platform-owned` | Content is owned by the agent-runner-v2 platform core. Use for platform constitution documents after they are published and activated. Staged draft outputs use `workflow-generated` until published. |
| `bundle-owned` | Content is owned by a specific Layer 3 workflow bundle. Use for bundle-local governance files and bundle-generated permanent outputs. |

### Authority Transitions

The authority of a document may change during its lifecycle:

1. **Staged (draft)**: `authority: "workflow-generated"` — the generating
   workflow is the producer but the content is not yet activated.
2. **Published (active)**: `authority: "platform-owned"` or
   `"bundle-owned"` — the owning layer/bundle now governs the content.

This transition is recorded by the publish action and reflected in both
frontmatter and the publish manifest.

## Additional Frontmatter Fields

The agent-runner-v2 platform extends the Layer 1 baseline metadata fields
with these platform-specific YAML frontmatter fields:

### `platform`

Identifies the platform that owns or generated the document.

| Value | Usage |
|---|---|
| `"agent-runner-v2"` | All documents generated or owned by this platform core. |

Required on all permanent platform standards. Layer 3 bundle outputs
should also include this field to identify their host platform.

### `template_id`

A stable identifier for the document's structural template. Used by
validators and scanners to confirm that a document has the expected
structure for its role.

| Template ID | Document |
|---|---|
| `SYS-02-IDX` | Platform Index (`README.md`) |
| `SYS-02-RM` | Runtime Model (`RUNTIME_MODEL.md`) |
| `SYS-02-BAC` | Bundle Authoring Contract (`BUNDLE_AUTHORING_CONTRACT.md`) |
| `SYS-02-SS` | Shared Services (`SHARED_SERVICES.md`) |
| `SYS-02-MC` | Metadata Contract (`METADATA_CONTRACT.md`) |
| `SYS-02-VC` | Validation Contract (`VALIDATION_CONTRACT.md`) |

Required on all permanent platform standards. Layer 3 bundles should
define their own `template_id` values for bundle-specific outputs.

### `managed_by`

Indicates what manages the document's lifecycle. For agent-runner-v2,
the typical value is `"workflow-generated"` for workflow-produced
documents.

### `lifecycle_status`

Tracks the document's position in the governance lifecycle.

| Value | Meaning |
|---|---|
| `"draft"` | Staged output from a workflow run; not yet published or activated. |
| `"published"` | Active, published document; the current authoritative version. |
| `"superseded"` | Previously published version replaced by a newer publication. |

Required on all governed documents. The publish action transitions status
from `"draft"` to `"published"`.

### `effective_version`

Identifies the workflow run (job ID) that produced this version of the
document. This provides traceability from the published document back to
the generating workflow run.

### `layer`

Identifies the owning layer of the document.

| Value | Usage |
|---|---|
| `"layer2"` | Platform core documents. |
| `"layer3"` | Bundle-owned documents. |

Required on all governed documents. Layer 1 documents use `"layer1"`.

## Inheritance Rules

### Layer 1 to Layer 2

Layer 2 inherits all Layer 1 baseline metadata fields and values without
modification:

- `doc_type` vocabulary (8 baseline values)
- `authority` vocabulary (5 baseline values)
- `scan_policy` vocabulary (3 values)
- Scanner compliance rules
- Required field rules

Layer 2 may only extend, never redefine or remove, Layer 1 values.

### Layer 2 to Layer 3

Layer 3 bundles inherit both:

1. Layer 1 baseline fields and values (via Layer 2)
2. Layer 2 platform-specific extensions

Layer 3 bundles may:

- Use any Layer 1 baseline or Layer 2 platform-specific `doc_type` value
- Use any Layer 1 baseline or Layer 2 platform-specific `authority` value
- Add bundle-specific frontmatter fields (not required by Layer 2)
- Define bundle-local `template_id` values

Layer 3 bundles must not:

- Redefine the meaning of any Layer 1 or Layer 2 value
- Remove or suppress required Layer 1 or Layer 2 frontmatter fields
- Claim `authority: "platform-owned"` for bundle-specific outputs

### Inheritance Constraints

| What | Layer 1 Defines | Layer 2 May Extend | Layer 3 Applies |
|---|---|---|---|
| Common field names | Yes | No (use as-is) | Yes |
| Baseline `doc_type` values | Yes | Add platform-specific values | Use any |
| Baseline `authority` values | Yes | Add platform-specific values | Use any |
| `scan_policy` values | Yes | No | Use as-is |
| Scanner compliance rules | Yes | Implement in code | Inherit |
| Additional fields | No | Add `platform`, `template_id`, `managed_by`, etc. | Add bundle-specific fields |

## Scan Policy Expectations

### Platform Standards

All permanent platform constitution documents carry:

- `scan_policy: "include"` — they must be included in operational scans.
- `scan_reason` explaining why inclusion is required.

### Temporary Evidence Artifacts

Review, validation, and audit artifacts carry:

- `scan_policy: "conditional"` or `"exclude"` — they are evidence, not
  permanent standards.
- `scan_reason` explaining their temporary or conditional role.

### Human-Authored Reference Documents

Masterplan and specification documents carry:

- `scan_policy: "exclude"` — they are design references, not operational
  outputs.
- `scan_reason` identifying them as reference blueprints.

### Scanner Compliance

Any document scanner, validator, or discovery component on this platform
must obey these rules:

1. Honor explicit `scan_policy` when present.
2. Skip `scan_policy: "exclude"` documents unless explicitly targeted.
3. Require an explicit inclusion rule for `scan_policy: "conditional"`.
4. Report documents with malformed or missing metadata as non-compliant.
5. Do not assume a document is authoritative solely because it was found.

These rules are derived from Layer 1 and implemented in the platform's
validation and scanning infrastructure.
