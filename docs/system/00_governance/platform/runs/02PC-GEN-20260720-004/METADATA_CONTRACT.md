# Metadata Contract

## Purpose

This document defines the platform-specific metadata extensions for
agent-runner-v2. It extends the Layer 1 metadata baseline with
platform-specific `doc_type` values, `authority` values, additional
frontmatter fields, inheritance rules, and scan policy expectations.

Layer 3 bundles running on agent-runner-v2 must comply with both the
Layer 1 metadata baseline and the extensions defined here.

## Platform doc_type Values

The Layer 1 Metadata Standard defines the baseline `doc_type`
vocabulary. agent-runner-v2 uses these Layer 1 values and clarifies
their platform-specific application:

| Value | Platform Application |
|---|---|
| `platform_standard` | Permanent Layer 2 platform constitution documents (the six docs in this set). |
| `system` | Layer 1 governance documents inherited by this platform. Not generated by Layer 2 workflows. |
| `masterplan` | Human-authored reference blueprints in `masterplan/`. Excluded from operational scans. |
| `bundle_definition` | Bundle-local control documents owned by a Layer 3 workflow bundle (e.g., governance files, prompt contracts). |
| `workflow_output` | Concrete output generated by a workflow step execution (e.g., generated documents, scaffolds). |
| `review_artifact` | Review result produced by a review step. Temporary evidence, not permanent authority. |
| `validation_artifact` | Deterministic validation result. Temporary evidence. |
| `audit_artifact` | Audit or verification result. Temporary evidence. |

### Platform Extension Rule

Layer 2 may introduce additional `doc_type` values for platform needs.
Any extension must:

- not change the meaning of Layer 1 baseline values
- be documented in this contract
- follow the naming conventions established by Layer 1

### doc_type Assignment by Layer

| Layer | Expected doc_type Values |
|---|---|
| Layer 1 | `system`, `masterplan` |
| Layer 2 (permanent) | `platform_standard` |
| Layer 2 (evidence) | `review_artifact`, `validation_artifact`, `audit_artifact` |
| Layer 3 (bundle defs) | `bundle_definition` |
| Layer 3 (outputs) | `workflow_output` |
| Layer 3 (evidence) | `review_artifact`, `validation_artifact`, `audit_artifact` |

## Platform authority Values

The Layer 1 Metadata Standard defines the baseline `authority`
vocabulary. agent-runner-v2 applies these values as follows:

| Value | Platform Application |
|---|---|
| `human-authored` | Masterplan documents and any human-maintained reference material. Layer 2 constitution docs must not use this value. |
| `workflow-generated` | Platform constitution documents generated by the `02_platform_core_foundation_v1` workflow. Also used for Layer 1 governance docs generated by `01_governance_foundation_v1`. |
| `platform-owned` | Content owned by the agent-runner-v2 platform core. Used when the platform itself is the canonical authority (e.g., published constitution docs after promotion). |
| `bundle-owned` | Content owned by a specific Layer 3 workflow bundle. Used for bundle-local governance, prompts, and action definitions. |
| `derived` | Content produced from another authoritative source. Used for context inventories, sync outputs, and transformed artifacts. |

### Authority Constraints

- Workflow-generated documents must not claim `human-authored` authority
- Layer 2 permanent docs use `workflow-generated` during staging and
  may transition to `platform-owned` after publication
- Layer 3 bundle outputs must not claim Layer 1 or Layer 2
  constitutional authority
- Derived artifacts must use `derived` authority and must not present
  themselves as the root authority

### Authority by Document Class

| Document Class | Allowed authority Values |
|---|---|
| Layer 2 permanent constitution | `workflow-generated`, `platform-owned` |
| Layer 2 evidence (review, validation, audit) | `workflow-generated`, `derived` |
| Layer 3 bundle definition | `bundle-owned`, `human-authored`, `workflow-generated` |
| Layer 3 workflow output | `workflow-generated`, `bundle-owned`, `derived` |
| Layer 3 evidence | `workflow-generated`, `derived` |

## Additional Frontmatter Fields

Beyond the Layer 1 baseline fields, agent-runner-v2 defines these
additional frontmatter fields for platform artifacts:

### `platform`

| Attribute | Value |
|---|---|
| Required | Yes, for all Layer 2 and Layer 3 permanent documents. |
| Value | `"agent-runner-v2"` |
| Purpose | Identifies the owning platform. Prevents platform-specific content from being mistaken for cross-platform governance. |

### `template_id`

| Attribute | Value |
|---|---|
| Required | Yes, for all permanent documents. |
| Value | Template-specific identifier (e.g., `SYS-02-IDX`, `SYS-02-RM`). |
| Purpose | Enables structural validation. Each template defines required section headings that validators check. |

### `managed_by`

| Attribute | Value |
|---|---|
| Required | Conditional. Required for workflow-generated documents. |
| Value | `"workflow-generated"` |
| Purpose | Declares that the document is workflow-managed and protected from manual edits. |

### `lifecycle_status`

| Attribute | Value |
|---|---|
| Required | Yes, for all permanent documents. |
| Values | `draft`, `review`, `approved`, `published`, `superseded`, `deprecated`, `retired` |
| Purpose | Tracks the document through the governance lifecycle defined in Layer 1. |

### `effective_version`

| Attribute | Value |
|---|---|
| Required | Conditional. Required for workflow-generated permanent documents. |
| Value | Run identifier (e.g., `02PC-GEN-20260720-004`) or change identifier. |
| Purpose | Links the document to the workflow run or change that produced it. Enables audit traceability. |

### `layer`

| Attribute | Value |
|---|---|
| Required | Yes, for all permanent documents. |
| Values | `"layer1"`, `"layer2"`, `"layer3"` |
| Purpose | Declares the owning layer for the document. |

### `generated_at`

| Attribute | Value |
|---|---|
| Required | No. |
| Value | ISO-8601 timestamp. |
| Purpose | Records when the document was generated. Used in temporary evidence artifacts. |

## Inheritance Rules

Metadata conventions inherit downward across layers for agent-runner-v2:

### Layer 1 Baseline

Layer 1 defines:

- Required field names (`doc_type`, `authority`, `scan_policy`,
  `scan_reason`)
- Baseline vocabularies for each field
- Scan policy rules and scanner compliance expectations
- Validation rules for metadata correctness

### Layer 2 Extensions

Layer 2 (this platform) adds:

- `platform` field (required for Layer 2 and Layer 3 permanent docs)
- `template_id` field (required for permanent docs)
- `managed_by` field (required for workflow-generated docs)
- `layer` field (required for permanent docs)
- `lifecycle_status` field (required for permanent docs)
- `effective_version` field (required for workflow-generated permanent docs)
- Platform-specific guidance for `doc_type` and `authority` application

### Layer 3 Compliance

Layer 3 bundles must:

- include all Layer 1 baseline fields
- include all Layer 2 extension fields where required
- use only values from the Layer 1 baseline vocabulary or the
  Layer 2 extension vocabulary
- not redefine the meaning of any Layer 1 or Layer 2 field
- not introduce new field names that conflict with Layer 1 or Layer 2
  fields

### Inheritance Direction

```
Layer 1 (baseline fields + vocabularies)
  |
  v
Layer 2 (adds platform fields + platform-specific guidance)
  |
  v
Layer 3 (inherits both, complies with both, may add bundle-local
         fields that do not conflict with higher layers)
```

## Scan Policy Expectations

### Platform Constitution Documents

Permanent Layer 2 platform constitution documents must use:

- `scan_policy: "include"` -- these documents participate in operational
  scans
- `scan_reason` -- must explain why the document is included

### Temporary Evidence Artifacts

Review, validation, and audit artifacts should use:

- `scan_policy: "conditional"` or `"exclude"` -- these are temporary
  evidence, not permanent authority
- `scan_reason` -- must explain the exclusion or conditional treatment

### Masterplan Documents

Human-authored masterplan documents must use:

- `scan_policy: "exclude"` -- reference blueprints are not operational
  documents
- `scan_reason` -- must explain the exclusion

### Layer 3 Bundle Documents

Layer 3 bundle documents follow these expectations:

| Document Class | Expected scan_policy |
|---|---|
| Bundle governance files | `include` |
| Workflow outputs | `include` |
| Prompt templates | `conditional` |
| Review/validation/audit evidence | `conditional` or `exclude` |

### Scanner Compliance

All scanners operating on agent-runner-v2 artifacts must follow the
Layer 1 scanner compliance rules:

1. Honor explicit `scan_policy` metadata when present
2. Skip `exclude` documents unless explicitly targeted
3. Require explicit inclusion rule for `conditional` documents
4. Report non-compliant metadata (missing fields, invalid values)
5. Not assume authority from absence of metadata
