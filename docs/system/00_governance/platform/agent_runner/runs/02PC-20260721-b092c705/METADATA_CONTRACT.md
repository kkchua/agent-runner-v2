# Metadata Contract

## Purpose

This document defines the platform-specific metadata extensions that
agent-runner-v2 adds to the Layer 1 Metadata Standard. Layer 3 bundles
and platform-generated documents inherit both the Layer 1 baseline and
these platform extensions.

## Platform doc_type Values

The Layer 1 Metadata Standard defines the baseline `doc_type` vocabulary.
agent-runner-v2 uses the following values from that vocabulary and adds
platform-specific semantics where appropriate.

### Values Defined by Layer 1 (Inherited)

| Value | Meaning |
|---|---|
| `masterplan` | Human-authored reference blueprint. Excluded from operational scans. |
| `system` | System-level governance or platform document. |
| `workflow_output` | Concrete output generated by a workflow execution. |
| `review_artifact` | Review result, critique, or recommendation artifact. |
| `validation_artifact` | Deterministic validation result or compliance artifact. |
| `audit_artifact` | Audit or verification artifact. |
| `bundle_definition` | Bundle-local definition or control document. |
| `platform_standard` | Layer 2 operating standard for a specific platform. |

### Platform-Specific Usage

On agent-runner-v2, these values carry the following platform-specific
expectations:

- `platform_standard` -- Used for all permanent Layer 2 platform
  constitution documents (this document set). Always carries
  `layer: "layer2"` and `platform: "agent-runner-v2"`.

- `bundle_definition` -- Used for Layer 3 bundle governance documents
  (`core_governance.md`, `prompt_sop.md`, etc.) and bundle-local
  TOML files where frontmatter is applicable. Always carries
  `layer: "layer3"` and a valid bundle name.

- `workflow_output` -- Used for concrete outputs generated by Layer 3
  workflow steps. Carries `layer: "layer3"`.

- `review_artifact`, `validation_artifact`, `audit_artifact` -- Used
  for temporary evidence artifacts produced during review, validation,
  and audit steps. These carry `scan_policy: "conditional"` or
  `scan_policy: "exclude"` and are never part of a permanent
  document set.

## Platform authority Values

The Layer 1 Metadata Standard defines the baseline `authority` vocabulary.
agent-runner-v2 uses these values with the following platform-specific
rules.

### Values Defined by Layer 1 (Inherited)

| Value | Meaning |
|---|---|
| `human-authored` | Content maintained directly by humans. |
| `workflow-generated` | Content produced and maintained by a workflow. |
| `bundle-owned` | Content owned by a specific Layer 3 bundle. |
| `platform-owned` | Content owned by a specific Layer 2 platform core. |
| `derived` | Content generated from another source; not the root authority. |

### Platform-Specific Authority Rules

- `platform-owned` -- Reserved for Layer 2 platform standards whose
  authoritative source is the platform core itself. Permanent platform
  constitution documents may carry this authority after publication.

- `workflow-generated` -- The default authority for platform documents
  produced by the `02_platform_core_foundation_v1` workflow. After
  publication, `authority` may be updated to `platform-owned`.

- `bundle-owned` -- Used for Layer 3 bundle artifacts whose canonical
  content is governed by the owning bundle.

- `derived` -- Used for evidence artifacts (review, validation, audit)
  that are produced from permanent artifacts but are not themselves
  authoritative.

### Usage Rules

The fields `authority` and `managed_by` are orthogonal axes:

- `authority` -- Answers: "Who owns the canonical truth of this
  document?" This is a content ownership question. Values are drawn
  from the Layer 1 authority vocabulary plus platform extensions.

- `managed_by` -- Answers: "What mechanism produced and maintains this
  file?" This is a mechanical production question. Values include
  `workflow-generated` (the file is produced by a workflow step and
  protected from manual edits) and other implementation-specific
  indicators.

A document carrying `authority: "platform-owned"` and
`managed_by: workflow-generated` is consistent: the platform core owns
the content, but a workflow mechanically produces and maintains the
file on disk. These fields serve different purposes and must not be
conflated.

## Additional Frontmatter Fields

agent-runner-v2 adds the following fields to the Layer 1 frontmatter
baseline:

### `platform`

| Field | Required | Description |
|---|---|---|
| `platform` | Yes (Layer 2 and Layer 3 docs) | Identifies the owning platform. For agent-runner-v2, the value is always `"agent-runner-v2"`. |

### `template_id`

| Field | Required | Description |
|---|---|---|
| `template_id` | Yes (permanent docs) | Stable identifier used for structural validation. Pattern: `SYS-{layer}-{code}` (e.g., `SYS-02-RM` for the Runtime Model). |

### `managed_by`

| Field | Required | Description |
|---|---|---|
| `managed_by` | Conditional | Indicator that the document is workflow-managed and protected from manual edits. Required for all workflow-generated documents. Common value: `workflow-generated`. |

### `lifecycle_status`

| Field | Required | Description |
|---|---|---|
| `lifecycle_status` | Yes (permanent docs) | Current lifecycle state from the Layer 1 governance lifecycle. On this platform: `draft`, `review`, `approved`, `published`, `superseded`, `deprecated`, `retired`. |

### `effective_version`

| Field | Required | Description |
|---|---|---|
| `effective_version` | Yes (workflow-generated docs) | The job ID or run identifier that produced this version. Used for audit trail and version tracking. |

### Field Placement

All fields use YAML frontmatter at the top of each markdown document:

```yaml
---
template_id: SYS-02-RM
version: "1.0"
doc_type: "platform_standard"
authority: "workflow-generated"
scan_policy: "include"
scan_reason: "..."
layer: "layer2"
platform: "agent-runner-v2"
lifecycle_status: "draft"
effective_version: "02PC-20260721-b092c705"
managed_by: workflow-generated
---
```

## Inheritance Rules

Metadata conventions inherit downward across layers on agent-runner-v2
as follows:

1. **Layer 1 Baseline** -- Layer 1 defines the common field names
   (`doc_type`, `authority`, `scan_policy`, `scan_reason`) and the
   baseline vocabularies for each field. All documents across all
   layers inherit these fields.

2. **Layer 2 Extensions** -- This platform adds the fields `platform`,
   `template_id`, `managed_by`, `lifecycle_status`, and
   `effective_version`. It also extends the allowed value sets for
   `doc_type` and `authority` with platform-specific semantics (as
   described above). Layer 2 does not redefine Layer 1 baseline values.

3. **Layer 3 Application** -- Layer 3 bundles inherit both Layer 1
   baseline values and Layer 2 platform extensions. Bundles apply
   platform-specific values (e.g., `platform: "agent-runner-v2"`) to
   their own outputs.

4. **No Redefinition** -- No lower layer may redefine the meaning of
   Layer 1 baseline values. For example, Layer 3 cannot change what
   `doc_type: "system"` means or claim `authority: "platform-owned"`
   for bundle outputs.

## Scan Policy Expectations

### Layer 2 Documents

| Document Class | Expected `scan_policy` | Expected `scan_reason` |
|---|---|---|
| Permanent platform standards | `include` | Permanent platform constitution; part of the governed document set. |
| Temporary evidence (review, validation, audit) | `conditional` or `exclude` | Run-scoped evidence; not permanent platform authority. |
| Platform context inventories | `exclude` | Comparison context only; not authoritative. |

### Layer 3 Documents

| Document Class | Expected `scan_policy` |
|---|---|
| Permanent bundle outputs | `include` |
| Review artifacts | `conditional` or `exclude` |
| Validation artifacts | `conditional` or `exclude` |
| Audit artifacts | `conditional` or `exclude` |

### Scanner Compliance

Scanners on agent-runner-v2 must obey the Layer 1 Scanner Compliance
Rules with the following platform-specific additions:

- Documents under `docs/system/00_governance/platform/current/` with
  `scan_policy: "include"` are part of the active platform constitution.
- Documents under `docs/system/00_governance/platform/runs/` are staged
  drafts and carry `lifecycle_status: "draft"` until published.
- Documents under `docs/system/00_governance/platform/history/` are
  archived snapshots and carry `lifecycle_status: "superseded"`.
