# SDLC Delivery Status Rules v1

## Purpose

Define the authoritative lifecycle status rules, state machine, promotion
patterns, and audit trail requirements for all SDLC delivery documents
produced by the Layer 3 AI-Driven SDLC workflows. This document governs
how delivery documents transition between lifecycle states and what
constraints apply at each state.

This document applies to all delivery document types: DRAFT-INIT, INIT,
REQ, PLAN, BACKLOG, TASK, IMPL, VALID, REV, MEM, and CLOSE.

## Scope

These rules apply to all delivery documents within the SDLC initiative
workflow chain (sdlc_10 through sdlc_80). They do not apply to codebase
documentation, scaffold artifacts, or Layer 1/2 governance documents,
which have their own lifecycle rules.

## Core Principles

### 1. Status Is Explicit

No hidden or implicit state changes. Every document carries its
lifecycle_status in its YAML frontmatter. The status field is the single
source of truth for the document's current state.

### 2. Approval Is Centralized

Only the human approval gate (via the workflow runner) can promote a
document from draft to approved. No agent has self-approval authority.

### 3. Execution Does Not Equal Approval

A document created by an agent has lifecycle_status: "draft". It is not
usable by downstream workflows until it passes review and promotion to
"approved".

### 4. Workflow Truth Is Durable

Workflow truth lives in runner state plus durable artifacts, not in chat
memory or conversation context. The document frontmatter and file system
are the sources of truth.

### 5. Rejection Stops Progression

If a document is rejected during review, no downstream workflow may use it
as input. The document must return to draft status for refinement, and the
refine loop must complete before re-review.

### 6. Approved Documents Are Immutable

Once a document reaches lifecycle_status: "approved", it is immutable.
No workflow, agent, or human may modify its content. Any required changes
must be handled through a new initiative or formal amendment process.

## Lifecycle States

### State Definitions

| Status | Meaning |
|---|---|
| draft | Initial document generated by an agent. Not yet reviewed. May be refined. |
| changes_requested | Review identified fixable defects. Document is being refined. |
| approved | All gates passed. Document is immutable. Downstream workflows may use it. |

### State Machine

```
draft --> changes_requested --> draft (refine loop) --> approved
```

Detailed transitions:

1. An agent generates a new document. Status is set to "draft".
2. The review step evaluates the document.
3. If the review passes and human approval is granted, status transitions
   to "approved".
4. If the review identifies fixable defects, status transitions to
   "changes_requested".
5. The refine step corrects the defects. Status returns to "draft".
6. The document re-enters review (goto step 2).
7. If the refine loop exhausts its iteration budget, the workflow fails.

### Forbidden Transitions

The following transitions are invalid:

- draft -> approved (without review and human approval)
- approved -> draft (approved is terminal within the initiative)
- approved -> changes_requested (approved is immutable)
- Any state -> draft (without going through the refine loop)
- changes_requested -> approved (must return to draft first via refine)

## Promotion Patterns

### Single Artifact Promotion

Used by most workflows (sdlc_20 through sdlc_70).

The document is generated as "draft", reviewed, refined if needed, then
promoted in-place from "draft" to "approved". The same file receives the
updated lifecycle_status.

Affected workflows: sdlc_20, sdlc_30, sdlc_40, sdlc_50, sdlc_60, sdlc_70.

### Two-File Promotion

Used by sdlc_10_requirement_v1 only.

The user authors a DRAFT-INIT document (draft status). The workflow
generates a new INIT-DOC from the DRAFT-INIT. The INIT-DOC follows the
standard draft -> review -> approved lifecycle. Both the DRAFT-INIT and
the INIT-DOC are preserved for audit trail purposes.

### Multi-Artifact Promotion

Used by sdlc_80_review_v1 only.

The workflow produces three documents (REV-DOC, MEM-DOC, CLOSE-DOC)
simultaneously. All three must pass review and receive human approval
before any of them are promoted to "approved". The promotion action
transitions all three documents to "approved" as a single atomic
operation.

## Refine Loop Rules

### Iteration Budget

Each workflow has a maximum refinement iteration budget (default: 2,
configurable per workflow). If the budget is exhausted without the
document passing review, the workflow fails and must be restarted.

### Refine Loop State Transitions

1. Review rejects the document -> status: "draft" -> "changes_requested"
2. Refine corrects the document -> status: "changes_requested" -> "draft"
3. Re-review evaluates the refined document
4. If still rejected, repeat from step 1 (subject to budget)

### Non-Fixable Defects

Defects that cannot be fixed through refinement (e.g., wrong scope,
invalid input, fundamental misunderstanding) MUST cause immediate workflow
failure. The refine loop is only for fixable defects.

## Audit Trail Requirements

### Immutability After Approval

Once a delivery document has lifecycle_status: "approved":
- It MUST NOT be modified by any workflow
- It MUST NOT be deleted
- It serves as an immutable audit trail record
- Any required changes require a new initiative or formal amendment

### Traceability

Every delivery document MUST include:
- Reference to the input document that produced it (cross_references)
- Reference to the output document it produced (cross_references)
- The workflow and step that generated it (managed_by field)
- The date of generation or approval
- The Initiative ID linking all documents in the same initiative

### Audit Trail Chain

The complete audit trail for an initiative follows this chain:

```
DRAFT-INIT -> INIT -> REQ -> PLAN -> BACKLOG -> TASK -> IMPL -> VALID -> REV + MEM + CLOSE
```

Each document in the chain references its predecessor and successor.

### Logging

Each workflow step that creates or modifies a document MUST log:
- The step name and workflow ID
- The document file path
- The lifecycle status before and after the operation
- The timestamp of the operation
- The agent or action that performed the operation

## Error Handling

### Validation Failures

If a generated document fails validation before review:
1. Log the specific validation failure.
2. Return to the refine loop for correction.
3. If max iterations exceeded, fail the workflow.

### Review Rejections

If a human reviewer rejects the document:
1. Capture the rejection reason and specific feedback.
2. Set status to "changes_requested".
3. Return to draft status for refinement.
4. After refinement, re-enter review.
5. If max iterations exceeded, fail the workflow.

### Agent Failures

If an agent fails to generate a valid response:
1. Retry with the same agent once.
2. If the second attempt fails, try an alternative coder backend.
3. If all backends fail, fail the workflow and escalate.
