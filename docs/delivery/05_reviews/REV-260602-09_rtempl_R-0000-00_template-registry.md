## Findings

### 1. The task-graph template exposes an unsupported lifecycle status
`02b_task_graph.template.md` allows `Draft / Approved / Completed / Superseded`. The governed Task Graph lifecycle is `Draft -> Approved`, with `Draft` or `Approved -> Superseded`. `Completed` is not a valid Task Graph status.

Required correction: remove `Completed` from the Task Graph metadata status values.

### 2. The task template dependency example can emit a self-dependency
`03_task.template.md` defines the generated Task ID as `TASK-{{YYYYMMDD}}-{{NN}}`, then uses the same `TASK-{{YYYYMMDD}}-{{NN}}` value as the first dependency example. Direct substitution can make a generated task depend on itself.

Required correction: use dedicated dependency placeholders or a dependency-list placeholder that cannot alias the generated task ID.

### 3. The registered validation template exposes an unsupported lifecycle status
`template_registry.md` maps Validation to `05_validation`, so registry consistency requires checking `05_validation.template.md`. Its metadata allows `Draft / Final / Superseded`, while the governed Validation lifecycle is `Draft -> Final`. Replacement validations may preserve supersession links, but `Superseded` is not a governed Validation artifact status.

Required correction: restrict Validation metadata status values to `Draft / Final`.

### 4. The registered validation template does not preserve complete upstream traceability
`05_validation.template.md` records Task ID, path, and version, but records the implementation plan and review without their upstream artifact versions. It also skips the mandatory implementation-record artifact in its traceability chain, moving directly from implementation plan to code.

The status rules require artifacts to preserve upstream IDs, source paths, versions, contract references, and relevant snapshot hashes. The SOP requires an accepted implementation record before implementation review and validation.

Required correction: add implementation-plan and review versions, and represent the implementation record in validation metadata or traceability fields with its ID, path, and version.

### 5. The registry misstates validation generation ownership
`template_registry.md` says Validation is generated by a runner validation action, "not a coder." The SOP assigns independent validation to the Validator and requires a validation artifact sidecar as coder-to-runner communication. The runner enforces and accepts validation; it does not author the artifact.

Required correction: describe validation as generated by the Validator through the runner-invoked validation action and accepted by the runner.

## Coverage Summary
All requested templates were reviewed against the project analysis, SOP, and status rules. Every requested artifact template has a metadata block containing `Doc Type` and `Template Version`. The registry flow, folder mappings, sidecar list, implementation-plan task path, and validation decision values are corrected. The remaining lifecycle, placeholder, traceability, and validation-ownership defects prevent approval.
