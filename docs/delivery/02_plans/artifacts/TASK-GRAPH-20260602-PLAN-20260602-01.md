## Task Graph Objective

This task graph decomposes the approved initiative to enhance Agent Runner with persistent database-backed daemon/worker mode into 12 executable tasks across 4 phases. The structure prioritizes foundational infrastructure (database schema and repository layer) before building CLI commands, worker integration, advanced features, and external documentation. Each task is narrow, testable, and reviewable, with explicit dependencies to enable parallel work within phases while maintaining execution order across phases.

## Task Graph

### `TASK-20260602-01` — Implement DB schema migrations for agent_runner_jobs, agent_runner_job_events, agent_runner_job_artifacts

**Description:** Design and implement three database migration files that create the foundational tables for persistent job state management: `agent_runner_jobs` (job metadata and status), `agent_runner_job_events` (append-only audit trail), and `agent_runner_job_artifacts` (workflow output registration). Ensure all tables include appropriate columns, indices, constraints (including support for PostgreSQL `SELECT ... FOR UPDATE SKIP LOCKED`), and are reversible. Validate transaction safety and concurrent claiming semantics at the schema level.

**Owner:** @kengkoon.chua

**Priority:** P0

**Depends On:** —

**Scope:** Phase 1 — Foundation (Slice 1); Database schema design and implementation; Success Criteria: All three tables created with correct columns, indices, and constraints; migrations reversible; schema supports PostgreSQL `FOR UPDATE SKIP LOCKED`.

**Deliverables:**
- Three migration files in `agent_runner_v2/db/migrations/` (auto-numbered by framework)
- Migration files create `agent_runner_jobs`, `agent_runner_job_events`, `agent_runner_job_artifacts` tables
- Schema specification document or inline migration comments clarifying column purposes and transaction semantics

**Testability:** Verify migrations apply and rollback without errors; query against created tables with sample data; validate indices exist and support `FOR UPDATE SKIP LOCKED` semantics with a simple concurrent test.

**Review Criteria:**
- All three tables exist with expected column definitions
- Primary keys, foreign keys, and unique constraints correctly defined
- Indices created for common query patterns (job_id, status, created_at, claimed_by)
- Migrations are reversible (up and down scripts)
- Schema supports `FOR UPDATE SKIP LOCKED` without errors

### `TASK-20260602-02` — Implement repository layer with six core methods

**Description:** Implement the `job_repository.py` module with six transaction-safe repository methods: `create_job`, `fetch_job`, `claim_next_job`, `update_job_status`, `append_event`, and `register_artifact`. Each method must be wrapped in database transactions, avoid N+1 query patterns, and handle concurrent access safely. The `claim_next_job` method is critical: it must use PostgreSQL's `SELECT ... FOR UPDATE SKIP LOCKED` to atomically claim the oldest queued job without race conditions or duplicate claims across concurrent workers.

**Owner:** @kengkoon.chua

**Priority:** P0

**Depends On:** `TASK-20260602-01`

**Scope:** Phase 1 — Foundation (Slice 1); Database schema and repository layer; Success Criteria: All six repository methods implemented; unit tests pass; no N+1 queries; transaction safety verified.

**Deliverables:**
- `agent_runner_v2/db/job_repository.py` module with six public methods
- Unit test suite exercising all methods, including concurrent claiming simulation
- Documentation of transaction semantics and query patterns

**Testability:** Unit tests verify each method with mocked database or test database; concurrent test spawns multiple threads claiming jobs; verify only one worker claims each job; verify event audit trail records all operations.

**Review Criteria:**
- All six repository methods fully implemented and tested
- No N+1 queries (inspect generated SQL or use query logging)
- Concurrent claiming test demonstrates zero race conditions
- Transaction boundaries clear and short-lived
- Error handling for constraint violations and concurrent conflicts

## Notes

- **Task Graph Decomposition Strategy:** The 12 tasks are organized into phases with explicit dependencies. Phase 1 (foundational database and CLI) unblocks Phase 2 (worker integration), which unblocks Phase 3 (advanced features). Testing is consolidated at the end to validate the entire feature set. Documentation is final to ensure guidance matches implementation.

- **Parallelism Windows:** Within each phase, multiple tasks can run in parallel where they have no inter-task dependencies. For example, the three Phase 1 CLI commands (TASK-03, TASK-04, TASK-05) depend only on the repository layer and can be developed concurrently.

- **Testing Strategy:** TASK-11 consolidates all testing (unit, integration, acceptance) to validate that all tasks work together. This avoids fragmented test suites and ensures end-to-end flows are tested.

- **Owner Assignment:** All tasks are currently assigned to @kengkoon.chua as the primary implementer. Work may be delegated within the team, but ownership remains for accountability.

- **No Implementation Code in Task Graph:** This document decomposes the plan into executable tasks without producing implementation plans, pseudocode, or design documents. Implementation details are left to the task execution phase.

- **State Machine Assumptions:** Tasks TASK-08, TASK-09, TASK-10 assume a well-defined state machine for job statuses (QUEUED, CLAIMED, RUNNING, WAITING_FOR_HUMAN_APPROVAL, READY_TO_RESUME, COMPLETED, FAILED, REJECTED, CANCELLED). This state machine should be documented separately.
