## Consistency Findings

### CS-001: Workflow Reference Inconsistency (CRITICAL)

Status: FAIL

The requirements document references `sdlc_10_requirement_v1` as the target
workflow throughout (FR-010, FR-002, AC-002, AC-007), but:

1. The initiative document INIT-20260723-004_console-sdlc10-support.md
   explicitly corrects this to `sdlc_00_init_doc_v1`.

2. The initiative notes: "The draft initiative referenced sdlc_10_requirement_v1
   as the target workflow for Phase 1. This initiative corrects the workflow
   reference to sdlc_00_init_doc_v1 based on the actual workflow definitions."

3. The artifact mapping confirms this: `sdlc_00_init_doc_v1` takes
   `DRAFT_INIT_FILE` as input and produces `INIT_FILE`, while
   `sdlc_10_requirement_v1` takes `INIT_FILE` as input and produces `REQ_FILE`.

Impact: Testers implementing AC-002, AC-007 would test against the wrong
workflow, leading to verification failures. The described functionality
(selecting DRAFT_INIT_FILE and producing INIT_FILE) aligns with
` sdlc_00_init_doc_v1`, not `sdlc_10_requirement_v1`.

Recommendation: Replace all occurrences of `sdlc_10_requirement_v1` with
`sdlc_00_init_doc_v1` in the requirements document.

### CS-002: Source Document Reference Inconsistency

Status: FAIL

The requirements document frontmatter declares:

## Feasibility and Implementation Status Findings

### F-001: Features Already Implemented (CRITICAL)

Status: FAIL

Codebase inspection reveals that the described functionality already exists:

1. **Dynamic Input Field Generation**: The operator console (app.py) already
   implements `rebuild_input_fields()` (lines 221-308) that dynamically
   generates input fields based on workflow.toml `required_inputs`.

2. **File Picker UI**: A `ft.FilePicker` is already instantiated (line 168)
   and wired to browse functionality with `on_browse_click()` handler.

3. **SDLC Input Directory Mapping**: The `SDLC_INPUT_DIRS` dict (lines 38-48)
   already maps artifact keys to delivery subdirectories, including
   `DRAFT_INIT_FILE`.

4. **Input Artifact Submission**: The `runner_service.submit_job()` method
   already accepts and forwards `input_artifacts` parameter (lines 38-65).

5. **Path Resolution**: The `resolve_input_path()` function (lines 313-345)
   already handles path resolution for SDLC artifact keys.

6. **Conditional Visibility**: Input fields are shown/hidden based on
   workflow selection via `rebuild_input_fields()`.

Impact: The requirements document describes "new" functionality that is
already implemented. This indicates:
- The requirements may have been generated without checking existing code
- Testers would find the acceptance criteria already passing
- Development effort estimates would be incorrect

Recommendation: Either:
a) Update the requirements document to reflect "enhancement" scope (e.g.,
   "Ensure existing file picker works correctly for SDLC workflows") rather
   than "new" feature scope.
b) Mark requirements as "VERIFICATION" type to confirm existing functionality.
c) Add a preamble noting that dynamic input handling already exists and this
   initiative validates it for SDLC workflows.

### F-002: Workflow.toml Input Discovery

Status: PARTIAL

The requirements assume workflows will declare their input requirements via
a mechanism, but do not specify where this information comes from. The existing
implementation uses `bundle.steps[init_step_name].required_inputs` from
workflow.toml. The requirements should document this dependency.
