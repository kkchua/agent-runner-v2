# Backlog: Incremental Codebase Documentation Updates with Git Hook Automation

## Backlog Overview

This backlog defines the ordered set of work items for implementing the Incremental Codebase Documentation Updates initiative in agent-runner-v2. The initiative addresses the problem that the existing full-scan workflow (`sdlc_00_codebase_v1`) processes all 141+ module documentation files on every run, even when only a small number of source files have changed.

The backlog is derived from the approved solution architecture plan (PLAN-20260806-001) and its source requirements (REQ-20260806-001). The solution delivers three integrated capabilities:

1. A reusable workflow package (`update_codebase_docs_v1`) that identifies source files changed since the last documentation update and regenerates only the affected module documentation files.
2. CLI commands (`install-codebase-hook`, `uninstall-codebase-hook`) to manage post-commit git hooks in any target repository.
3. A post-commit git hook mechanism that automatically triggers the incremental documentation update workflow when source code commits occur.

All work items in this backlog are traceable to the approved plan components (Component A: Workflow Package, Component B: CLI Commands, Component C: Git Hook Script). No scope has been invented beyond what the plan specifies.

### Scope Boundaries

The following boundaries are inherited from the plan and requirements and are not redefined here:

- The solution complements `sdlc_00_codebase_v1` and does not modify it (NFR-009, NFR-010).
- The solution does not change the codebase documentation format, structure, or template design (NFR-011).
- The solution does not change the codebase manifest schema or artifact key naming conventions (NFR-012).
- Layer 1 governance (METADATA_STANDARD.md) and Layer 2 platform constitution (BUNDLE_AUTHORING_CONTRACT.md, METADATA_CONTRACT.md, VALIDATION_CONTRACT.md) are treated as read-only.

### Assumptions Carried Forward

- ASSUMPTION-001: The target repository already has an initial codebase documentation set generated by `sdlc_00_codebase_v1` or `codebase-init`.
- ASSUMPTION-002: The initiative's referenced workflow spec will be available as a design reference during implementation.
- ASSUMPTION-003: The git hook should verify daemon availability before submitting the workflow to avoid orphaned submissions.
- ASSUMPTION-004: A manual trigger command for testing without committing should be evaluated during implementation.
- ASSUMPTION-005: Pre-push hooks may be considered as an alternative or complementary trigger during implementation.
- ASSUMPTION-006: The exact hook script source path within the agent-runner-v2 package will be finalized during implementation.

### WI-20260806-001_incremental-codebase-doc-update-02 Incremental Change Detection Action

**Source:** Plan Component A - Step: detect_incremental_changes; Plan Section: Incremental Detection Strategy

**Description:** Implement the `detect_incremental_changes` action function decorated with `@action()`. This action:

- Reads the `.last_sync_commit` file at the repository root to obtain the reference commit hash.
- Runs `git diff --name-only <last_sync_commit>..HEAD` to identify changed source files.
- Calls `build_snapshot(project_root, mode=..., job_id=..., step=..., workflow_name=...)` to obtain the full snapshot.
- Uses the snapshot `items` list (each `ScanItem` has `rel_path` and `owner_doc_path` fields) to map changed source files to their owner documentation paths.
- Filters to only files that have corresponding module documentation.
- Writes the `INCREMENTAL_CHANGE_LIST` artifact (JSON list of changed files and their affected doc paths).
- If no changes detected, terminates early with a skip status (FR-021).
- Produces clear error messages for: missing `.last_sync_commit` (FR-022), missing `docs/repo/codebase/current/` (FR-024).

**Requirements Covered:** FR-003, FR-005, FR-021, FR-022, FR-024, FR-025

**Affected Codebase Areas:** `agent_runner_v2/codebase_docs.py` (public API: `build_snapshot()`, `ScanItem`), `workflows/update_codebase_docs_v1/actions.py`

**Verified API Signatures:**
- `build_snapshot(project_root: Path, *, mode: str, job_id: str, step: str, workflow_name: str | None = None) -> dict[str, Any]` (codebase_docs.py line 762)
- `ScanItem(rel_path: str, category: str, subcategory: str, doc_mode: str, status: str, owner_doc_path: str, last_verified_by_change: str)` (codebase_docs.py line 122)

**Audit/Compliance Sensitivity:** Uses only public APIs (build_snapshot, ScanItem dataclass). Does not import private functions (_classify_file, _module_doc_path).

### WI-20260806-001_incremental-codebase-doc-update-07 Git Hook Script Template

**Source:** Plan Component C - Git Hook Script

**Description:** Create the post-commit git hook script template at `agent_runner_v2/data/hooks/post_commit_codebase_update.py`. The script:

- Is a Python script with a shebang line (`#!/usr/bin/env python3`).
- After a commit, checks for daemon/backend availability. If unavailable, logs a warning and exits without blocking the commit (FR-020, NFR-002).
- Checks for concurrent execution by looking for the lock file (FR-023). If another update is in progress, exits silently.
- Submits the `update_codebase_docs_v1` workflow to the backend via CLI invocation (`ukbe-run-agent run update_codebase_docs_v1`). This is preferred over direct `BackendClient` import to avoid coupling to package internals (Integration Point 4).

**Cross-Platform Strategy:**
- On Unix (Linux/macOS): script installed directly as `.git/hooks/post-commit` with executable permissions.
- On Windows: a small batch file wrapper (`.git/hooks/post-commit.bat` or similar) invokes the Python script via the system Python interpreter. Related to Plan Open Question OQ-003.

**Requirements Covered:** FR-017, FR-018, FR-019, FR-020, NFR-002

### WI-20260806-001_incremental-codebase-doc-update-08 Error Handling and Concurrency Guards

**Source:** Plan Section: Error Handling, Concurrency and State Management

**Description:** Implement the error handling guards and concurrency mechanisms across the workflow actions:

- **No-change detection (FR-021):** The `detect_incremental_changes` action detects when `git diff` returns an empty list and terminates early with a skip status, logging a clear message.

- **Missing tracking file (FR-022):** The `detect_incremental_changes` action produces a clear error message with recovery instructions ("Run the full-scan workflow (sdlc_00_codebase_v1) first to establish the initial documentation set") when `.last_sync_commit` is not found.

- **Concurrent execution guard (FR-023, NFR-004):** A lock file mechanism (e.g., `.ukbe-runner/incremental_codebase_update.lock`) prevents concurrent executions. The lock file is created at the start of `detect_incremental_changes` and removed at the end of `commit_changes`. If the lock exists and its timestamp is within a reasonable window (e.g., 10 minutes), the workflow skips execution. The timeout value should be defined as a named constant (e.g., `LOCK_STALE_TIMEOUT_SECONDS`) and documented as configurable for tuning based on repository size. Related to Plan Open Question OQ-002.

- **Missing docs structure (FR-024):** The `detect_incremental_changes` action produces a clear error message or skips the repository when `docs/repo/codebase/current/` is not found.

- **Backend unavailability (FR-020, NFR-006):** The hook script handles connection timeout or error gracefully by logging the error and exiting without blocking the commit.

**Requirements Covered:** FR-021, FR-022, FR-023, FR-024, FR-025, NFR-004, NFR-006

**Affected Codebase Areas:** `workflows/update_codebase_docs_v1/actions.py`, `agent_runner_v2/data/hooks/post_commit_codebase_update.py`

**Audit/Compliance Sensitivity:** Error messages must be clear and actionable (NFR-008). The concurrency lock file must have a stale timeout to avoid permanent lockouts.

**Dependencies:** WI-20260806-001_incremental-codebase-doc-update-02, WI-20260806-001_incremental-codebase-doc-update-07 (error handling is cross-cutting across detection action and hook script).

### OQ-BL-006: New Artifact Key Registration

**Status:** Resolved -- global registration recommended.
**Source:** Backlog analysis
**Description:** The plan defines five new artifact keys (INCREMENTAL_CHANGE_LIST, INCREMENTAL_MODULE_DOCS, INCREMENTAL_INVENTORY, INCREMENTAL_CHANGE_IMPACT, TRACKING_UPDATE_MANIFEST). It needs to be determined whether these keys must be registered in `artifact_keys.py` and `path_catalog.py`, or whether they can be declared locally in the workflow's `workflow.toml` `[step.artifacts]` section per BUNDLE_AUTHORING_CONTRACT.md conventions.
**Codebase evidence:** Examination of existing workflow packages shows that artifact keys used by codebase-related workflows are registered globally in `artifact_keys.py`. For example, `CODEBASE_INVENTORY` (line 113) and `CODEBASE_CHANGE_IMPACT` (line 114) are both globally registered. Each workflow's `context_extensions.py` provides a `register_artifact_keys()` method mapping keys to relative paths (e.g., `sdlc_00_codebase_scaffold_v1/context_extensions.py`). The `workflow.toml` `[step.artifacts]` section declares which keys each step produces and consumes.
**Recommendation:** Register all five new artifact keys globally in `artifact_keys.py`, provide path mappings in the workflow's `context_extensions.py` via `register_artifact_keys()`, and declare them in `workflow.toml` `[step.artifacts]` sections. This follows the established pattern and ensures consistency with the path resolution system.
**Affects:** WI-20260806-001_incremental-codebase-doc-update-01, WI-20260806-001_incremental-codebase-doc-update-09
**Resolution approach:** Apply during WI-01 implementation. Verify in WI-09.
