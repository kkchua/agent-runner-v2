# Requirements: Incremental Codebase Documentation Updates with Git Hook Automation

## Requirements Overview

This document specifies the requirements for automating incremental codebase documentation updates across all agent-runner-v2 enabled repositories. The initiative addresses the problem that the existing full-scan workflow (`sdlc_00_codebase_v1`) processes all 141+ module documentation files on every run, even when only one or two source files have changed. This results in excessive execution time and resource consumption, while documentation frequently falls out of sync between manual refreshes.

The solution must deliver three primary capabilities:

1. A reusable workflow package (`update_codebase_docs_v1`) that regenerates only the documentation files affected by recent source code changes.
2. CLI commands (`install-codebase-hook`, `uninstall-codebase-hook`) to manage post-commit git hooks in any target repository.
3. A post-commit git hook mechanism that automatically triggers incremental documentation updates when source code commits occur.

All requirements in this document are derived from the approved initiative document (INIT-20260806-001). No scope has been invented beyond what the initiative specifies.

### Assumptions

- ASSUMPTION-001: The target repository already has an initial codebase documentation set generated by `sdlc_00_codebase_v1` or `codebase-init`.
- ASSUMPTION-002: The initiative's referenced workflow spec (`docs/repo/workflow_builder/specs/incremental-codebase-update.md`) will be available as a design reference during the planning phase.
- ASSUMPTION-003: The git hook should verify daemon availability before submitting the workflow to avoid orphaned submissions (per initiative Notes).
- ASSUMPTION-004: A manual trigger command for testing without committing should be evaluated during planning, as it supports testing and debugging scenarios (per critique resolution Finding 4).
- ASSUMPTION-005: Pre-push hooks may be considered as an alternative or complementary trigger during planning, to support batching of multiple commits (per critique resolution Finding 5).
- ASSUMPTION-006: The exact hook script source path within the agent-runner-v2 package will be finalized during the planning phase (per critique resolution Finding 2).

## Functional Requirements

### Workflow Package

FR-001: The system shall provide a reusable workflow package named `update_codebase_docs_v1` that performs incremental codebase documentation updates.

FR-002: The workflow package shall be repo-agnostic and operable in any agent-runner-v2 enabled repository that has the standard `docs/repo/codebase/` directory structure.

FR-003: The workflow shall identify which source code files have changed since the last documentation update by comparing against the `.last_sync_commit` tracking file reference.

FR-004: The workflow shall regenerate only the module documentation files corresponding to changed source code files, not all module documentation.

FR-005: The workflow shall reuse existing `codebase_docs.py` module functions: `build_snapshot()`, `render_module_doc()`, `render_inventory()`, and `render_change_impact()`.

FR-006: The workflow shall update the `.last_sync_commit` tracking file to record the current commit reference after successful documentation regeneration.

FR-007: The workflow shall automatically commit the updated documentation files to the repository after incremental regeneration.

FR-008: The workflow package shall follow the existing workflow package structure: `workflow.toml`, `prompts/`, `actions.py`, `context_extensions.py`.

### CLI Commands

FR-009: The system shall provide an `install-codebase-hook` CLI command that installs a post-commit git hook in a target repository.

FR-010: The system shall provide an `uninstall-codebase-hook` CLI command that removes the post-commit git hook from a target repository.

FR-011: Both CLI commands shall default to operating on the current working directory when no repository path is specified.

FR-012: Both CLI commands shall support a `--repo /path/to/repo` flag for targeting arbitrary repositories.

FR-013: The `install-codebase-hook` command shall verify the presence of `docs/repo/codebase/current/` before enabling the hook.

FR-014: The `install-codebase-hook` command shall be idempotent -- running it multiple times shall not create duplicate hooks or produce errors.

FR-015: The `uninstall-codebase-hook` command shall be idempotent -- running it multiple times shall not produce errors.

FR-016: The `uninstall-codebase-hook` command shall preserve the `.last_sync_commit` tracking file during removal.

### Git Hook Behavior

FR-017: The post-commit git hook shall automatically trigger the incremental documentation update workflow when source code changes are committed.

FR-018: The post-commit git hook shall submit the incremental update workflow to the backend for execution.

FR-019: The git hook script shall be stored in the agent-runner-v2 package (under `agent_runner_v2/`) and copied to the target repository's `.git/hooks/` directory during installation.

FR-020: The git hook shall be lightweight and shall not block the commit operation with heavy synchronous processing.

### Error Handling

FR-021: The system shall detect and handle the case where no source changes are detected between the current commit and the last sync commit, and skip the documentation update.

FR-022: The system shall detect and handle the first-run scenario where the `.last_sync_commit` tracking file does not exist, and produce a clear error message.

FR-023: The system shall detect and handle concurrent workflow execution by skipping the run if an incremental update is already in progress.

FR-024: The system shall detect and handle the absence of the `docs/repo/codebase/current/` directory structure, and produce a clear error message or skip the repository.

FR-025: The system shall produce clear, actionable error messages for each error condition listed in FR-021 through FR-024.

## Non-Functional Requirements

### Performance

NFR-001: Incremental update execution time shall achieve a target reduction of 50% or greater compared to full-scan workflow runs for typical commits (one to five files changed), measured under comparable conditions.

NFR-002: The git hook script shall not add noticeable latency to the git commit operation itself.

NFR-003: The benchmark target (NFR-001) shall be measured against the baseline full-scan execution time on the same repository under similar conditions.

### Reliability

NFR-004: The system shall prevent duplicate or concurrent workflow executions when multiple commits occur in rapid succession.

NFR-005: The `.last_sync_commit` tracking file shall be preserved across uninstall/reinstall cycles of the git hook.

NFR-006: The workflow shall handle backend unavailability gracefully without corrupting repository state.

### Usability

NFR-007: After initial hook installation, codebase documentation shall stay synchronized with code changes with zero manual intervention.

NFR-008: Error messages produced by the system shall be clear and actionable, enabling users to diagnose and resolve issues without consulting source code.

### Compatibility

NFR-009: The incremental workflow shall complement `sdlc_00_codebase_v1` and shall not replace it. The full-scan workflow remains the authority for initial setup, major refactoring, and periodic refresh.

NFR-010: The solution shall not modify the existing `sdlc_00_codebase_v1` full-scan workflow.

NFR-011: The solution shall not change the codebase documentation format, structure, or template design.

NFR-012: The solution shall not change the codebase manifest schema or artifact key naming conventions.

## Risk Assessment

### Risk R-001: codebase_docs.py API Incompatibility

**Description:** The existing `codebase_docs.py` functions (`build_snapshot()`, `render_module_doc()`, `render_inventory()`, `render_change_impact()`) may not support incremental invocation patterns or may require parameters not suitable for partial regeneration.

**Impact:** High -- the workflow depends on reusing these functions.

**Mitigation:** Verify function signatures and invocation patterns against the actual source code before finalizing the workflow design. The functions are confirmed to exist with the signatures documented in the codebase module documentation. If API modifications are needed, they must remain backward-compatible with the existing full-scan workflow.

### Risk R-002: Git Hook Portability Across Platforms

**Description:** The post-commit git hook script must work on Windows, Linux, and macOS. Git hooks are platform-sensitive (shell script vs. batch file vs. PowerShell).

**Impact:** Medium -- the CLI commands must produce hooks that work on the developer's platform.

**Mitigation:** The hook script template must be designed with cross-platform compatibility in mind during the planning phase. Consider platform-specific hook generation or a universal approach (e.g., Python script invoked by the hook).

### Risk R-003: Concurrent Execution Race Conditions

**Description:** Multiple rapid commits could trigger overlapping workflow submissions, leading to race conditions in `.last_sync_commit` updates or duplicate documentation commits.

**Impact:** Medium -- could cause inconsistent documentation state or git conflicts.

**Mitigation:** Implement a concurrency guard (FR-023) that skips execution if an update is already in progress. The `.last_sync_commit` update must be atomic relative to the documentation regeneration.

### Risk R-004: Backend Service Unavailability

**Description:** The git hook triggers workflow submission to the backend. If the backend is unreachable, the hook must not fail the commit, but the documentation update may be lost.

**Impact:** Medium -- documentation could fall out of sync if backend is frequently unavailable.

**Mitigation:** The hook should check daemon/backend availability before submitting (ASSUMPTION-003). Failed submissions should be logged but not block the commit. The `.last_sync_commit` should only advance after confirmed successful execution.

### Risk R-005: Benchmark Measurement Difficulty

**Description:** The 50% reduction target (NFR-001) requires comparable baseline measurements. Execution time varies with repository size, system load, and network conditions.

**Impact:** Low -- measurement methodology must be agreed upon before verification.

**Mitigation:** Define a standard benchmark protocol during the planning phase: same repository, same commit set, same system conditions. Use wall-clock time for the full workflow execution (not just the documentation rendering step).

### Risk R-006: Scope Creep from Planning-Phase Evaluations

**Description:** The initiative notes several items for planning-phase evaluation (manual trigger command, pre-push hooks). These evaluations could expand scope beyond the approved initiative boundaries.

**Impact:** Low -- could delay delivery if evaluations lead to additional requirements.

**Mitigation:** Planning-phase evaluations are explicitly scoped as evaluation only, not commitment. Any items promoted from evaluation to requirement must go through the initiative amendment process before being added to this requirements document.
