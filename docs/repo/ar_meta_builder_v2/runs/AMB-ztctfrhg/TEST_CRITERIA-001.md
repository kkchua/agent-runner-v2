# Test Criteria -- Target Workflow Design Phases

## Introduction

This document defines the acceptance criteria for all 8 design phases of the target workflow that is generated by the meta-workflow described in bootstrap.spec.md. The criteria apply to the TARGET workflow output -- not the builder itself. Every criterion is designed to be objectively verifiable by a gatekeeper step (LLM review or deterministic validation).

Scope: These criteria cover identity correctness, three-layer architecture compliance, artifact contract integrity, step routing validity, operational completeness, and negative constraints (forbidden content). The criteria are organized by the 8 sequential design phases plus a consolidated negative criteria section and a self-validation section.

Target workflow output type: documented_versioned (as declared in the runtime spec frontmatter).

Applicable invariants (the 4 meta-test-criteria):
- INV-1: Identity Isolation -- the builder identity must never leak into generated output.
- INV-2: Three-Layer Architecture -- Layer 1 (components), Layer 2 (composition), Layer 3 (resolved output) must each be present and distinct.
- INV-3: Test-Driven Development -- each phase must include generation, review, validation, and gatekeeping steps.
- INV-4: Recursive Capability -- the generated workflow must be capable of bootstrapping itself.


## Criteria for Phase 1 (Analyze Spec)

This phase extracts identity, output type, domain description, component types, and composition requirements from the runtime specification.

### Identity Correctness

- P1-ID-001: The extracted target workflow name is a non-empty string that differs from the builder workflow name.
- P1-ID-002: The extracted standard name is a non-empty string that differs from the builder standard name.
- P1-ID-003: The extracted standard version matches the semver format (MAJOR.MINOR.PATCH) declared in the runtime spec frontmatter.
- P1-ID-004: The standard filename ends with the suffix .md and is not identical to any builder-owned filename.

### Output Type Extraction

- P1-OT-001: The output delivery type is exactly one of: documented_versioned, direct.
- P1-OT-002: If the output type is documented_versioned, the target standard filename is recorded and will be included in the final workflow package.
- P1-OT-003: If the output type is direct, no separate standard document is required in the output package.

### Meta-Test-Criteria Coverage (4 Invariants)

- P1-MTC-001: The phase output explicitly acknowledges INV-1 (identity isolation) and records the builder identity tokens that must be excluded from all downstream artifacts.
- P1-MTC-002: The phase output explicitly acknowledges INV-2 (three-layer architecture) and records that Layers 1, 2, and 3 will each be produced.
- P1-MTC-003: The phase output explicitly acknowledges INV-3 (test-driven development) and records that each subsequent phase will include generation, review, validation, and gatekeeping steps.
- P1-MTC-004: The phase output explicitly acknowledges INV-4 (recursive capability) and records that the generated workflow must accept its own output type as valid input.


## Criteria for Phase 2 (Component Schema)

This phase defines Layer 1 -- the component types, their common and type-specific properties, and the validation rules that govern them.

### All Component Types Defined

- P2-CT-001: At least one component type is defined in the schema.
- P2-CT-002: Each component type has a unique type identifier (string, non-empty, alphanumeric with underscores).
- P2-CT-003: No component type identifier duplicates the builder workflow name or standard name.
- P2-CT-004: Each component type includes a human-readable description field.

### 7 Common Properties

- P2-CP-001: Every component type defines exactly 7 common properties (the set must be consistent across all types).
- P2-CP-002: Each common property has a name, a data type, and a required/optional flag.
- P2-CP-003: Common property names are unique within the common properties set.
- P2-CP-004: Common property data types are limited to: string, integer, boolean, list, object.
- P2-CP-005: Each common property includes a description explaining its purpose.
- P2-CP-006: At least one common property serves as the component identifier.
- P2-CP-007: The common properties set is identical for every component type (no type may omit or rename a common property).

### Type-Specific Properties

- P2-TSP-001: Each component type may define additional type-specific properties beyond the 7 common ones.
- P2-TSP-002: Type-specific property names must not collide with common property names within the same type.
- P2-TSP-003: Type-specific properties follow the same naming and typing conventions as common properties.

### Validation Rules VR-001 through VR-008

- P2-VR-001: At least 8 validation rules (VR-001 through VR-008) are defined and numbered sequentially.
- P2-VR-002: Each validation rule has a unique identifier in the format VR-NNN.
- P2-VR-003: Each validation rule specifies the component type(s) it applies to.
- P2-VR-004: Each validation rule specifies a deterministic check (a condition that can be evaluated as pass/fail without ambiguity).
- P2-VR-005: Each validation rule specifies the error message to emit on failure.
- P2-VR-006: VR-001 through VR-004 cover structural validity (required properties present, correct types).
- P2-VR-007: VR-005 through VR-008 cover semantic validity (cross-property constraints, value ranges, referential integrity).
- P2-VR-008: No validation rule references builder-specific types, names, or artifacts.


## Criteria for Phase 3 (Composition Format)

This phase defines Layer 2 -- the composition format that specifies how components bind together, how placeholders resolve, and how ordering works.

### Binding Rules (One Per Type)

- P3-BR-001: Exactly one binding rule is defined for each component type declared in Phase 2.
- P3-BR-002: Each binding rule specifies which other component types it may reference.
- P3-BR-003: Each binding rule specifies the binding cardinality (one-to-one, one-to-many, or many-to-many).
- P3-BR-004: Binding rules are bidirectionally consistent -- if type A binds to type B, then type B's rule acknowledges the relationship.

### Override Mechanism

- P3-OM-001: The composition format defines a mechanism for overriding default binding behavior.
- P3-OM-002: The override mechanism specifies the syntax for declaring an override.
- P3-OM-003: The override mechanism specifies precedence rules (which override wins when multiple apply).
- P3-OM-004: The override mechanism is documented with at least one example.

### 7 Placeholders

- P3-PH-001: Exactly 7 placeholder tokens are defined in the composition format.
- P3-PH-002: Each placeholder uses the syntax {PLACEHOLDER_NAME} with uppercase alphanumeric and underscore characters.
- P3-PH-003: Each placeholder has a documented resolution source (which component property or runtime value fills it).
- P3-PH-004: Placeholder names are unique across the composition format.
- P3-PH-005: At least one placeholder resolves from the runtime spec frontmatter.
- P3-PH-006: At least one placeholder resolves from a component property.
- P3-PH-007: No placeholder name collides with any artifact key declared in Phase 5.

### Ordering Rules

- P3-OR-001: The composition format specifies the order in which components are resolved.
- P3-OR-002: Ordering rules prevent circular dependencies between component types.
- P3-OR-003: The ordering is deterministic -- given the same input, the same order is always produced.
- P3-OR-004: The ordering rules account for all component types defined in Phase 2.


## Criteria for Phase 4 (Output Format)

This phase defines Layer 3 -- the resolved output structure, resolution rules, and quality requirements.

### 3-Part Output Structure

- P4-OS-001: The output format defines exactly 3 parts (corresponding to Layer 1, Layer 2, and Layer 3 content).
- P4-OS-002: Part 1 contains the component definitions (Layer 1 content).
- P4-OS-003: Part 2 contains the composition format with all placeholders resolved (Layer 2 content).
- P4-OS-004: Part 3 contains the fully resolved deliverables (Layer 3 content).
- P4-OS-005: Each part is clearly delimited with section headings.
- P4-OS-006: The 3-part structure is present in every output document regardless of output type.

### Resolution Rules RR-001 through RR-005

- P4-RR-001: At least 5 resolution rules (RR-001 through RR-005) are defined.
- P4-RR-002: Each resolution rule specifies which placeholder or binding it resolves.
- P4-RR-003: Each resolution rule specifies the transformation logic (direct copy, template expansion, computed value, or external lookup).
- P4-RR-004: Each resolution rule specifies the expected output format after resolution.
- P4-RR-005: RR-001 through RR-003 handle Layer 1 to Layer 2 resolution (component properties to composition bindings).
- P4-RR-006: RR-004 through RR-005 handle Layer 2 to Layer 3 resolution (composition to fully resolved output).
- P4-RR-007: All resolution rules are deterministic -- same input always produces same output.

### Quality Requirements QR-001 through QR-012

- P4-QR-001: At least 12 quality requirements (QR-001 through QR-012) are defined.
- P4-QR-002: Each quality requirement has a unique identifier in the format QR-NNN.
- P4-QR-003: Each quality requirement specifies a measurable condition (pass/fail criterion).
- P4-QR-004: QR-001 through QR-004 cover structural completeness (all required sections present).
- P4-QR-005: QR-005 through QR-008 cover content correctness (no placeholder leakage, all references resolved).
- P4-QR-006: QR-009 through QR-012 cover format compliance (ASCII-only, YAML frontmatter present, section headings correct).
- P4-QR-007: No quality requirement is vague (e.g., "must work properly" is forbidden).
- P4-QR-008: Quality requirements are verifiable by automated or deterministic review.


## Criteria for Phase 5 (Artifact Contract)

This phase defines the artifact keys, filename patterns, and registry constraints for the target workflow.

### Key Uniqueness

- P5-KU-001: Every artifact key declared in the workflow is globally unique within the target workflow.
- P5-KU-002: Artifact keys follow the naming convention: uppercase letters, digits, and underscores only.
- P5-KU-003: Artifact keys end with the _FILE suffix when they represent file artifacts.
- P5-KU-004: No artifact key matches any builder-owned artifact key.
- P5-KU-005: The total number of artifact keys is consistent with the number of outputs declared across all 8 phases.

### Filename Patterns

- P5-FP-001: Each file artifact key has an associated filename pattern.
- P5-FP-002: Filename patterns use the format {KEY_NAME}-{seq}.md or {KEY_NAME}-{timestamp}.ext as appropriate.
- P5-FP-003: All filename patterns produce unique filenames when expanded with valid parameters.
- P5-FP-004: No filename pattern produces a name that collides with builder-owned filenames.
- P5-FP-005: The target standard filename matches the value declared in Phase 1.

### No Global Registry Conflicts

- P5-GRC-001: No artifact key in the target workflow conflicts with any key in the builder workflow.
- P5-GRC-002: No filename pattern in the target workflow produces output in the builder workflow output directory.
- P5-GRC-003: The target workflow declares its own artifact registry independently -- it does not extend or modify the builder registry.
- P5-GRC-004: Cross-references between artifacts use only keys declared within the target workflow.


## Criteria for Phase 6 (Step Sequence)

This phase defines the workflow steps, their routing, and artifact delivery flow.

### Routing Valid

- P6-RV-001: Every step declares at least one valid routing outcome (onsuccess or on_reject_refine).
- P6-RV-002: Routing targets reference steps that exist within the workflow definition.
- P6-RV-003: No step routes to itself (no self-loops unless explicitly designed as a refinement loop with a maximum iteration count).
- P6-RV-004: The workflow has a defined start step and at least one terminal step.
- P6-RV-005: Every non-terminal step has an exit path (no dead-end steps).
- P6-RV-006: Refinement loops (on_reject_refine) include a maximum iteration limit to prevent infinite loops.

### No Dangling References

- P6-DR-001: Every input artifact declared in a step prompt matches an artifact key produced by a preceding step.
- P6-DR-002: Every output artifact declared in a step is consumed by at least one subsequent step or is a final deliverable.
- P6-DR-003: No step references an artifact key that is not declared in the workflow definition.
- P6-DR-004: The workflow.toml [step.artifacts] section for each step lists only keys that exist in the artifact contract.

### Output Delivery Matches Spec Type

- P6-OD-001: If the output type is documented_versioned, the step sequence produces a COMPOSITION_STANDARD.md (or equivalent standard document) as a final deliverable.
- P6-OD-002: If the output type is documented_versioned, the standard document contains all 3 layers (component schema, composition format, resolved output).
- P6-OD-003: If the output type is direct, the step sequence produces final deliverables directly without an intermediate standard document.
- P6-OD-004: All final deliverables are listed in the workflow definition as terminal artifacts.


## Criteria for Phase 7 (Runtime Standard)

This phase consolidates all previous phases into a single runtime standard document (the target COMPOSITION_STANDARD.md).

### All Phases Consolidated

- P7-AC-001: The runtime standard document contains content from all 8 phases.
- P7-AC-002: Phase 1 identity information appears in the standard frontmatter.
- P7-AC-003: Phase 2 component schema appears as Layer 1 content.
- P7-AC-004: Phase 3 composition format appears as Layer 2 content.
- P7-AC-005: Phase 4 output format appears as Layer 3 content.
- P7-AC-006: Phase 5 artifact contract is referenced or embedded in the standard.
- P7-AC-007: Phase 6 step sequence is consistent with the standard structure.
- P7-AC-008: Phase 8 operational details are consistent with the standard.

### Identity Correct

- P7-IC-001: The standard document frontmatter contains the target workflow name (not the builder name).
- P7-IC-002: The standard document frontmatter contains the target standard name (not the builder standard name).
- P7-IC-003: The standard document frontmatter contains the target standard version.
- P7-IC-004: No occurrence of the builder workflow name appears anywhere in the standard document body.
- P7-IC-005: No occurrence of the builder standard name appears anywhere in the standard document body.

### Cross-Phase Consistency

- P7-CPC-001: Component types referenced in Layer 2 match those defined in Layer 1.
- P7-CPC-002: Placeholders referenced in Layer 3 match those defined in Layer 2.
- P7-CPC-003: Validation rules in Layer 1 reference only properties that exist in the schema.
- P7-CPC-004: Resolution rules in Layer 3 resolve only placeholders declared in Layer 2.
- P7-CPC-005: Quality requirements reference only artifacts and sections that exist in the standard.
- P7-CPC-006: The ordering rules in Layer 2 are consistent with the step sequence in Phase 6.


## Criteria for Phase 8 (Operational Workflow)

This phase produces the executable workflow package -- TOML definition, prompt files, action implementations, and context extensions.

### Steps Reference Standard

- P8-SRS-001: Every prompt file in the workflow package references the target standard by its target standard filename.
- P8-SRS-002: No prompt file references the builder standard name or builder standard filename.
- P8-SRS-003: The workflow.toml manifest declares the target workflow name, not the builder name.
- P8-SRS-004: Context extensions reference only artifact keys declared in the target workflow.

### Prompt Files Exist

- P8-PF-001: At least one prompt file exists for each generation step in the workflow.
- P8-PF-002: At least one prompt file exists for each review step in the workflow.
- P8-PF-003: Each prompt file references only declared input artifacts (no undeclared artifact keys).
- P8-PF-004: Each prompt file uses the correct placeholder syntax ({ARTIFACT_KEY}) for all artifact references.
- P8-PF-005: Each prompt file includes a self-validation section that the gatekeeper can verify.
- P8-PF-006: Each prompt file includes a forbidden content section that explicitly excludes builder identity tokens.
- P8-PF-007: Prompt files use ASCII characters only.

### Action Implementations Present

- P8-AI-001: Every action step referenced in the workflow.toml has a corresponding implementation in the actions directory.
- P8-AI-002: Action implementations are valid Python modules with proper imports.
- P8-AI-003: Action implementations do not import or reference builder-specific modules or constants.
- P8-AI-004: Context extensions implement the required path resolution for all declared artifact keys.
- P8-AI-005: Context extensions do not expose builder identity through any API or constant.
- P8-AI-006: The workflow package can be loaded by the agent-runner-v2 engine without errors (valid TOML, valid Python syntax).


## Negative Criteria

These criteria define what MUST NOT appear in any generated artifact. Violation of any negative criterion is an automatic rejection.

### Builder Identity Leakage

- NC-BIL-001: The string "ar_meta_builder_v2" must NOT appear in any generated artifact (prompt, action, standard, TOML, context extension).
- NC-BIL-002: The string "AMB_STANDARD" must NOT appear in any generated artifact.
- NC-BIL-003: The string "AMB-ztctfrhg" (or any job-specific builder identifier) must NOT appear in any generated artifact.
- NC-BIL-004: Filenames referencing the builder workflow must NOT appear in the generated output.
- NC-BIL-005: Comments, docstrings, or documentation in generated code must NOT reference the builder.

### Non-ASCII Content

- NC-NA-001: All generated text files must contain only ASCII characters (code points 0-127).
- NC-NA-002: No em-dashes, curly quotes, or Unicode special characters may appear in generated output.
- NC-NA-003: Section headings must use plain text only -- no Unicode formatting characters.

### Scope Invention

- NC-SI-001: Generated artifacts must not define component types not traceable to the runtime spec.
- NC-SI-002: Generated artifacts must not define validation rules that check conditions not implied by the spec constraints.
- NC-SI-003: Generated artifacts must not add workflow steps that have no traceable purpose in the 8-phase design.
- NC-SI-004: Generated artifacts must not introduce dependencies not declared in the runtime spec or the platform constitution.

### Hardcoded Types

- NC-HT-001: Component type names must not be hardcoded to the builder domain (e.g., no "meta_component", "meta_phase").
- NC-HT-002: Placeholder names must not embed builder-specific terminology.
- NC-HT-003: Artifact key names must reflect the target domain, not the builder domain.
- NC-HT-004: Validation rules must not check for builder-specific patterns or conventions.

### Vague Criteria

- NC-VC-001: No generated prompt, standard, or document may contain criteria phrases like "must work properly", "should be good", or "must be correct" without measurable definition.
- NC-VC-002: Every quality requirement must specify a deterministic pass/fail condition.


## Self-Validation

This section verifies that the test criteria themselves are complete and consistent.

### Coverage of All Spec Sections

- SV-CS-001: The spec "Purpose" section is covered by P1-ID (identity extraction from purpose).
- SV-CS-002: The spec "Input" section is covered by Phase 1 criteria (runtime spec analysis).
- SV-CS-003: The spec "Output" section is covered by Phase 8 criteria (operational workflow package).
- SV-CS-004: The spec "Constraints -- Identity Isolation" is covered by NC-BIL and P7-IC criteria.
- SV-CS-005: The spec "Constraints -- Three-Layer Architecture" is covered by P2 (Layer 1), P3 (Layer 2), P4 (Layer 3), and P7-AC criteria.
- SV-CS-006: The spec "Constraints -- Test-Driven Development" is covered by P1-MTC-003 and P8-PF criteria (generation, review, validation, gatekeeping steps).
- SV-CS-007: The spec "Constraints -- Recursive Capability" is covered by P1-MTC-004.
- SV-CS-008: The spec "Constraints -- Artifact Tracking" is covered by Phase 5 and P6-DR criteria.
- SV-CS-009: The spec "Constraints -- Prompt Quality" is covered by P8-PF criteria.
- SV-CS-010: The spec "Knowledge Requirements" is covered by the combination of all phase criteria (a passing workflow demonstrates all required knowledge).
- SV-CS-011: The spec "Success Criteria" items 1-6 are each mapped:
  - Success Criterion 1 (immediately executable): P6-RV, P8-AI.
  - Success Criterion 2 (valid structured output): P4-OS, P4-QR.
  - Success Criterion 3 (identity isolation): NC-BIL, P7-IC.
  - Success Criterion 4 (three-layer pattern): P2, P3, P4, P7-AC.
  - Success Criterion 5 (comprehensive validation): P2-VR, P4-RR, P4-QR.
  - Success Criterion 6 (recursive capability): P1-MTC-004.
- SV-CS-012: The spec "What NOT to Specify" section is respected -- no criterion mandates exact step names, exact step count, exact artifact key names, exact prompt content, exact routing logic, or exact validation rule content beyond what is structurally required.

### Verifiability by Gatekeeper

- SV-VG-001: Every criterion with a numeric identifier (P1-*, P2-*, P3-*, P4-*, P5-*, P6-*, P7-*, P8-*, NC-*) can be evaluated as PASS or FAIL by a gatekeeper.
- SV-VG-002: No criterion uses subjective language without an objective anchor (e.g., "correct" is always anchored to a specific check like "matches the value declared in Phase 1").
- SV-VG-003: Negative criteria (NC-*) are verifiable by string search and content inspection.
- SV-VG-004: Coverage criteria (SV-CS-*) are verifiable by cross-referencing spec sections to criterion identifiers.
- SV-VG-005: The gatekeeper can produce a pass/fail report by evaluating each criterion against the corresponding artifact.
