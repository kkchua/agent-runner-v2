# Test Criteria -- Target Workflow Design Phases

## Introduction

This document defines the acceptance criteria for all 8 design phases of the target workflow that is generated by the meta-workflow described in bootstrap.spec.md. These criteria apply to the TARGET workflow output -- not the builder itself. Every criterion is designed to be objectively verifiable by a gatekeeper step (LLM review or deterministic validation).

The target workflow is whatever executable workflow package the meta-builder generates from a given runtime spec. All criteria are written in terms of "target workflow_name", "target standard_name", "target standard_version", and "target standard_filename" -- these values come from the runtime spec YAML frontmatter identity section.

Scope:
- 8 design phases (Phases 1-8), each with phase-specific acceptance criteria
- Cross-phase invariants (meta-test-criteria) that ALL gatekeepers must check
- Negative criteria defining what MUST NOT appear in generated output
- Self-validation criteria ensuring complete coverage

These criteria are accumulated into a single TEST_CRITERIA_FILE and injected into ALL subsequent gatekeep prompts (Phases 2-8) as the baseline for pass/fail decisions.

Target workflow output type: documented_versioned (as declared in the runtime spec frontmatter).

Applicable invariants (the 4 meta-test-criteria):
- INV-1: Identity Isolation -- the builder identity must never leak into generated output. The target workflow uses the spec identity exclusively.
- INV-2: Three-Layer Architecture -- Layer 1 (component definitions), Layer 2 (composition format), and Layer 3 (resolved outputs) must each be present and distinct.
- INV-3: Test-Driven Development -- each phase must include generation, review, validation, and gatekeeping steps.
- INV-4: Recursive Capability -- the generated workflow must be capable of bootstrapping the next version of itself given its own output spec as input.

- TC-P3-004: Each binding rule specifies whether the binding is required or optional.
- TC-P3-005: Binding rules are bidirectionally consistent -- if type A binds to type B, then type B rule acknowledges the relationship.
- TC-P3-006: The binding chain forms a valid dependency graph with no cycles.
- TC-P3-007: Each binding rule specifies the source phase that produces the component and the consuming phases that depend on it.

- TC-P3-008: The composition_format defines a mechanism for overriding default binding behavior.
- TC-P3-009: The override mechanism specifies the syntax for declaring an override.

- TC-P3-012: The override mechanism is documented with at least one example.
- TC-P3-013: The override mechanism specifies that meta-test-criteria from Phase 1 are injected into ALL subsequent gatekeep prompts.

### 7 Placeholders

- TC-P3-015: Each placeholder uses the syntax {PLACEHOLDER_NAME} with uppercase alphanumeric and underscore characters.
- TC-P3-016: Each placeholder has a documented resolution source (which component property or runtime value fills it).
- TC-P3-017: Placeholder names are unique across the composition format (no duplicates).
- TC-P3-018: At least one placeholder resolves from the runtime spec frontmatter (e.g., {WORKFLOW_SPEC_FILE}).

- TC-P3-020: No placeholder name collides with any artifact key declared in Phase 5.
- TC-P3-021: All 7 placeholders are marked as required (no optional placeholders).
- TC-P3-022: Each placeholder has a documented data source mapping indicating where the value comes from (spec frontmatter, context, or runtime).

### Ordering Rules

- TC-P3-023: The composition_format specifies the order in which components are resolved.
- TC-P3-024: Ordering rules prevent circular dependencies between component types.
- TC-P3-025: The ordering is deterministic -- given the same input, the same order is always produced.
- TC-P3-026: The ordering rules account for all component types defined in Phase 2.
- TC-P3-027: The composition_format specifies that phases execute in sequential order (Phase 1 through Phase 8).
- TC-P3-028: Each phase output is available as input to all subsequent phases via the binding chain.

## Criteria for Phase 6 (Step Sequence)

Phase 6 produces the step_sequence component. This defines the workflow steps, their routing, and artifact delivery flow.

### Routing Valid

- TC-P6-001: Every step declares at least one valid routing outcome (onsuccess or on_reject_refine).
- TC-P6-002: Every step in the sequence has a valid onsuccess routing to the next step (or terminal state for the last step).
- TC-P6-003: Routing targets reference steps that exist within the workflow definition (no forward references to undefined steps).
- TC-P6-004: No step routes to itself (no self-loops unless explicitly designed as a refinement loop with a maximum iteration count).
- TC-P6-005: The workflow has a defined start step and at least one terminal step.
- TC-P6-006: Every non-terminal step has an exit path (no dead-end steps).
- TC-P6-007: Refinement loops (on_reject_refine) include a maximum iteration limit to prevent infinite loops.
- TC-P6-008: Steps with review loops have valid on_reject_refine routing to the corresponding refine step.
- TC-P6-009: Refine steps route back to their corresponding review step, forming a valid refinement loop.

### No Dangling References

- TC-P6-010: Every input artifact declared in a step prompt matches an artifact key produced by a preceding step or declared as a workflow input.
- TC-P6-011: Every output artifact declared in a step is consumed by at least one subsequent step or is a final deliverable.
- TC-P6-012: No step references an artifact key that is not declared in the workflow definition.
- TC-P6-013: The workflow.toml [step.artifacts] section for each step lists only keys that exist in the artifact contract.
- TC-P6-014: Every required_input artifact key referenced by a step is either produced by a prior step or declared as a workflow input.
- TC-P6-015: Every produced artifact key is consumed by at least one subsequent step or is a declared workflow output.

### Output Delivery Matches Spec Type

- TC-P6-016: If the output type is documented_versioned, the step sequence produces a COMPOSITION_STANDARD.md (or equivalent standard document) as a final deliverable.
- TC-P6-017: If the output type is documented_versioned, the standard document contains all 3 layers (component schema, composition format, resolved output).
- TC-P6-018: If the output type is documented_versioned, the step sequence includes review steps, refine steps, approval gates, and promotion/archival steps.
- TC-P6-019: If the output type is direct, the step sequence produces final deliverables directly without an intermediate standard document.
- TC-P6-020: If the output type is direct, the step sequence does NOT include review/approval gates and delivers output directly.
- TC-P6-021: All final deliverables are listed in the workflow definition as terminal artifacts.
- TC-P6-022: The delivery_mechanism object in the step_sequence matches the output_type declared in the spec.

### Step Type Correctness

- TC-P6-023: Each step has a declared type: "prompt" for LLM-driven steps or "action" for deterministic Python steps.
- TC-P6-024: Prompt-driven steps reference a prompt file path that exists in the prompts/ directory.
- TC-P6-025: Action steps reference an action function name that is implemented in actions.py.
- TC-P6-026: Each step declares its role_policy for coder assignment (e.g., architect_standard, reviewer_standard).

## Negative Criteria

These criteria define what MUST NOT appear in any generated artifact. Violation of any negative criterion is an automatic rejection.

### Builder Identity Leakage

- NC-BIL-001: The string "ar_meta_builder_v2" must NOT appear in any generated artifact (prompt, action, standard, TOML, context extension) as the target workflow name.
- NC-BIL-002: The string "AMB_STANDARD" must NOT appear in any generated artifact as the target standard name.
- NC-BIL-003: The string "AMB-zlk6p8rh" (or any job-specific builder identifier) must NOT appear in any generated artifact.
- NC-BIL-004: Filenames referencing the builder workflow must NOT appear in the generated output.
- NC-BIL-005: Comments, docstrings, or documentation in generated code must NOT reference the builder as if it were the target workflow.
- NC-BIL-006: The generated workflow.toml MUST NOT contain the builder workflow_name as its name field.
- NC-BIL-007: The generated context_extensions.py MUST NOT contain class names derived from the builder workflow_name.
- NC-BIL-008: The generated README.md MUST NOT describe the builder -- it must describe the target workflow.

### Non-ASCII Content

- NC-NA-001: All generated text files must contain only ASCII characters (code points 0-127).
- NC-NA-002: No em-dashes, curly quotes, or Unicode special characters may appear in generated output.
- NC-NA-003: Section headings must use plain text only -- no Unicode formatting characters.

### Scope Invention

- NC-SI-001: Generated artifacts must not define component types not traceable to the runtime spec.
- NC-SI-002: Generated artifacts must not define validation rules that check conditions not implied by the spec constraints.
- NC-SI-003: Generated artifacts must not add workflow steps that have no traceable purpose in the 8-phase design.
- NC-SI-004: Generated artifacts must not introduce dependencies not declared in the runtime spec or the platform constitution.

### Hardcoded Types

- NC-HT-001: Component type names must not be hardcoded to the builder domain (e.g., no "meta_component", "meta_phase").
- NC-HT-002: Placeholder names must not embed builder-specific terminology.
- NC-HT-003: Artifact key names must reflect the target domain, not the builder domain.
- NC-HT-004: Validation rules must not check for builder-specific patterns or conventions.

### Vague Criteria

- NC-VC-001: No generated prompt, standard, or document may contain criteria phrases like "must work properly", "should be good", or "must be correct" without measurable definition.
- NC-VC-002: Every quality requirement must specify a deterministic pass/fail condition.

### Structural Leakage

- NC-SL-001: The generated workflow MUST NOT copy the builder phase structure unless the target spec independently requires that structure.
- NC-SL-002: The generated workflow MUST NOT hardcode the builder component types -- component types must be derived from the target spec.
- NC-SL-003: The generated workflow MUST NOT assume output_type -- it must check the spec declaration.
- NC-SL-004: The generated workflow MUST NOT contain hardcoded file paths from the builder environment.
