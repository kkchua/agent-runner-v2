# System Context: agent-runner-v2

## Context Statement

`agent-runner-v2` is a standalone workflow runner extracted from UKBE (UK Build Engine) that orchestrates AI-Driven SDLC workflows with human approval gates. It manages the full lifecycle of software development artifacts from requirements through validation, invoking LLM coders for generative steps and deterministic Python actions for validation and file operations.

The system operates as a CLI-first tool with optional daemon-based backend worker mode for continuous operation. It follows a layered architecture where Layer 1 generates ecosystem governance, Layer 2 produces repo master docs, and Layer 3+ executes SDLC-specific workflows.

## Primary Context Elements

### System Boundaries

| Boundary | Direction | Description |
|----------|-----------|-------------|
| LLM Coders | Inbound | External AI processes (OpenCode, Claude, etc.) invoked for generative steps |
| Backend API | Inbound | Optional backend server providing job queue and state management |
| Filesystem | Internal | All workflow artifacts, job state, and configuration are file-based |
| Git Repository | Internal | Source code under version control; workflows must not mutate code |
| Pushover API | Outbound | Optional notification service for step completion alerts |

### Execution Modes

1. **Manual Mode**: Direct CLI invocation via `run_agent.py` for interactive workflow execution
2. **Daemon Mode**: Background worker polling backend API for job assignments
3. **Hybrid Mode**: Daemon spawns manual-mode subprocess for actual execution (unified path)

### Core Data Flows

```
Workflow TOML → WorkflowBundle → Step Execution → Coder/Action → Meta.json Sidecar → Job State Update
                                                                                      ↓
                                                                           Notification (optional)
```

### Primary Actors

| Actor | Role | Interaction Point |
|-------|------|-------------------|
| Developer | Implements workflows, runs tests | CLI, batch files, pytest |
| Operator | Monitors daemon, manages jobs | `run-daemon.bat`, job folders |
| LLM Coder | Generates artifacts | External process invocation via `coder_adapters.py` |
| Backend Server | Queues jobs, persists state | HTTP API via `backend_client.py` |

| Location | Purpose | Lifecycle |

| `.ukbe-runner/jobs/<job_id>/` | Job state, step directories, meta.json sidecars | Per-job, cleaned after completion |

### Integration Points

| Integration | Type | Protocol | Description |
|-------------|------|----------|-------------|
| Backend API | External | HTTP/JSON | Job queue, state persistence, cleanup endpoints |
| LLM Coders | External | Subprocess/stdio | Prompt in, meta.json result out |
| Pushover | External | HTTP POST | Notification delivery |
| Git | External | CLI | Repository state queries (no mutations) |
| pytest | Internal | CLI | Unit and integration test execution |

### Constraints and Assumptions

- **Zero source mutation**: Bootstrap workflows must not alter code, only docs
- **Absolute paths required**: All placeholder paths must be absolute for Windows compatibility
- **File-based state**: No database; job state persisted as JSON files
- **Sidecar contract**: Coder results must be reported via `meta.json` sidecar
- **Layer dependency**: Layer 2 requires Layer 1; Layer 3+ requires Layer 2
