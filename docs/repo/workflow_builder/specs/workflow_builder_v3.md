# Composition System Specification: Workflow Builder v3

> **Domain:** Meta-meta workflow builder
> **Input to:** workflow_builder_v2 (for initial generation) or workflow_builder_v3 (for self-bootstrapping)
> **Standard:** BASE_COMPOSITION_STANDARD.md (to be generated by v3)

---

## 1. Domain Overview

**Domain name:** `workflow_builder`
**Label:** Workflow Builder v3
**Job prefix:** `WBUILD3`
**Description:** Meta-meta builder that generates meta builders (agents). Each generated meta builder is itself a composition system with its own composition standard, enabling extensibility and self-bootstrapping.

### 1.1 Purpose

Workflow Builder v3 is a **meta-meta builder** — it builds meta builders (agents) that can produce different output variances based on composition specs. Unlike v2 which generates domain-specific workflows (e.g., video_campaign_manuscript), v3 generates **meta builders** that are themselves composition systems.

**Key Innovation:** Every workflow generated by v3 is a **self-describing composition system**:
1. **The Standards** — A composition standard (COMPOSITION_STANDARD.md) that defines the schema for that builder's domain
2. **The Spec** — A meta composition spec that defines component types, composition formats, and output formats
3. **The Execution Workflow** — The actual workflow package (workflow.toml, prompts, actions) that understands its own Standards and Spec

**Multi-Level Architecture:**
```
Level 0: v3 builder (creates agents)
Level 1: Agent Workflow Spec (composition standard)
Level 2: User Workflows (composition specs)
Level 3: Agent execution outputs
```

**Trigger:** User provides a composition system spec describing a meta builder (e.g., "creative_workflow_builder", "data_processor_builder").

**Outcome:** Three outputs:
1. `Standards/COMPOSITION_STANDARD.md` — The composition standard for the generated meta builder
2. `Specs/{name}.md` — The meta composition spec (component types, composition formats, output formats)
3. Workflow package — The executable workflow (workflow.toml, prompts/, actions.py, context_extensions.py, README.md)

### 1.2 Domain Context

The workflow builder sits at the top of the workflow creation hierarchy. It is a **meta-meta-workflow**: a workflow that builds workflows that build deliverables. The builder itself follows the composition system standard, making it self-describing and self-bootstrapping.

**Analogy to Agentic Platforms (JiMeng/DREAMAI):**
- **v3 builder** = creates the "agent" (meta workflow builder)
- **Agent workflow spec** = the composition standard (defines what the agent can do)
- **User workflows** = composition specs (specific configurations for specific use cases)
- **Agent execution** = produces output variances based on compositions

**Self-Bootstrapping:**
- v3's `Specs/` folder contains `workflow_builder_v3.md`
- Feed that spec into v3 → generates v4
- Each version has its own `Standards/` and `Specs/` folders

**Folder Structure:**
```
{builder_name}/
├── Standards/
│   └── COMPOSITION_STANDARD.md (consistent filename, always)
├── Specs/
│   └── {user_provided_specs}.md
└── workflow.toml, prompts/, actions.py, context_extensions.py, README.md
```

### 1.3 Key Differences from v2

| Aspect | v2 | v3 |
|--------|----|----|
| Component knowledge | Hardcoded in prompts (5 types) | **Dynamic** — reads from standard |
| Output | Domain-specific workflow | **Meta builder** (with Standards + Spec + workflow) |
| Extensibility | Adding new component type = rewrite v2 | **Standard is the template** — new components auto-handled |
| Self-bootstrapping | Can describe itself as composition system | **Full self-bootstrapping** — can generate v4 |
| Folder structure | Flat (all files in one directory) | **Organized** (Standards/, Specs/, workflow files) |

## 2. Component Schema (Layer 1)

### 2.1 Component Types

In this composition system, "components" are the structural building blocks of meta builders. Each component type represents a distinct aspect of meta builder structure.

| Component Type | Purpose | Required? | Cardinality |
|---|---|---|---|
| `step_definition` | A workflow step with type, purpose, inputs, outputs | Yes | Ordered list (N steps per workflow) |
| `role_policy` | Coder role assignment for a step | Yes | Singleton per step |
| `routing_pattern` | How steps connect (success, reject, refine) | Yes | Singleton per step |
| `prompt_pattern` | Prompt structure elements (self-critic, validation, etc.) | No | Unordered set per prompt-driven step |
| `artifact_contract` | Input/output artifact definitions | Yes | Unordered set per workflow |
| `composition_standard` | The composition standard schema for the generated meta builder | Yes | Singleton (defines the base standard) |
| `output_variance` | A specific output configuration the meta builder can produce | No | Unordered set (defines different output types) |
| `domain_spec` | A user-provided spec that the meta builder processes | No | Unordered set (defines input spec types) |

### 2.2 Common Properties

All components share these properties:

| Property | Type | Required | Description |
|---|---|---|---|
| `component_id` | string | Yes | Unique identifier (format: `{type}-{name}-{seq}`) |
| `component_type` | enum | Yes | One of the 8 types in 2.1 |
| `name` | string | Yes | Human-readable display name |
| `version` | string | Yes | Semantic version (MAJOR.MINOR.PATCH) |
| `description` | string | Yes | What this component does |

### 2.3 Type-Specific Properties

#### Type: step_definition

| Property | Type | Required | Description | Example |
|---|---|---|---|---|
| `step_name` | string | Yes | Lowercase with underscores | `"generate_component_schema"` |
| `step_type` | enum | Yes | Values: prompt, action | `"prompt"` |
| `purpose` | string | Yes | What this step achieves | `"Generate the component schema for Layer 1"` |
| `required_inputs` | array | No | Artifact keys this step reads | `["WORKFLOW_SPEC_FILE", "TEST_CRITERIA_FILE"]` |
| `produces` | array | Yes | Artifact keys this step writes | `["COMPONENT_SCHEMA_FILE"]` |

#### Type: role_policy

| Property | Type | Required | Description | Example |

#### Type: routing_pattern

| `description` | string | Yes | What this artifact contains | `"Component schema for Layer 1"` |

| `required` | boolean | Yes | Whether this artifact is required | `true` |
| `produced_by` | string | No | Step that produces this artifact | `"generate_component_schema"` |

#### Type: composition_standard

| Property | Type | Required | Description | Example |
|---|---|---|---|---|
| `standard_name` | string | Yes | Name of the standard | `"BASE_COMPOSITION_STANDARD"` |
| `standard_version` | string | Yes | Version of the standard | `"1.0.0"` |

| `component_requirements` | array | Yes | Which components are required for this variance | `["step_definition", "role_policy", "routing_pattern"]` |
| `output_files` | array | Yes | Files produced by this variance | `["workflow.toml", "prompts/*.txt", "context_extensions.py"]` |

#### Type: domain_spec

| Property | Type | Required | Description | Example |
|---|---|---|---|---|
| `spec_type` | string | Yes | Type of spec this builder accepts | `"creative_workflow_spec"` |
| `spec_version_range` | string | Yes | Compatible spec versions | `"1.0.0 - 3.99.99"` |
| `required_sections` | array | Yes | Sections the spec must have | `["Domain Overview", "Component Schema", "Composition Format", "Output Format"]` |
| `example_specs` | array | No | Example spec filenames | `["world_building_v1.md", "story_design_v1.md"]` |

### 2.4 Component File Format

Components are not stored as individual files. They are defined inline in the workflow composition (Layer 2) and materialized as workflow.toml sections, prompt files, and Python code.

### 2.5 Validation Rules

- **Step name uniqueness:** No duplicate step_name values within a workflow
- **Valid step_type:** Must be one of: prompt, action
- **Valid policy_name:** Must be one of the 5 role policies
- **Artifact key format:** UPPER_SNAKE_CASE, _FILE suffix for documents
- **Routing completeness:** Every step must have onsuccess; review/refine steps must have on_reject_refine
- **Prompt pattern completeness:** Every prompt-driven step must have self_critic and self_validation patterns
- **Artifact flow integrity:** Every step's required_inputs must reference an artifact produced by a prior step or an input artifact
- **Composition standard completeness:** The composition_standard component must define all 3 layers (Component Schema, Composition Format, Output Format)
- **Output variance feasibility:** Each output_variance must have a valid combination of component_requirements

## 3. Composition Format (Layer 2)

### 3.1 Composition Structure

A meta builder composition is a declarative definition with this structure:

| Field | Type | Required | Description |
|---|---|---|---|
| `builder_name` | string | Yes | Unique builder identifier |
| `builder_label` | string | Yes | Human-readable display name |
| `job_prefix` | string | Yes | 4-6 character prefix for job IDs |
| `builder_purpose` | string | Yes | What problem this builder solves |
| `workflow_pattern` | enum | Yes | Pattern type (see 3.1.1) |
| `step_bindings` | array | Yes | Ordered list of step_definitions |
| `artifact_bindings` | object | Yes | Input and output artifact contracts |
| `composition_standard_binding` | object | Yes | The composition standard this builder generates (see 3.6) |
| `output_variances` | array | No | List of output variances this builder can produce (see 3.7) |

#### 3.1.1 Workflow Patterns

| Pattern | Description | Steps |
|---|---|---|
| `action_only` | All steps are deterministic Python operations | validate → publish → init → sync → stepCompletion |
| `prompt_driven` | LLM generates documents with review/refine loop | generate → review → [refine → review] → promote → stepCompletion |
| `mixed` | Combination of prompt and action steps | generate → review → refine → validate → promote → stepCompletion |
| `gatekeeper_pipeline` | Multi-phase with QC gates after each phase | generate → gatekeep → ... → generate_pkg → gatekeep → validate → review → [refine] → promote → stepCompletion |
| `meta_workflow_builder` | Workflow that builds workflows (this pattern) | generate_test_criteria → review → [refine] → ... → generate_package → validate → gatekeep → review → [refine] → promote → stepCompletion |
| `meta_meta_builder` | **NEW in v3** — Workflow that builds meta builders | generate_test_criteria → review → [refine] → ... → generate_composition_standard → generate_meta_spec → generate_package → validate → gatekeep → review → [refine] → promote → stepCompletion |

### 3.2 Binding Rules

| Binding Name | Component Type | Cardinality | Required? | Description |
|---|---|---|---|---|
| `steps` | step_definition | Ordered list | Yes | Workflow step sequence |
| `roles` | role_policy | Singleton per step | Yes | Each step must have a role |
| `routing` | routing_pattern | Singleton per step | Yes | Each step must have routing |
| `prompts` | prompt_pattern | Unordered set per prompt step | No | Prompt structure elements |
| `artifacts` | artifact_contract | Unordered set | Yes | Input/output artifact definitions |
| `standard` | composition_standard | Singleton | Yes | The composition standard this builder generates |
| `variances` | output_variance | Unordered set | No | Output variances this builder can produce |
| `domain_specs` | domain_spec | Unordered set | No | Input spec types this builder accepts |

### 3.3 Override Mechanism

```yaml
step_bindings:
  - step_name: "generate_component_schema"
    step_type: "prompt"
    purpose: "Generate the component schema for Layer 1"
    produces: ["COMPONENT_SCHEMA_FILE"]
    role:
      policy_name: "architect_standard"
    routing:
      onsuccess: "gatekeep_component_schema"
    prompt_patterns:
      - pattern_name: "self_critic"
      - pattern_name: "self_validation"
      - pattern_name: "reference_inputs"
```

**Rules:**
- Every step must bind a role_policy
- Every step must bind a routing_pattern
- Prompt-driven steps should bind prompt_patterns (self_critic, self_validation are mandatory)
- Action-driven steps do not bind prompt_patterns

### 3.4 Placeholder Resolution

| Data Source | Fields Provided | Required? |
|---|---|---|
| Input Spec | WORKFLOW_SPEC_FILE, domain_name, job_prefix | Yes |
| Governance | BASE_COMPOSITION_STANDARD, GOVERNANCE_RUNTIME_ROOT | Yes |
| Runtime | job_id, seq, workspace_root | Yes |

**Resolution rules:**
- Placeholders in prompt templates resolved at runtime
- Artifact paths resolved via context_extensions.py
- Governance paths resolved via runtime_context module

```yaml

builder_label: "Creative Workflow Builder"
job_prefix: "CWFBLD"

  - variance_name: "mixed_workflow_with_api"
    variance_description: "A workflow with prompt steps and Agnes API action steps"
    component_requirements: ["step_definition", "role_policy", "routing_pattern", "api_action"]
    output_files: ["workflow.toml", "prompts/*.txt", "actions.py", "context_extensions.py", "README.md", ".env.sample"]
```

### 3.6 Composition Standard Binding (NEW in v3)

The composition_standard_binding defines the composition standard that the generated meta builder will use. This is the **key innovation** of v3 — every generated meta builder has its own composition standard.

**Structure:**
| Field | Type | Required | Description |
|---|---|---|---|
| `standard_name` | string | Yes | Name of the standard (e.g., "CREATIVE_WORKFLOW_STANDARD") |
| `standard_version` | string | Yes | Version of the standard |
| `component_types_defined` | array | Yes | List of component types this standard defines |
| `schema_sections` | array | Yes | Sections of the schema (Layer 1, Layer 2, Layer 3) |
| `extensibility_model` | string | Yes | How new components can be added |

**Purpose:**
- Defines what the meta builder can build
- Enables extensibility (new component types can be added)
- Makes the meta builder self-describing

### 3.7 Output Variances (NEW in v3)

Output variances define different output configurations the meta builder can produce. This enables the meta builder to produce different types of workflows based on the input spec.

**Structure:**
| Field | Type | Required | Description |
|---|---|---|---|
| `variance_name` | string | Yes | Name of the variance |
| `variance_description` | string | Yes | What this variance produces |
| `component_requirements` | array | Yes | Which components are required for this variance |
| `output_files` | array | Yes | Files produced by this variance |

**Purpose:**
- Enables the meta builder to produce different output types
- Makes the meta builder flexible (can handle different use cases)
- Documents what each variance produces

## 4. Output Format (Layer 3)

### 4.1 Output Structure

The output is a meta builder directory with 3 parts:

| Part | Source | Description |
|---|---|---|
| **Standards/COMPOSITION_STANDARD.md** | composition_standard_binding | The composition standard for the generated meta builder |
| **Specs/{name}.md** | Generated | The meta composition spec (component types, composition formats, output formats) |
| **Workflow package** | step_bindings + routing + artifacts | The executable workflow (workflow.toml, prompts/, actions.py, context_extensions.py, README.md) |

### 4.2 Resolution Rules

- **All step_definitions expanded** into workflow.toml [[step]] sections with [step.artifacts] and [step.coder]
- **All role_policies resolved** to [step.coder] role_policy values
- **All routing_patterns resolved** to onsuccess and [step.on_reject_refine] configurations
- **All prompt_patterns expanded** into prompt template sections
- **Composition standard generated** as Standards/COMPOSITION_STANDARD.md
- **Meta composition spec generated** as Specs/{name}.md
- **Artifact paths resolved** via context_extensions.py register_artifact_keys()

### 4.3 Quality Requirements

- **No dangling step references:** Every onsuccess and on_reject_refine step must exist
- **No dangling artifact references:** Every required_inputs artifact must be produced by a prior step or be an input artifact
- **Complete prompt patterns:** Every prompt-driven step must have self_critic and self_validation sections
- **Valid role assignments:** Every step must have a role_policy
- **Artifact flow integrity:** Can trace each output artifact back to its producing step
- **Composition standard completeness:** The generated COMPOSITION_STANDARD.md must define all 3 layers
- **Output variance feasibility:** Each output_variance must have a valid combination of component_requirements
- **Self-bootstrapping capability:** The generated meta builder should be able to process specs in its domain

### 4.4 Example Output (Skeleton)

```
creative_workflow_builder/
├── Standards/
│   └── COMPOSITION_STANDARD.md          # NEW — The composition standard
├── Specs/
│   └── (user-provided specs go here)
├── workflow.toml                         # Workflow manifest
├── context_extensions.py                 # Artifact key registration
├── actions.py                            # Custom actions
├── prompts/
│   ├── 01_generate_test_criteria.txt
│   ├── 02_review_test_criteria.txt
│   ├── ...
│   └── NN_generate_package.txt
├── README.md                             # Workflow documentation
├── .env.sample                           # Environment variables (if needed)
└── config.json.sample                    # Runtime config (if needed)
```

## 5. Operational Requirements

### 5.1 Workflow Phases

| Phase | Purpose |
|---|---|
| **Foundation (TDD Loop)** | Generate acceptance criteria, review, refine (universal for all workflows) |
| **Component Schema** | Generate component schema for Layer 1, gatekeep |
| **Composition Format** | Generate composition format for Layer 2, gatekeep |
| **Output Format** | Generate output format for Layer 3, gatekeep |
| **Operational Workflow** | Generate operational workflow design, gatekeep |
| **Composition Standard** | **NEW in v3** — Generate the composition standard for the meta builder |
| **Meta Composition Spec** | **NEW in v3** — Generate the meta composition spec |
| **Package Assembly** | Generate workflow package, validate, gatekeep, review, refine |
| **Promotion** | Promote workflow package + Standards + Spec to target directory |

### 5.2 Input Artifacts

| Artifact Key | Description | Required? |
|---|---|---|
| `WORKFLOW_SPEC_FILE` | Composition system specification (input to the builder) | Yes |

### 5.3 Output Artifacts

| Artifact Key | Description | Produced By |
|---|---|---|
| `TEST_CRITERIA_FILE` | Acceptance criteria for the composition system | generate_test_criteria |
| `REVIEW_TEST_CRITERIA_FILE` | Review of acceptance criteria | review_test_criteria |
| `COMPONENT_SCHEMA_FILE` | Component schema for Layer 1 | generate_component_schema |
| `GATEKEEP_COMPONENT_SCHEMA_FILE` | Gatekeep review of component schema | gatekeep_component_schema |

### 5.4 Action Steps

Two custom action steps:

1. **validate_package_deterministic** — Deterministic validation of the generated workflow package. Checks:
   - workflow.toml syntax and structure
   - Step references (onsuccess, on_reject_refine) exist
   - Artifact references (required_inputs, produces) are valid
   - Role policies are valid
   - Prompt files exist for all prompt-driven steps
   - **NEW in v3:** Composition standard file exists and is well-formed
   - **NEW in v3:** Meta composition spec file exists and is well-formed

2. **promote_workflow_package** — Promote the generated workflow package to the workflows/ directory. Copies:
   - workflow.toml, context_extensions.py, actions.py, prompts/, README.md
   - .env.sample, config.json.sample (if present)
   - **NEW in v3:** Standards/COMPOSITION_STANDARD.md
   - **NEW in v3:** Specs/ directory (if present)

### 5.5 Domain-Specific Requirements

- **Self-bootstrapping:** The workflow builder should be able to process its own composition spec to generate the next version
- **Three outputs:** Every generated meta builder must include Standards/COMPOSITION_STANDARD.md, Specs/{name}.md, and the workflow package
- **Dynamic component discovery:** The meta builder should read its composition standard dynamically, not hardcode component types
- **Output variances:** The meta builder should be able to produce different output types based on the input spec
- **Folder-based domain separation:** Each meta builder has its own folder with Standards/ and Specs/ subdirectories
- **Consistent standard filename:** The composition standard is always named COMPOSITION_STANDARD.md
- **TDD loop universal:** All workflows must start with generate_test_criteria → review → refine (TDD loop)
- **Gatekeeper pattern:** Meta-workflows must have gatekeeper steps after each major phase
- **Action reuse:** Check existing reusable actions before generating custom ones
- **Self-critic/self-validation:** All prompt-driven steps must include self-critic and self-validation sections
