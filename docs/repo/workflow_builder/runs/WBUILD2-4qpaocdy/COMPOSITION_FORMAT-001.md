# Composition Format: Workflow Builder v3

## Overview

This document defines the composition format (Layer 2) for the workflow_builder domain. The composition format is the declarative assembly layer that specifies how components from the component library (Layer 1) are selected, bound, and configured to produce complete workflow packages. It follows the universal composition pattern defined in COMPOSITION_SYSTEM_STANDARD.md Section 4, specialized for the workflow_builder domain where compositions describe meta-meta builders -- agents that generate other composition systems.

In the three-layer architecture, compositions sit between the component library and the resolved outputs. Components define WHAT the building blocks are (step definitions, role policies, routing patterns, prompt patterns, artifact contracts, composition standards, output variances, and domain specifications). Compositions define HOW those building blocks are assembled into a specific meta builder (which components, in what order, with what overrides, and resolved against what data sources). Outputs (Layer 3) are the result of expanding all references, applying overrides, and filling all placeholders.

The workflow_builder domain produces compositions that describe meta-meta builders. Each composition defines a complete workflow package: its steps, roles, routing, prompt structure, artifact contracts, composition standard binding, and output variances. The domain uses 8 component types, 8 binding rules, and 6 workflow patterns, producing three deliverables per generated builder: a Standards/COMPOSITION_STANDARD.md, a Specs/ directory for user-provided specs, and an executable workflow package.

## Composition Structure

The composition format follows the universal composition pattern from COMPOSITION_SYSTEM_STANDARD.md Section 4. Every composition is a YAML document with a fixed set of top-level fields. The universal pattern maps to domain-specific field names for the workflow_builder domain:

| Universal Field | Domain Field | Type | Required | Description |
|---|---|---|---|---|
| composition_id | builder_name | string | Yes | Unique builder identifier. Format: lowercase_with_underscores (e.g., "creative_workflow_builder") |
| name | builder_label | string | Yes | Human-readable display name (e.g., "Creative Workflow Builder") |
| target_metadata | job_prefix | string | Yes | 4-6 character prefix for job IDs generated by this builder (e.g., "CWFBLD") |
| target_metadata | builder_purpose | string | Yes | What problem this builder solves (e.g., "Generates creative media workflows from agent-md files") |
| target_metadata | workflow_pattern | enum | Yes | The workflow pattern type. Must be one of the 6 defined patterns (see table below) |
| component_bindings | step_bindings | array | Yes | Ordered list of step_definition components |
| component_bindings | artifact_bindings | object | Yes | Input and output artifact contract definitions |
| component_bindings | composition_standard_binding | object | Yes | The composition standard this builder generates (v3 innovation) |
| component_bindings | output_variances | array | No | List of output variances this builder can produce |
| component_bindings | domain_specs | array | No | Input specification types this builder accepts |

### Field Definitions

#### builder_name (string, required)

Unique identifier for the builder. Must be lowercase_with_underscores. Serves as the composition_id in the universal pattern. This identifier is used in file paths, directory names, and cross-references.

#### builder_label (string, required)

Human-readable display name for the builder. Shown in UIs, documentation, and logs. No format constraints beyond being a non-empty string.

#### job_prefix (string, required)

A 4-6 character uppercase prefix used to generate job IDs for runs of this builder. Format: uppercase letters only (e.g., "WBUILD", "CWFBLD"). This prefix appears in artifact filenames and progress tracking.

#### builder_purpose (string, required)

A concise description of what problem this builder solves. Must be a non-empty string. This field provides context for downstream workflows and for the builder's own self-documentation.

#### workflow_pattern (enum, required)

The structural pattern that defines the step sequence shape. Must be one of the 6 defined patterns:

| Pattern | Description | Step Sequence Shape |
|---|---|---|
| action_only | All steps are deterministic Python operations | validate -> publish -> init -> sync -> stepCompletion |
| prompt_driven | LLM generates documents with review/refine loop | generate -> review -> [refine -> review] -> promote -> stepCompletion |
| mixed | Combination of prompt and action steps | generate -> review -> refine -> validate -> promote -> stepCompletion |
| gatekeeper_pipeline | Multi-phase with QC gates after each phase | generate -> gatekeep -> ... -> generate_pkg -> gatekeep -> validate -> review -> [refine] -> promote -> stepCompletion |
| meta_workflow_builder | Workflow that builds workflows | generate_test_criteria -> review -> [refine] -> ... -> generate_package -> validate -> gatekeep -> review -> [refine] -> promote -> stepCompletion |
| meta_meta_builder | Workflow that builds meta builders (NEW in v3) | generate_test_criteria -> review -> [refine] -> ... -> generate_composition_standard -> generate_meta_spec -> generate_package -> validate -> gatekeep -> review -> [refine] -> promote -> stepCompletion |

#### step_bindings (array, required)

An ordered list of step_definition component bindings. Each entry references a step_definition component by component_id and may include inline overrides for role, routing, and prompt_patterns. The ordering defines the execution sequence of the workflow.

#### artifact_bindings (object, required)

An object containing two sub-arrays: input_artifacts and output_artifacts. Each artifact is an artifact_contract component reference with optional overrides.

#### composition_standard_binding (object, required)

A singleton binding that defines the composition standard the generated meta builder will use. This is the key v3 innovation -- every generated meta builder has its own composition standard that defines its component types, composition format, and output format across the 3-layer architecture.

#### output_variances (array, optional)

An unordered list of output_variance component references. Each variance defines a different output configuration the meta builder can produce based on the input specification.

#### domain_specs (array, optional)

An unordered list of domain_spec component references. Each spec defines a type of user-provided specification that the meta builder can process.

### Complete Structure Example

```yaml
builder_name: "creative_workflow_builder"
builder_label: "Creative Workflow Builder"
job_prefix: "CWFBLD"
builder_purpose: "Generates creative media workflows from agent-md files"
workflow_pattern: "meta_meta_builder"

step_bindings:
  - component_id: "step-generate-test-criteria-001"
    overrides:
      produces: ["TEST_CRITERIA_FILE"]
    # ... more steps ...

artifact_bindings:
  input_artifacts:
    - component_id: "artifact-workflow-spec-file-001"
  output_artifacts:
    - component_id: "artifact-composition-standard-file-001"
    # ... more artifacts ...

composition_standard_binding:
  component_id: "standard-base-composition-001"
  overrides:
    standard_name: "CREATIVE_WORKFLOW_STANDARD"
    component_types_defined:
      - "agent_md_analysis"
      - "prompt_template"
      - "api_action"

output_variances:
  - component_id: "variance-prompt-only-001"
  - component_id: "variance-mixed-with-api-001"

domain_specs:
  - component_id: "domainspec-creative-workflow-001"
```

## Component Bindings

Component bindings define how components from the library are assembled into a composition. The workflow_builder domain defines 8 binding rules, one per component type. Each binding rule specifies the component type, cardinality, and required/optional status.

### Binding Rules

| Binding Name | Component Type | Cardinality | Required? | Description |
|---|---|---|---|---|
| steps | step_definition | Ordered list (N items) | Yes | Workflow step sequence. Defines the execution order of all steps in the workflow. |
| roles | role_policy | Singleton per step | Yes | Each step must bind exactly one role_policy. Bound inline within the step binding. |
| routing | routing_pattern | Singleton per step | Yes | Each step must bind exactly one routing_pattern. Bound inline within the step binding. |
| prompts | prompt_pattern | Unordered set per prompt-driven step | No | Prompt structure elements bound to prompt-driven steps. Optional for action steps, but self_critic and self_validation are mandatory for prompt steps. |
| artifacts | artifact_contract | Unordered set per workflow | Yes | Input and output artifact definitions. Split into input_artifacts and output_artifacts sub-bindings. |
| standard | composition_standard | Singleton | Yes | The composition standard this builder generates. Exactly one per composition. |
| variances | output_variance | Unordered set | No | Output variances this builder can produce. Zero or more per composition. |
| domain_specs | domain_spec | Unordered set | No | Input spec types this builder accepts. Zero or more per composition. |

### Reference Pattern

Components are referenced by component_id, NOT copied inline. This is the "references, not duplicates" principle from COMPOSITION_SYSTEM_STANDARD.md Section 4.2. The workflow resolves references against the component library at generation time.

**Correct (reference by ID):**
```yaml
step_bindings:
  - component_id: "step-generate-component-schema-001"
    overrides:
      purpose: "Generate the component schema for Layer 1 of the creative domain"
```

**Incorrect (duplicate inline):**
```yaml
step_bindings:
  - step_name: "generate_component_schema"
    step_type: "prompt"
    purpose: "Generate the component schema for Layer 1"
    # ... full component content duplicated here -- VIOLATES REFERENCE PATTERN
```

### Singleton Bindings

Singleton bindings bind exactly one component per binding slot. In the workflow_builder domain:

- **roles**: Each step binds exactly one role_policy. The role is bound inline within the step binding using the `role` key.
- **routing**: Each step binds exactly one routing_pattern. The routing is bound inline within the step binding using the `routing` key.
- **standard**: The composition binds exactly one composition_standard via composition_standard_binding.

```yaml
# Singleton: role_policy bound inline per step
step_bindings:
  - component_id: "step-generate-component-schema-001"
    role:
      component_id: "role-architect-standard-001"
    routing:
      component_id: "routing-generate-component-schema-001"

# Singleton: composition_standard_binding
composition_standard_binding:
  component_id: "standard-base-composition-001"
```

### Ordered List Bindings

Ordered list bindings contain multiple components in a defined sequence. The order matters and is preserved during resolution.

- **steps**: The step_bindings array is an ordered list. The array index determines execution order. The first element is the first step executed; the last element is the final step (typically stepCompletion).

```yaml
# Ordered list: step_bindings
step_bindings:
  - component_id: "step-generate-test-criteria-001"      # Step 1 (first executed)
  - component_id: "step-review-test-criteria-001"        # Step 2
  - component_id: "step-refine-test-criteria-001"        # Step 3 (conditional)
  - component_id: "step-generate-component-schema-001"   # Step 4
  # ... more steps in order ...
  - component_id: "step-step-completion-001"             # Final step
```

### Unordered Set Bindings

Unordered set bindings contain components without a defined sequence. Order does not affect resolution.

- **prompts**: Prompt patterns bound to a step are unordered. They contribute sections to the prompt template regardless of binding order.
- **artifacts**: Artifact contracts are unordered within input_artifacts and output_artifacts sub-bindings.
- **variances**: Output variances are unordered. Each variance is independently selectable.
- **domain_specs**: Domain specs are unordered. Each spec is independently processable.

```yaml
# Unordered set: prompt_patterns (order does not matter)
prompt_patterns:
  - component_id: "prompt-self-critic-001"
  - component_id: "prompt-self-validation-001"
  - component_id: "prompt-reference-inputs-001"

# Unordered set: output_variances
output_variances:
  - component_id: "variance-prompt-only-001"
  - component_id: "variance-mixed-with-api-001"
```

### Required vs Optional Bindings

| Binding | Required? | Omission Rule |
|---|---|---|
| steps | Yes | A composition without steps is invalid. At minimum, a workflow has one step. |
| roles | Yes | Every step must bind a role_policy. No step may omit its role. |
| routing | Yes | Every step must bind a routing_pattern. No step may omit its routing. |
| prompts | No | Optional for action steps. For prompt steps, self_critic and self_validation are mandatory; other patterns are optional. |
| artifacts | Yes | At minimum, one input artifact (WORKFLOW_SPEC_FILE) must be declared. |
| standard | Yes | Exactly one composition_standard per composition. Cannot be omitted. |
| variances | No | May be omitted if the builder produces only one output type. |
| domain_specs | No | May be omitted if the builder accepts only the default spec type. |

### Composition Standard Binding (v3 Innovation)

The composition_standard_binding is the key v3 innovation. It defines the composition standard that the generated meta builder will use, making every generated meta builder self-describing with its own composition standard.

| Field | Type | Required | Description |
|---|---|---|---|
| component_id | string | Yes | Reference to a composition_standard component |
| overrides.standard_name | string | Yes | Name of the standard (e.g., "CREATIVE_WORKFLOW_STANDARD") |
| overrides.standard_version | string | Yes | Version in MAJOR.MINOR.PATCH format |
| overrides.component_types_defined | array | Yes | List of component types this standard defines |
| overrides.schema_sections | array | Yes | Must contain exactly 3 entries: "Component Schema", "Composition Format", "Output Format" |
| overrides.extensibility_model | string | Yes | How new component types can be added without breaking existing compositions |

```yaml
composition_standard_binding:
  component_id: "standard-base-composition-001"
  overrides:
    standard_name: "CREATIVE_WORKFLOW_STANDARD"
    standard_version: "1.0.0"
    component_types_defined:
      - "agent_md_analysis"
      - "prompt_template"
      - "api_action"
    schema_sections:
      - "Component Schema"
      - "Composition Format"
      - "Output Format"
    extensibility_model: "New component types can be added to support new creative workflow patterns without breaking existing compositions"
```

### Output Variances (v3 Innovation)

Output variances define different output configurations the meta builder can produce. Each variance is an output_variance component reference with optional overrides.

| Field | Type | Required | Description |
|---|---|---|---|
| component_id | string | Yes | Reference to an output_variance component |
| overrides.variance_name | string | No | Override the variance name |
| overrides.variance_description | string | No | Override the variance description |
| overrides.component_requirements | array | No | Override which component types are required |
| overrides.output_files | array | No | Override the files produced |

```yaml
output_variances:
  - component_id: "variance-prompt-only-001"
    # Uses component as-is (no overrides)
  - component_id: "variance-mixed-with-api-001"
    overrides:
      output_files:
        - "workflow.toml"
        - "prompts/*.txt"
        - "actions.py"
        - "context_extensions.py"
        - "README.md"
        - ".env.sample"
```

## Override Mechanism

Overrides allow per-composition customization of component properties without modifying the original component in the library. When a composition references a component by component_id, it may include an `overrides` block that replaces specific property values.

### Override Rules

1. **Schema conformance**: Overrides must only specify properties that exist in the component type's schema. Adding properties not defined for the component type is a validation error.

2. **Merge semantics**: Overrides are merged with the component's base properties. The override value wins on conflict. Properties not mentioned in the override retain their base values from the component.

3. **Common properties are not overridable**: The 5 required common properties (component_id, component_type, name, version, description) cannot be overridden. These are intrinsic to the component identity.

4. **Optional properties can be added via override**: An override may supply a value for an optional property that the base component did not set.

5. **Type-specific properties only**: Overrides apply to the type-specific properties of the component, plus the 3 optional common properties (duration_range, platforms, tags).

### Merge Example

Given a base component:
```yaml
component_id: "step-generate-component-schema-001"
component_type: "step_definition"
step_name: "generate_component_schema"
step_type: "prompt"
purpose: "Generate the component schema for Layer 1"
required_inputs:
  - "WORKFLOW_SPEC_FILE"
  - "TEST_CRITERIA_FILE"
produces:
  - "COMPONENT_SCHEMA_FILE"
enable_notifications: true
requires_human_approval_after: false
```

And a composition override:
```yaml
step_bindings:
  - component_id: "step-generate-component-schema-001"
    overrides:
      purpose: "Generate the component schema for the creative workflow domain"
      enable_notifications: false
```

The resolved step has:
```yaml
# Resolved properties (override wins on conflict)
step_name: "generate_component_schema"          # From base (not overridden)
step_type: "prompt"                              # From base (not overridden)
purpose: "Generate the component schema for the creative workflow domain"  # OVERRIDDEN
required_inputs:                                  # From base (not overridden)
  - "WORKFLOW_SPEC_FILE"
  - "TEST_CRITERIA_FILE"
produces:                                         # From base (not overridden)
  - "COMPONENT_SCHEMA_FILE"
enable_notifications: false                       # OVERRIDDEN
requires_human_approval_after: false              # From base (not overridden)
```

### Override Syntax in Step Bindings

In the workflow_builder domain, step bindings have a special override structure because roles, routing, and prompt_patterns are bound inline within the step:

```yaml
step_bindings:
  - component_id: "step-generate-component-schema-001"
    overrides:
      purpose: "Generate the component schema for Layer 1"
      produces: ["COMPONENT_SCHEMA_FILE"]
    role:
      component_id: "role-architect-standard-001"
    routing:
      component_id: "routing-generate-component-schema-001"
    prompt_patterns:
      - component_id: "prompt-self-critic-001"
      - component_id: "prompt-self-validation-001"
      - component_id: "prompt-reference-inputs-001"
```

### Override Syntax in Other Bindings

For non-step bindings, overrides follow the standard pattern:

```yaml
# Artifact binding with override
artifact_bindings:
  output_artifacts:
    - component_id: "artifact-component-schema-file-001"
      overrides:
        description: "Component schema for the creative workflow domain"

# Variance binding with override
output_variances:
  - component_id: "variance-prompt-only-001"
    overrides:
      output_files:
        - "workflow.toml"
        - "prompts/*.txt"
        - "context_extensions.py"
        - "README.md"
        - "Standards/COMPOSITION_STANDARD.md"
```

### Invalid Override Example

```yaml
# INVALID: step_type is not a property of role_policy
role:
  component_id: "role-architect-standard-001"
  overrides:
    step_type: "prompt"    # ERROR: step_type belongs to step_definition, not role_policy

# INVALID: common property override
step_bindings:
  - component_id: "step-generate-component-schema-001"
    overrides:
      component_type: "action"    # ERROR: common properties cannot be overridden
```

## Placeholder Resolution

Placeholders are `{variable_name}` tokens in composition values that are resolved from external data sources at generation time. The workflow_builder domain defines three data sources for placeholder resolution.

### Data Sources

| Data Source | Fields Provided | Required? | Description |
|---|---|---|---|
| Input Spec | WORKFLOW_SPEC_FILE, domain_name, job_prefix | Yes | The composition system specification provided as input to the builder. Contains the full domain spec, component type definitions, and composition rules. |
| Governance | BASE_COMPOSITION_STANDARD, GOVERNANCE_RUNTIME_ROOT | Yes | The composition standard document and the governance runtime root directory. Provides access to Layer 1 and Layer 2 governance documents. |
| Runtime | job_id, seq, workspace_root | Yes | Values computed at workflow execution time. The job_id identifies the current run, seq is the sequence number for artifact filenames, and workspace_root is the working directory. |

### Resolution Rules

1. **Prompt template placeholders**: Placeholders in prompt templates (e.g., `{ARTIFACT_KEY}` references) are resolved at runtime by the context_extensions.py module. Artifact keys are resolved to absolute file paths via the `known_artifact_paths()` function.

2. **Artifact path placeholders**: The `{seq}` placeholder in filename patterns (e.g., `COMPONENT_SCHEMA-{seq}.md`) is resolved from the Runtime data source. The sequence number is assigned by the workflow runner at execution time.

3. **Governance path placeholders**: Paths referencing governance documents (e.g., `{GOVERNANCE_RUNTIME_ROOT}/foundation/`) are resolved from the Governance data source via the runtime_context module.

4. **Domain-specific placeholders**: Placeholders like `{domain_name}`, `{builder_name}`, and `{job_prefix}` are resolved from the Input Spec data source.

### Resolution Order

Placeholders are resolved in the following order:
1. Governance paths (static, known before execution)
2. Input Spec values (loaded from WORKFLOW_SPEC_FILE at start)
3. Runtime values (computed during execution)
4. Prompt template placeholders (resolved by context_extensions.py at coder invocation)

### Unresolved Placeholder Handling

If a placeholder cannot be resolved from any available data source, it is flagged in the output as:

```
{UNRESOLVED: field_name}
```

For example, if `{custom_api_key}` cannot be resolved:
```yaml
overrides:
  api_endpoint: "{UNRESOLVED: custom_api_key}"
```

Unresolved placeholders are flagged but do not block the workflow. They are noted as gaps in the output and reported in validation.

### Placeholder Resolution Example

```yaml
# In the composition:
step_bindings:
  - component_id: "step-generate-package-001"
    overrides:
      purpose: "Generate the workflow package for {domain_name}"
      produces:
        - "WORKFLOW_MANIFEST_FILE"
        - "WORKFLOW_EXTENSIONS_FILE"

# Resolution:
# {domain_name} -> resolved from Input Spec -> "creative_workflow"
#
# Resolved value:
# purpose: "Generate the workflow package for creative_workflow"

# Filename pattern:
# WORKFLOW_MANIFEST_FILE -> "workflow.toml"
# WORKFLOW_EXTENSIONS_FILE -> "context_extensions.py"
```

## Ordering Rules

The workflow_builder domain defines specific ordering rules for each binding type. These rules are domain-driven: they reflect the logical execution sequence of workflow steps and the structural constraints of the meta builder architecture.

### Ordered List Bindings

| Binding | Ordered? | Reason |
|---|---|---|
| step_bindings | Yes | Steps execute sequentially. The array order defines the execution pipeline. Step 1 runs before Step 2, which runs before Step 3, and so on. |
| prompt_patterns (within a step) | No | Prompt patterns contribute sections to a prompt template. The section order is determined by the prompt template structure, not the binding order. |
| artifact_bindings (within input/output) | No | Artifacts are resolved by key lookup, not by position. Order within input_artifacts or output_artifacts does not affect resolution. |
| output_variances | No | Variances are independently selectable output configurations. No ordering constraint. |
| domain_specs | No | Domain specs are independently processable input types. No ordering constraint. |

### Singleton Bindings

| Binding | Singleton? | Reason |
|---|---|---|
| role (per step) | Yes | Each step has exactly one coder role. Multiple roles per step would create ambiguity about which standard governs the step. |
| routing (per step) | Yes | Each step has exactly one routing pattern. Multiple routing patterns per step would create ambiguous flow control. |
| composition_standard_binding | Yes | Each composition generates exactly one meta builder with one composition standard. Multiple standards would create conflicting definitions. |

### Ordering Constraints for step_bindings

The step_bindings array has the following ordering constraints:

1. **Foundation phase first**: The first steps must be generate_test_criteria, review_test_criteria, and optionally refine_test_criteria. This is the universal TDD loop.

2. **Layer sequence**: Component Schema (Layer 1) steps must precede Composition Format (Layer 2) steps, which must precede Output Format (Layer 3) steps.

3. **Gatekeep immediately after generate**: Each gatekeep step must immediately follow its corresponding generate step.

4. **Review after gatekeep**: Review steps follow gatekeep steps (when gatekeep approves).

5. **Refine after review**: Refine steps follow review steps (when review rejects). Refine steps route back to the corresponding review step.

6. **Terminal step last**: The stepCompletion step must be the final step with no onsuccess routing.

```yaml
# Ordered step_bindings with constraint annotations:
step_bindings:
  # Foundation phase (TDD loop) -- MUST be first
  - component_id: "step-generate-test-criteria-001"
  - component_id: "step-review-test-criteria-001"
  # Layer 1 phase
  - component_id: "step-generate-component-schema-001"
  - component_id: "step-gatekeep-component-schema-001"
  # Layer 2 phase
  - component_id: "step-generate-composition-format-001"
  - component_id: "step-gatekeep-composition-format-001"
  # Layer 3 phase
  - component_id: "step-generate-output-format-001"
  - component_id: "step-gatekeep-output-format-001"
  # ... more phases ...
  # Terminal step -- MUST be last
  - component_id: "step-step-completion-001"
```

### Mandatory Binding Rules

Every composition must satisfy these binding requirements:

| Rule | Description |
|---|---|
| Every step has a role | No step may exist without a role_policy binding. |
| Every step has routing | No step may exist without a routing_pattern binding. |
| Prompt steps have self_critic and self_validation | Every step with step_type="prompt" must bind at least the self_critic and self_validation prompt_patterns. |
| Action steps have no prompt_patterns | Steps with step_type="action" must not bind prompt_patterns. |
| Exactly one composition_standard | The composition_standard_binding must contain exactly one component reference. |
| At least one input artifact | The artifact_bindings.input_artifacts must contain at least the WORKFLOW_SPEC_FILE. |

## Composition Validation

Every composition must pass the following validation checks before it can be resolved into outputs. These checks enforce the binding rules, override constraints, placeholder resolvability, and ordering constraints defined in the preceding sections.

### CV-001: Component Reference Existence

All component_id values referenced in the composition must exist in the component library. No dangling references are permitted.

- Every step_bindings[].component_id must reference a valid step_definition component.
- Every role.component_id must reference a valid role_policy component.
- Every routing.component_id must reference a valid routing_pattern component.
- Every prompt_patterns[].component_id must reference a valid prompt_pattern component.
- Every artifact binding's component_id must reference a valid artifact_contract component.
- The composition_standard_binding's component_id must reference a valid composition_standard component.
- Every output_variances[].component_id must reference a valid output_variance component.
- Every domain_specs[].component_id must reference a valid domain_spec component.

### CV-002: Override Schema Conformance

All overrides must conform to the component type's schema. No override may specify a property that does not exist in the target component's type-specific property definitions.

- Step overrides may only specify step_definition properties (step_name, step_type, purpose, required_inputs, produces, enable_notifications, requires_human_approval_after).
- Role overrides may only specify role_policy properties (policy_name, assignment_rule).
- Routing overrides may only specify routing_pattern properties (onsuccess, on_reject_refine, max_iterations, exhausted_failure_code, exhausted_failure_class).
- Artifact overrides may only specify artifact_contract properties (artifact_key, description, filename_pattern, required, produced_by).
- Standard overrides may only specify composition_standard properties (standard_name, standard_version, component_types_defined, schema_sections, extensibility_model).
- Variance overrides may only specify output_variance properties (variance_name, variance_description, component_requirements, output_files).

### CV-003: Required Bindings Present

All required bindings must be present in the composition:

- step_bindings must be present and non-empty.
- Every step must have a role binding.
- Every step must have a routing binding.
- artifact_bindings must be present with at least one input_artifact.
- composition_standard_binding must be present.

### CV-004: Placeholder Resolvability

All placeholders in override values must be resolvable from the declared data sources:

- Input Spec placeholders (domain_name, job_prefix) must be present in WORKFLOW_SPEC_FILE.
- Governance placeholders (BASE_COMPOSITION_STANDARD, GOVERNANCE_RUNTIME_ROOT) must be accessible.
- Runtime placeholders (job_id, seq, workspace_root) are resolved at execution time.

Unresolvable placeholders are flagged as `{UNRESOLVED: field_name}` but do not block validation.

### CV-005: Ordering Constraints Satisfied

The step_bindings array must satisfy the ordering constraints defined in Section 6:

- Foundation phase steps (generate_test_criteria, review_test_criteria) appear first.
- Layer sequence is maintained (Layer 1 before Layer 2 before Layer 3).
- Gatekeep steps immediately follow generate steps.
- The stepCompletion step is the final entry.

### CV-006: Workflow Pattern Validity

The workflow_pattern field must be one of the 6 defined values:
- action_only
- prompt_driven
- mixed
- gatekeeper_pipeline
- meta_workflow_builder
- meta_meta_builder

### CV-007: Composition Standard Completeness

The composition_standard_binding must define all required fields after override resolution:

- standard_name: non-empty string in UPPER_SNAKE_CASE
- standard_version: valid semantic version (MAJOR.MINOR.PATCH)
- component_types_defined: non-empty array of valid component type names
- schema_sections: exactly 3 entries ("Component Schema", "Composition Format", "Output Format")
- extensibility_model: non-empty, concrete description

### CV-008: Step Name Uniqueness

After override resolution, all step_name values across all step_bindings must be unique. No two steps may share the same step_name.

### CV-009: Routing Completeness

Every step must have an onsuccess routing value. The onsuccess target must reference an existing step_name within the composition. Review and gatekeep steps that can reject must have on_reject_refine routing defined.

### CV-010: Artifact Flow Integrity

Every step's required_inputs must reference an artifact that is either:
- Declared as an input_artifact in artifact_bindings (no produced_by), or
- Produced by a step that executes before the consuming step in the step_bindings order.
