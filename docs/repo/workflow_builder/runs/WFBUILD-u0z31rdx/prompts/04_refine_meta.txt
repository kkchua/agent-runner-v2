Objective

Refine the generated meta content files based on review feedback. Read the
review document and apply corrections to the affected meta content files
in place. Only modify files that received feedback.

Layer Boundary

- This workflow belongs to Layer 3 and operates on top of the Layer 2 platform contract.
- Refine only the generated meta content files, not the codebase or governance docs.
- Treat Layer 1 governance and Layer 2 platform constitution as read-only authority.

Reference Inputs

- Read the developer meta file: {META_DEV_FILE}
- Read the architect meta file: {META_ARCH_FILE}
- Read the executive meta file: {META_EXEC_FILE}
- Read the meta index: {META_INDEX}
- Read the audience index: {AUDIENCE_INDEX}
- Read the review document: {REVIEW_FILE_SUGGESTED}

Refinement Rules

1. Address All Critical Findings:
   - Missing required frontmatter fields must be added
   - Incorrect frontmatter values must be corrected
   - Missing required sections must be added
   - Section structure deviations must be fixed
   - Encoding violations must be corrected

2. Address All Major Findings:
   - Tone violations must be corrected to match audience specification
   - Missing focus area coverage must be added
   - Excluded content must be removed
   - Inaccurate code references must be verified and corrected
   - Content accuracy issues must be resolved

3. Address Minor Findings:
   - Style improvements should be applied
   - Minor clarifications should be added where requested
   - Section headings should use plain text format

4. Preserve Original Intent:
   - Do not change the audience scope or add new focus areas
   - Do not add content beyond what the codebase documentation supports
   - Do not modify the section structure beyond what the audience definition specifies
   - Maintain the self-contained nature of each file

5. Verify Technical Accuracy:
   - Verify code patterns against actual source code
   - Verify API names and signatures against installed libraries
   - Verify file paths reference real files
   - Do not rely on training data for library APIs

6. Update Frontmatter:
   - If section_count changed, update the field
   - If generated_date needs updating, use current date
   - Keep all other frontmatter fields intact

Refinement Process

1. Read {REVIEW_FILE_SUGGESTED} carefully
2. Identify all critical and major findings per audience
3. For each affected meta file:
   a. Read the current content
   b. Read the corresponding audience definition from {AUDIENCE_INDEX}
   c. Apply corrections for each finding
   d. Verify the corrections address the specific feedback
   e. Write the corrected content back in place
4. Update {META_INDEX} if any metadata changed
5. Verify all files still pass structural checks

Output Instructions

- Update each meta content file in place at its designated path.
- Update {META_INDEX} if metadata changed.
- Use ASCII-only characters.
- Use plain text section headings.
- Keep frontmatter fields present and consistent.
- Do not change the document structure unless required by review findings.
- Only modify files that received specific feedback.

Self-Validation

Before reporting APPROVED, validate your refinements:

1. All critical findings from the review are addressed
2. All major findings from the review are addressed
3. Frontmatter is correct for each modified file
4. Section structure matches audience definitions
5. Tone matches audience specifications
6. Exclude lists are respected
7. Content is ASCII-only
8. {META_INDEX} is updated if needed

If any check fails, revise before reporting APPROVED.

Forbidden Content

- Layer 1 governance redefinition or contradiction
- Layer 2 platform contract redefinition
- Content not grounded in the actual codebase documentation
- Topics listed in any audience's exclude list
- Non-ASCII characters
- Changes to files that did not receive review feedback
