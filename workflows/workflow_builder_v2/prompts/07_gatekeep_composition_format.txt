Objective

Validate the generated composition format for clarity, correctness, and
conformance to the Composition System Standard. This is a quality control
checkpoint before downstream steps consume the format.

The gatekeeper asks: "Does this format define how compositions reference
components? Are the override mechanism and placeholder resolution clear?
Can downstream steps resolve compositions into outputs unambiguously?"

Reference Inputs

- Read {COMPOSITION_FORMAT_FILE} for the format to validate.
- Read {COMPONENT_SCHEMA_FILE} for the component types -- compositions
  reference these components.
- Read {TEST_CRITERIA_FILE} for acceptance criteria -- sections 4 and 5
  define what makes a good composition format and what the gatekeeper must
  check.
- Read {COMPOSITION_SYSTEM_STANDARD} Section 4 (Composition Format Standard)
  for the standard composition pattern.
- Read {WORKFLOW_SPEC_FILE} for the original specification -- verify the
  format aligns with the spec's composition requirements.

Validation Questions

Answer each question with specific evidence from the documents:

1. Structure Completeness: Does the format define the YAML structure with
   all required fields (composition_id, name, target_metadata,
   component_bindings)? Are there missing fields?

2. Reference Pattern: Are components referenced by component_id (not copied)?
   Is the reference pattern clear and unambiguous? Can a composition author
   know how to reference a component?

3. Override Mechanism: Is the override mechanism defined? Can composition
   authors customize components per-composition without modifying the
   component? Do overrides conform to the component type schema?

4. Placeholder Resolution: Are {placeholder} values resolved from external
   data sources? Are the data sources identified? Is the resolution process
   clear? Are unresolved placeholders handled ({UNRESOLVED: field_name})?

5. Ordering Rules: Are ordered list bindings vs singleton bindings defined?
   Is the reasoning clear (why some are ordered, others are singletons)?
   Can a composition author know which type to use?

6. Optional Bindings: Are required vs optional bindings defined? Can a
   composition omit non-required bindings?

7. Validation Rules: Are composition validation rules defined? Can a
   gatekeeper validate compositions unambiguously? Rules for:
   - All referenced component_ids exist
   - Overrides conform to component type schema
   - Required bindings present
   - Placeholders are resolvable
   - Ordering constraints satisfied

8. Example Quality: Are there at least two complete example compositions?
   Do they demonstrate the full range of the format (different binding types,
   overrides, placeholders)?

9. Standard Conformance: Does the format follow the Composition System
   Standard's composition format pattern? Are there deviations?

10. Downstream Feasibility: Can a downstream step read this format and know
    how to resolve compositions into outputs? Is the format clear enough for
    implementation?

Self-Critic (Before Final Verdict)

Challenge your review before committing to a verdict:

1. Am I rubber-stamping, or did I actually verify each composition rule
   against the standard and spec?
2. Did I find at least one substantive finding, or am I just saying
   "looks good"?
3. If I missed an issue that a later step catches, what would it be?
4. Is my verdict based on evidence from the format, or on assumptions
   about what the generator "probably" did?

If your review is superficial, go back and dig deeper before reporting.

Decision Rules

- APPROVED: The composition format is complete, clear, and conforms to the
  Composition System Standard. All validation questions have satisfactory
  answers. The override mechanism and placeholder resolution are clear.
  Examples demonstrate the full range of the format.

- REJECTED: The composition format has gaps (missing structure, unclear
  overrides, missing placeholder resolution), does not conform to the
  standard, or will cause downstream failures. Include specific findings
  for each failed validation question.

Output Instructions

- Write the gatekeeper report to {GATEKEEP_COMPOSITION_FORMAT_FILE}.
- Include YAML frontmatter with doc_type: "gatekeep_report".
- Structure:
  1. Summary: Overall assessment (1-2 sentences)
  2. Validation Results: Table with columns: Question, Status (PASS/FAIL),
     Evidence
  3. Issues (if any): Numbered list of specific gaps found
  4. Recommendations: Specific suggestions to fix issues
  5. Verdict: APPROVED or REJECTED on its own line
- All content must be ASCII-only.
- The result field in meta.json must match the verdict exactly.

Forbidden Content

- Non-ASCII characters
- Vague findings without specific evidence
- Approving formats with known gaps
