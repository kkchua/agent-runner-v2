Objective

Generate the complete composition system workflow package. Assemble all design
artifacts into a deployable workflow bundle that implements the operational
workflow design.

The package includes:
- workflow.toml: Step definitions, routing, artifact bindings
- context_extensions.py: WorkflowExtensions class, artifact key registration
- actions.py: Action implementations for action-driven steps (if any)
- prompts/: One prompt file per prompt-driven step
- README.md: User guide with step reference and artifact keys
- OUTPUT_COMPOSITION_SPEC.md: Composition spec for output artifacts (extensibility)

Package Generation Principles

1. Generate ALL files implied by the operational workflow design:
   - For EACH prompt-driven step: generate a prompt file in prompts/
   - For EACH action-driven step: add action implementation to actions.py
   - Always generate: workflow.toml, context_extensions.py, README.md,
     OUTPUT_COMPOSITION_SPEC.md
   - Conditionally generate: actions.py (if action steps exist), .env.sample
     (if env vars needed), config.json.sample (if runtime config needed)

2. workflow.toml generation:
   - Include all domain steps from {OPERATIONAL_WORKFLOW_FILE} in order
   - Add infrastructure steps after domain steps: promote, then stepCompletion
   - Use artifact keys from the operational workflow's artifact contract
   - Place onsuccess at [[step]] top level (not under [step.artifacts])
   - Every prompt step has [step.coder] with a valid role_policy
   - Every prompt step has [step.artifacts] with produces and result_meta_key
   - Review steps have [step.on_reject_refine] with step, artifact,
     max_iterations, exhausted_failure_code, exhausted_failure_class
   - Refine steps have onsuccess pointing to the review step
   - Step names are lowercase_with_underscores and unique
   - Include stepCompletion as the terminal step
   - Include promote step before stepCompletion

3. context_extensions.py generation:
   - WorkflowExtensions class that inherits correctly
   - workflow_name matches the workflow directory name
   - register_artifact_keys() returns relative paths with {job_id}, {seq}
     placeholders
   - build_context_extensions() returns absolute paths
   - Include install_to_global() and sync_to_backend() methods
   - All artifact keys from workflow.toml produces AND required_inputs lists
     appear in register_artifact_keys() (both outputs and inputs must be
     registered)
   - Module, class, and methods have docstrings

4. actions.py generation (if action steps exist):
   - Read action specifications from {OPERATIONAL_WORKFLOW_FILE}
   - Infrastructure steps (promote, stepCompletion) should have corresponding
     @action implementations in the generated actions.py:
     - promote step: implement promote_workflow_package action
     - terminal step: action = "step_completion" (globally registered)
   - For domain-specific action steps: check if an existing reusable
     action covers the need before proposing new ones. Implement ONLY truly
     new actions with @action decorator.
   - Include proper ActionResult returns (APPROVED/REJECTED)
   - Include error handling and input validation
   - Use type hints and docstrings

5. prompts/ generation:
   - Name: prompts/NN_step_name.txt where NN is step order
   - Include Objective, Reference Inputs, Output Instructions sections
   - Use bare {ARTIFACT_KEY} placeholders (never backtick-wrapped)
   - ASCII-only content
   - Each prompt must explicitly instruct the LLM to use file-writing tools
     to create actual files on disk
   - Each prompt must clarify that meta.json result field is for status/summary
     ONLY, not artifact data

6. README.md generation:
   - Overview: what the workflow does
   - Prerequisites: what inputs are needed
   - Usage: how to run the workflow
   - Step Reference: table of steps with name, type, purpose
   - Artifact Keys: table of all artifact keys with descriptions
   - Architecture: how the three-layer architecture is implemented

7. OUTPUT_COMPOSITION_SPEC.md generation:
   - Copy the content from {OUTPUT_COMPOSITION_SPEC_FILE} into the package
     output directory as OUTPUT_COMPOSITION_SPEC.md
   - This file enables extensibility — new output types can be added by
     composition without modifying the workflow
   - Ensure the file is complete and well-formatted (it was generated by a
     prior step)

8. Conditional files:
   - .env.sample: Only if environment variables needed. Each variable has a
     descriptive comment and placeholder value.
   - config.json.sample: Only if runtime config needed. Must be valid JSON
     with sensible defaults.

9. Artifact binding fidelity (CRITICAL):
   - The operational workflow design's Step Sequence table is the AUTHORITATIVE
     source for each step's required_inputs and produces lists.
   - You MUST copy these lists VERBATIM into workflow.toml [step.artifacts].
   - Do NOT summarize, reorder, or omit items from the design's artifact
     declarations. Every key the design lists MUST appear in workflow.toml.
   - If a prompt file references {SOME_KEY}, that key MUST appear in the
     step's required_inputs (if consumed) or produces (if created).
   - Missing a required_inputs entry means the runner will not verify the
     artifact exists before executing the step -- this causes silent failures.

Code Quality Rules (CRITICAL)

These rules prevent runtime defects. Violations cause NameError, TypeError,
or silent failures at workflow execution time.

CQ-1: Import Placement
   - ALL imports used at runtime MUST be at the top level of the file.
   - NEVER put runtime imports inside `if TYPE_CHECKING:` blocks.
   - TYPE_CHECKING is False at runtime. Names imported inside it do NOT exist
     when the code executes.
   - Only use TYPE_CHECKING for imports that are ONLY used in type annotations
     (e.g., `def foo(x: SomeType)` where SomeType is never called).
   - If a function calls `build_snapshot()`, then `build_snapshot` MUST be
     importable at runtime -- not inside TYPE_CHECKING.

CQ-2: Early Exit / No-Op Paths
   - When an action detects "no work to do" (e.g., no changes, empty input),
     it MUST return an empty artifacts dict: `artifacts={}`.
   - Do NOT write placeholder/stub files with content like "No changes detected".
   - Do NOT create empty files just to have artifact paths to return.
   - The correct pattern:
     ```
     if no_work_needed:
         return ActionResult(status="APPROVED", remark="...", artifacts={})
     ```
   - Downstream steps check for empty artifacts to detect early exit.

CQ-3: Artifact Binding Consistency
   - An artifact key MUST NOT appear in both required_inputs AND produces of
     the same step. This is a self-referential binding that fails at runtime.
   - required_inputs lists artifacts this step CONSUMES (produced by prior steps).
   - produces lists artifacts this step CREATES.
   - If a step both reads and updates an artifact, it should be in produces only.

CQ-4: Error Handling Pattern
   - Every action must handle: missing context variables, missing files,
     external command failures (subprocess.CalledProcessError, FileNotFoundError).
   - Use explicit reject_code values for each failure mode.
   - Write meta.json sidecar BEFORE returning ActionResult.
   - Do NOT use bare `except Exception:` without logging the error.

CQ-5: ActionResult Contract
   - Every @action function MUST return ActionResult.
   - APPROVED: includes artifacts dict with all produced artifact paths.
   - REJECTED: includes reject_code string and empty artifacts dict.
   - Never return None, a dict, or any other type.

Cross-Reference Verification (Before Self-Validation)

After generating all files, verify consistency across them:

1. workflow.toml vs {OPERATIONAL_WORKFLOW_FILE}:
   - Does every step in the design appear in workflow.toml?
   - Are step names, types (prompt/action), and routing identical?
   - Are artifact bindings (produces, required_inputs) VERBATIM from the
     design? For EACH step, compare the design's required_inputs list against
     workflow.toml's required_inputs list -- every key must match exactly.
     A missing required_inputs key means the runner will not verify the
     artifact exists before step execution.

2. context_extensions.py vs workflow.toml:
   - Does register_artifact_keys() include ALL keys from workflow.toml
     (both produces AND required_inputs from all steps)?
   - Does workflow_name match the workflow directory name?

3. actions.py vs workflow.toml:
   - Does every action step in workflow.toml have a corresponding
     @action("name") function in actions.py?
   - Are reusable actions (step_completion, promote_workflow_package)
     referenced by name, not re-implemented?

4. prompts/ vs workflow.toml:
   - Does every prompt-driven step have a corresponding prompts/NN_name.txt?
   - Are prompt file names consistent with step names?
   - For each prompt file, extract every {ARTIFACT_KEY} placeholder. Each
     referenced key MUST appear in that step's required_inputs (if the prompt
     reads the artifact) or produces (if the prompt creates it) in
     workflow.toml. A placeholder referencing an undeclared key means the
     runner will not provide the artifact path at runtime.

Common Pitfalls (DO NOT)

PITFALL-1: TYPE_CHECKING imports
   WRONG:
     if TYPE_CHECKING:
         from module import build_snapshot
     def my_action():
         build_snapshot()  # NameError at runtime!
   RIGHT:
     from module import build_snapshot
     def my_action():
         build_snapshot()  # Works at runtime

PITFALL-2: Self-referential artifact bindings
   WRONG:
     required_inputs = ["UPDATED_MANIFEST_FILE"]
     produces = ["UPDATED_MANIFEST_FILE"]
   RIGHT:
     produces = ["UPDATED_MANIFEST_FILE"]

PITFALL-3: Placeholder files on early exit
   WRONG:
     if no_changes:
         path.write_text("No changes detected")
         return ActionResult(status="APPROVED", artifacts={"KEY": str(path)})
   RIGHT:
     if no_changes:
         return ActionResult(status="APPROVED", remark="No changes", artifacts={})

PITFALL-4: Missing @action decorator
   WRONG:
     def my_action(*, context, state, step_cfg, project_root):
         ...
   RIGHT:
     @action("my_action")
     def my_action(*, context, state, step_cfg, project_root):
         ...

PITFALL-5: Hardcoded paths in register_artifact_keys
   WRONG:
     "MY_FILE": "D:/repo/docs/runs/{job_id}/file.md"
   RIGHT:
     "MY_FILE": "docs/repo/runs/{job_id}/file.md"

PITFALL-6: Missing required_inputs in workflow.toml
   WRONG (refine step prompt references {OUTPUT_FILE} but workflow.toml omits it):
     # In prompts/06_refine_output.txt:
       "Current Output File: {OUTPUT_FILE}"
     # In workflow.toml [[step]] refine_output:
       required_inputs = ["REVIEW_FILE_SUGGESTED", "RESOLUTION_PLAN_FILE"]
       # OUTPUT_FILE is MISSING -- runner won't verify it exists!
   RIGHT:
     # In workflow.toml [[step]] refine_output:
       required_inputs = ["REVIEW_FILE_SUGGESTED", "OUTPUT_FILE", "RESOLUTION_PLAN_FILE"]
       # OUTPUT_FILE included -- matches both the prompt and the design

CRITICAL -- meta.json Artifact Reporting

The artifacts dict in meta.json MUST use the individual file artifact keys
listed below. Each key maps to the absolute path of the generated file.

Correct meta.json artifacts example:

    "artifacts": {
      "WORKFLOW_MANIFEST_FILE": "D:/repo/runs/JOB-123/output/workflow.toml",
      "WORKFLOW_EXTENSIONS_FILE": "D:/repo/runs/JOB-123/output/context_extensions.py",
      "WORKFLOW_ACTIONS_FILE": "D:/repo/runs/JOB-123/output/actions.py",
      "WORKFLOW_PROMPTS_INDEX_FILE": "D:/repo/runs/JOB-123/output/prompts_index.json",
      "WORKFLOW_README_FILE": "D:/repo/runs/JOB-123/output/README.md"
    }

WRONG -- do NOT use a single summary key:

    "artifacts": {
      "WORKFLOW_PACKAGE": null
    }

The key "WORKFLOW_PACKAGE" is NOT a valid artifact key. Always use the
individual file keys:

  - WORKFLOW_MANIFEST_FILE: path to workflow.toml
  - WORKFLOW_EXTENSIONS_FILE: path to context_extensions.py
  - WORKFLOW_ACTIONS_FILE: path to actions.py (if generated)
  - WORKFLOW_PROMPTS_INDEX_FILE: path to prompts_index.json
  - WORKFLOW_README_FILE: path to README.md
  - WORKFLOW_ENV_SAMPLE_FILE: path to .env.sample (if generated)
  - WORKFLOW_CONFIG_SAMPLE_FILE: path to config.json.sample (if generated)

Individual prompt files (prompts/*.txt) are NOT separate artifacts -- they
are covered by WORKFLOW_PROMPTS_INDEX_FILE.

Forbidden Content

- Non-ASCII characters
- Backtick-wrapped placeholders like `{ARTIFACT_KEY}`
- Hardcoded absolute paths in register_artifact_keys()
- Missing stepCompletion terminal step
- Using "WORKFLOW_PACKAGE" as an artifact key in meta.json
- Omitting WORKFLOW_ACTIONS_FILE from meta.json when actions.py exists
- Inventing artifact keys not in the produces list
- Runtime imports inside TYPE_CHECKING blocks
- Self-referential artifact bindings
- Placeholder/stub files on early-exit paths
