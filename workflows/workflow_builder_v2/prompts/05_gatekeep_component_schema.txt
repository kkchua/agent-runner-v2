Objective

Validate the generated component schema for completeness, correctness, and
conformance to the Composition System Standard. This is a quality control
checkpoint before downstream steps consume the schema.

The gatekeeper asks: "Does this schema define all component types from the spec?
Are the type-specific properties concrete and actionable? Can downstream
compositions reference these components unambiguously?"

Reference Inputs

- Read {COMPONENT_SCHEMA_FILE} for the schema to validate.
- Read {TEST_CRITERIA_FILE} for acceptance criteria -- sections 2 and 3
  define what makes a good component schema and what the gatekeeper must check.
- Read {COMPOSITION_SYSTEM_STANDARD} Section 3 (Universal Component Schema)
  for the standard schema pattern.
- Read {WORKFLOW_SPEC_FILE} for the original specification -- verify the
  schema covers all component types implied by the spec.

Validation Questions

Answer each question with specific evidence from the documents:

1. Type Completeness: Does the schema define ALL component types from the spec?
   Are there component types implied by the spec but missing from the schema?
   List any missing types.

2. Common Properties: Does every component type include the common properties
   (component_id, component_type, name, version, description)? Are there
   deviations from the standard?

3. Type-Specific Properties: For each component type, are the type-specific
   properties concrete and actionable? Do they have:
   - Property name
   - Type (string, enum, number, boolean, array, object)
   - Required/optional
   - Description
   - Example value
   Are any properties vague (e.g., "some value", "varies")?

4. Validation Rules: Are validation rules present for each component type?
   Are the rules enforceable (can a gatekeeper pass/fail unambiguously)?
   Are there rules for:
   - Required fields present
   - Valid component_type
   - Unique component_id
   - Type-specific schema conformance
   - Semantic version format

5. Extensibility Model: Is the extensibility model clear? Can new types be
   added without breaking existing compositions? Are backward compatibility
   rules defined?

6. Example Quality: Is there at least one example component per type? Are
   examples realistic, complete, and conformant to the schema?

7. Standard Conformance: Does the schema follow the Composition System
   Standard's universal component schema pattern? Are there deviations?

8. Downstream Feasibility: Can a composition reference these components by
   component_id and know what properties to expect? Is the schema clear
   enough for composition authors?

Self-Critic (Before Final Verdict)

Challenge your review before committing to a verdict:

1. Am I rubber-stamping, or did I actually verify each component type
   against the spec?
2. Did I find at least one substantive finding, or am I just saying
   "looks good"?
3. If I missed an issue that a later step catches, what would it be?
4. Is my verdict based on evidence from the schema, or on assumptions
   about what the generator "probably" did?

If your review is superficial, go back and dig deeper before reporting.

Decision Rules

- APPROVED: The component schema is complete, correct, and conforms to the
  Composition System Standard. All validation questions have satisfactory
  answers. All component types from the spec are defined with concrete
  properties and enforceable validation rules.

- REJECTED: The component schema has gaps (missing types, vague properties,
  missing validation rules), does not conform to the standard, or will cause
  downstream failures. Include specific findings for each failed validation
  question.

Output Instructions

- Write the gatekeeper report to {GATEKEEP_COMPONENT_SCHEMA_FILE}.
- Include YAML frontmatter with doc_type: "gatekeep_report".
- Structure:
  1. Summary: Overall assessment (1-2 sentences)
  2. Validation Results: Table with columns: Question, Status (PASS/FAIL),
     Evidence
  3. Issues (if any): Numbered list of specific gaps found
  4. Recommendations: Specific suggestions to fix issues
  5. Verdict: APPROVED or REJECTED on its own line
- All content must be ASCII-only.
- The result field in meta.json must match the verdict exactly.

Forbidden Content

- Non-ASCII characters
- Vague findings without specific evidence
- Approving schemas with known gaps
