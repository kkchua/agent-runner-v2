Objective

Generate the Output Composition Specification for the workflow being built.
This spec treats the workflow's output artifacts as a composable component
library, enabling extensibility — new output types can be added by composition
without modifying the workflow itself.

The Output Composition Spec defines:
- Component types for each output artifact category (Layer 1)
- Composition rules for how output artifacts can be combined or extended (Layer 2)
- Resolution rules for generating outputs from compositions (Layer 3)

This is the key extensibility mechanism: downstream users can add new
"compositions" (new output types) without changing the workflow code.

Output Composition Spec Design Principles

1. Identify output artifact categories:
   - Group the workflow's output artifacts into logical categories
   - Each category becomes a component type
   - Example: codebase_to_meta produces audience-specific meta files →
     component types: stakeholder_meta, developer_meta, architecture_meta

2. Define component type schemas:
   - For each component type, define its properties (format, audience, scope, etc.)
   - Properties should capture what makes each output variant distinct
   - Include common properties shared by all output components

3. Define composition rules:
   - How are output components selected and combined?
   - What overrides can be applied per-composition?
   - What placeholders need resolution?

4. Enable extensibility:
   - New component types can be added without modifying the workflow
   - New compositions can be created by combining existing component types
   - The spec should make it clear HOW to extend the output set

5. Follow the three-layer pattern:
   - Layer 1: Component types (output artifact categories with schemas)
   - Layer 2: Compositions (specific output configurations)
   - Layer 3: Resolved outputs (the actual generated files)

Generation Tasks

Produce an Output Composition Specification document with these sections:

1. Overview
   - What output artifacts does this workflow produce?
   - How can they be categorized into component types?
   - What is the extensibility story? (how to add new output types)

2. Component Schema (Layer 1)
   - Table of component types (one per output artifact category)
   - Common properties shared by all output components
   - Type-specific properties for each component type
   - Validation rules for output components

3. Composition Format (Layer 2)
   - How are output compositions structured?
   - Binding rules: which component types go where
   - Override mechanism: per-composition customizations
   - Example composition: a specific output configuration

4. Output Format (Layer 3)
   - What does a resolved output look like?
   - Resolution rules for generating outputs
   - Quality requirements for outputs
   - Example output skeleton

5. Extension Guide
   - How to add a new component type (new output artifact category)
   - How to add a new composition (new output configuration)
   - What files need to change (if any) when extending

Context Verification (Before Self-Critic)

Verify consistency with prior artifacts:

1. Output Artifact Completeness: Does the component schema cover ALL output
   artifacts listed in {OPERATIONAL_WORKFLOW_FILE} Section 4?
2. Output Format Alignment: Do the component type schemas match the output
   structure defined in {OUTPUT_FORMAT_FILE}?
3. Spec Alignment: Does the composition format align with the input spec's
   output requirements in {WORKFLOW_SPEC_FILE} Section 4?
4. Extensibility: Can a new output type be added by defining a new component
   type and composition, without modifying the workflow code?

If any inconsistency is found, fix it before proceeding.

Self-Critic (Before Self-Validation)

Challenge your reasoning before checking completeness:

1. Am I treating output artifacts as composable components, or just listing them?
2. Does the spec actually enable extensibility, or is it just documentation?
3. Would a downstream user know how to add a new output type from this spec?
4. Did I follow the three-layer pattern from the Composition System Standard?

If you find reasoning issues, fix them before proceeding to Self-Validation.

Self-Validation (Before Output)

Before reporting APPROVED, validate:

1. Component Type Completeness: Does every output artifact category have a
   component type definition?

2. Schema Quality: Are component type schemas concrete (with typed properties,
   examples) or vague?

3. Composition Format: Can compositions be declaratively defined? Are binding
   rules clear?

4. Extension Guide: Is it clear how to add new component types and compositions?

5. Three-Layer Conformance: Does the spec follow the Component → Composition →
   Output pattern?

6. No Workflow Changes Required: Can new output types be added WITHOUT modifying
   the workflow's workflow.toml, prompts, or actions?

If validation fails, report REJECTED with specific gaps found.

Output Instructions

- Write the Output Composition Specification to {OUTPUT_COMPOSITION_SPEC_FILE}.
- Output must be ASCII-only.
- Include YAML frontmatter with at minimum:
  - doc_type: "output_composition_spec"
  - lifecycle_status: "draft"
  - effective_version: "{job_id}"
  - domain: "{domain_name}" (from spec)
  - component_type_count: {number}
- Use tables for component types and composition rules.
- Include at least one example composition and one example output skeleton.
- The Extension Guide section must provide step-by-step instructions for adding
  new output types.

Forbidden Content

- Non-ASCII characters
- Vague component type descriptions like "output file" or "generated document"
- Component types that don't map to actual output artifacts
- Extension instructions that require modifying workflow code
