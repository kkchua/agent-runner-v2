Objective

Perform a technical critique of the backlog document, focusing on decomposition quality, dependency correctness, and work item scoping.

Layer Boundary

- This workflow belongs to Layer 3 and operates on top of the Layer 2 platform contract.
- Critique only the backlog document, not task or implementation artifacts.
- Treat Layer 1 governance and Layer 2 platform constitution as read-only authority.

Reference Inputs

- Read `BACKLOG_FILE` (the backlog document to critique).
- Read `PLAN_FILE` (approved plan for scope coverage verification).
- Read codebase context from `docs/repo/codebase/current/` to validate technical assumptions.
- Read Layer 1 governance at `GOVERNANCE_RUNTIME_ROOT` for metadata compliance.
- Read Layer 2 platform constitution at `PLATFORM_RUNTIME_ROOT` for platform contract compliance.

Critique Criteria

Evaluate the backlog document against these criteria:

1. **Work Item Scoping**:
   - Are work items properly scoped (not too large, not too small)?
   - Each work item should represent a coherent unit of work
   - Work items should be independently estimable and testable
   - No work item should require multiple unrelated skill sets

2. **Boundary Clarity**:
   - Are boundaries between work items clear with no overlap?
   - Each work item should have distinct ownership and deliverables
   - No duplicate scope across work items
   - Interfaces between work items are explicitly defined

3. **Dependency Analysis**:
   - Are dependencies correctly identified and sequenced?
   - Dependency chains do not contain circular references
   - Critical path dependencies are explicitly marked
   - Dependencies reference valid work item IDs within the backlog

4. **Acceptance Criteria Independence**:
   - Are acceptance criteria for each work item independently verifiable?
   - Each criterion has clear pass/fail conditions
   - Criteria do not depend on implementation details
   - Criteria are measurable without ambiguity

5. **Scope Coverage**:
   - Does the decomposition cover the full plan scope with no gaps?
   - Every requirement in PLAN_FILE maps to at least one work item
   - No orphaned work items without plan traceability
   - Scope boundaries match the approved plan

6. **Parallel Execution Opportunities**:
   - Are parallel execution opportunities correctly identified?
   - Independent work items are not artificially sequenced
   - Parallelizable items have no hidden dependencies
   - Concurrency constraints are documented where they exist

7. **API and SDK Verification**:
   - Verify API and SDK usage against the actual installed library version
   - Check referenced modules, function signatures, and patterns against the codebase
   - Do not rely on training data for library APIs -- they may have changed

Critique Output

Generate a critique document with YAML frontmatter and the following sections:

YAML Frontmatter:
  template_id: "SYS-03-CR"
  version: "1.0.0"
  doc_type: "review_artifact"
  lifecycle_status: "draft"

Document Sections:
1. **Decision**: APPROVED or REJECTED
2. **Summary**: Brief overview of critique findings
3. **Findings**: Detailed list of issues (if any), categorized as:
   - **Critical**: Must fix (incorrect dependencies, scope gaps, overlapping work items)
   - **Major**: Should fix (poor scoping, missing parallel opportunities, weak acceptance criteria)
   - **Minor**: Nice to fix (naming inconsistencies, documentation gaps)
4. **Recommendations**: Specific actions to address findings

If APPROVED:
   - Work items are well-scoped with clear boundaries
   - Dependencies are correct and complete
   - Acceptance criteria are independently verifiable
   - Full plan scope is covered

If REJECTED:
   - Provide specific, actionable feedback
   - Cite exact work items, sections, or text that need changes
   - Explain what must be fixed for the critique to be approved

Output Instructions

- Write the critique document to `CRITIQUE_FILE_SUGGESTED` path.
- Use ASCII-only characters.
- Include YAML frontmatter with the fields specified above.
- Use plain text section headings.
- Provide direct citations to offending text when rejected.
- Be specific and actionable in feedback.
