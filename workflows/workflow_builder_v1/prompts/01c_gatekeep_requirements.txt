Objective

Validate that the generated requirements document is complete, technically sound,
and will achieve all objectives defined in the original specification. This is a
quality control checkpoint before downstream steps consume the requirements.

The gatekeeper asks: "Will this solution actually work? Are there gaps that
will cause downstream failures?"

Reference Inputs

- Read the original specification: {WORKFLOW_SPEC_FILE}
- Read the generated requirements: {WORKFLOW_REQUIREMENTS}
- Read the test criteria: {TEST_CRITERIA}

Validation Questions

Answer each question with specific evidence from the documents:

1. Completeness: Does the requirements document define ALL elements needed to
   achieve the spec objectives? Are there undeclared inputs, outputs, or steps?

2. Workflow Type Appropriateness: Is the inferred workflow type (prompt-driven,
   action-driven, or mixed) appropriate for the problem? Would a different
   approach be better?

3. Step Sequence Validity: Does the proposed step sequence logically flow from
   inputs to outputs? Are dependencies properly chained? Is the init_step
   appropriate?

4. Action Specifications: If action-driven steps are proposed, are the action
   specifications complete (purpose, inputs, outputs, logic)? Are they truly
   deterministic operations suitable for code implementation?

5. Prompt Specifications: If prompt-driven steps are proposed, are the purposes
   clear? Are inputs/outputs well-defined? Is the scope appropriate for an LLM?

6. Constraint Satisfaction: Does the solution respect all constraints declared
   in the spec (layer boundaries, naming conventions, forbidden patterns)?

7. Downstream Feasibility: Can the artifact definition step consume these
   requirements and produce a complete artifact contract? Are there implied
   artifacts not explicitly declared?

8. Inference Quality: For elements the LLM inferred (workflow type, step types,
   sequence), is the inference sound? Are there better alternatives?

Decision Rules

- APPROVED: The requirements are complete and will achieve spec objectives.
  All validation questions have satisfactory answers.

- REJECTED: The requirements have gaps, will not achieve objectives, or need
  significant revision. Include specific findings for each failed validation
  question.

Output Instructions

- Write the gatekeeper report to {GATEKEEP_REQUIREMENTS}.
- Include YAML frontmatter with doc_type: "gatekeep_report".
- Structure:
  1. Summary: Overall assessment (1-2 sentences)
  2. Validation Results: Table with columns: Question, Status (PASS/FAIL), Evidence
  3. Issues (if any): Numbered list of specific gaps found
  4. Recommendations: Specific suggestions to fix issues
  5. Verdict: APPROVED or REJECTED on its own line
- All content must be ASCII-only.
- The result field in meta.json must match the verdict exactly.

Forbidden Content

- Non-ASCII characters
- Vague findings without specific evidence
- Approving requirements with known gaps
