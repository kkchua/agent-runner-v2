Objective

Define all artifact keys and their filesystem paths for the new workflow
package based on the structured requirements document.

Reference Inputs

- Read {WORKFLOW_REQUIREMENTS_FILE} for the structured requirements.
- Read {WORKFLOW_CREATION_GUIDE} Part C for artifact naming conventions and
  path patterns.

Artifact Definition Tasks

1. For each output artifact listed in the requirements, define:
   - Artifact key in UPPER_SNAKE_CASE
   - Relative path pattern using {job_id}, {seq}, and {slug} placeholders
   - Human-readable description
   - Whether the artifact is required or optional

2. For each input artifact, confirm the key name matches existing conventions
   in the codebase. If the input is a new key, define it here.

3. Include WORKFLOW_ACTIONS artifact if requirements propose action-driven steps:
   - Key: WORKFLOW_ACTIONS
   - Path: actions.py (in workflow package root)
   - Description: Python module with @action decorated functions
   - Required: conditional (yes if action steps exist, no otherwise)

4. Include shared artifacts that the workflow framework expects:
   - REVIEW_FILE_SUGGESTED for review output

5. Ensure no key collisions with existing artifact keys in the codebase.

6. Use consistent path patterns:
   - All outputs under docs/repo/<workflow_name>/runs/{job_id}/
   - Filename prefix matches the artifact key name
   - Include {seq} for auto-incrementing sequence numbers
   - Include {slug} derived from the input specification filename

Self-Critic (Before Self-Validation)

Challenge your reasoning before checking completeness:

1. Am I creating artifact keys for things that aren't separate files?
2. Are any of these keys redundant or duplicating information another
   key already captures?
3. If a downstream step reads this contract, would any path patterns
   confuse them or fail to resolve?
4. Did I stay in my lane (artifact definition), or did I leak into step
   design or workflow routing?

If you find reasoning issues, fix them before proceeding to Self-Validation.

Self-Validation (Before Output)

Before reporting APPROVED, validate:

1. Coverage: Does every artifact from {WORKFLOW_REQUIREMENTS_FILE} have a path
   defined? Are there implied artifacts not declared?

2. WORKFLOW_ACTIONS: If {WORKFLOW_REQUIREMENTS_FILE} declares action-driven steps,
   is WORKFLOW_ACTIONS included in the contract?

3. Placeholder Validity: Are {job_id}, {seq}, {slug}, {iter} used correctly?
   Are all paths relative?

4. Path Consistency: Do paths follow conventions from {WORKFLOW_CREATION_GUIDE}?

If validation fails, report REJECTED with specific gaps found.

Output Instructions

- Write the artifact contract document to {ARTIFACT_CONTRACT_FILE}.
- Output must be ASCII-only.
- Include YAML frontmatter with at minimum:
  - doc_type: "artifact_contract"
  - lifecycle_status: "draft"
  - effective_version: "{job_id}"
- Include these sections:
  1. Artifact Key Summary: table with columns Key, Path Pattern, Description,
     Required (yes/no).
  2. Input Artifacts: subsection listing keys the workflow reads, with source
     descriptions.
  3. Output Artifacts: subsection listing keys the workflow writes, with
     content descriptions.
  4. Shared Artifacts: list any framework-level keys used (e.g.
     REVIEW_FILE_SUGGESTED).
  5. Naming Rationale: brief explanation of key naming choices.
- Every key in the summary table must use UPPER_SNAKE_CASE.
- Path patterns must use forward slashes even on Windows.

Forbidden Content

- Step definitions or routing logic
- workflow.toml content
- Non-ASCII characters
- Hardcoded absolute paths
