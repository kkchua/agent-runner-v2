Objective

Read the workflow specification and produce a comprehensive test criteria
document that defines what "done" looks like for the generated workflow.
This document serves as the acceptance contract -- all downstream steps
must fulfill these criteria.

The test criteria must align with the enhanced workflow architecture:
- Gatekeeper QC steps between each major step
- Inference-based requirements generation (LLM infers from spec)
- Principles-based package generation (not fixed numbered lists)
- Self-Validation sections in each producer step

Reference Inputs

- Read {WORKFLOW_SPEC_FILE} for the complete workflow specification.
- Read {WORKFLOW_CREATION_GUIDE} for reference on workflow package structure.

Test Criteria Design Principles

1. Focus on SEMANTIC correctness, not just structural validity.
   - BAD: "actions.py must exist"
   - GOOD: "generate_images action must call Agnes Image API, download
     images, update JSON with URLs, handle retries, and produce index.json"

2. Structure criteria by workflow builder step so each step can look up
   only the criteria relevant to it.

3. Include both positive criteria (what must be present) and negative
   criteria (what must NOT be present).

4. Each criterion must be verifiable -- a reviewer must be able to
   check the generated files and determine pass/fail unambiguously.

5. Include criteria for gatekeeper validation -- QC checkpoints that
   validate solution quality before downstream consumption.

6. Include criteria for inference validation -- when LLM infers
   implementation details (workflow type, steps, actions), the
   inference must be sound and justified.

Generation Tasks

Produce a test criteria document with these sections:

1. Spec Objective Summary
   - One-paragraph summary of what the workflow must achieve
   - The end-to-end transformation (input -> output)

2. Criteria for analyze_spec step
   - Requirements document must capture all spec objectives
   - Input/output artifacts must be identified (explicit or inferred)
   - Constraints and dependencies must be documented
   - INFERENCE VALIDATION: If workflow type is inferred (not explicit),
     is the inference sound? Justify why this type vs alternatives.
   - INFERENCE VALIDATION: If step sequence is proposed, is it the most
     appropriate solution for the problem domain?
   - INFERENCE VALIDATION: If custom actions are inferred, are they truly
     deterministic operations suitable for code implementation?
   - INFERENCE VALIDATION: Do action specifications include sufficient detail
     (purpose, inputs, outputs, logic) for implementation?
   - INFERENCE VALIDATION: Are there any elements the LLM should have
     inferred but missed? (gaps in the solution)
   - SELF-VALIDATION: Does the document include Self-Validation section
     that checks coverage before reporting APPROVED?
   - SELF-VALIDATION: If gaps found, does it report REJECTED with specifics?

3. Criteria for gatekeep_requirements step
   - COMPLETENESS: Does the gatekeeper verify ALL spec objectives are
     covered by the requirements?
   - APPROACH VALIDITY: Does the gatekeeper evaluate whether the inferred
     workflow type and step sequence are appropriate?
   - DOWNSTREAM FEASIBILITY: Does the gatekeeper verify downstream steps
     can consume these requirements and succeed?
   - CONSTRAINT SATISFACTION: Does the gatekeeper verify all spec
     constraints are respected?
   - EVIDENCE: Is the verdict (APPROVED/REJECTED) justified with specific
     evidence, not just assertions?
   - LOOP VALIDITY: If REJECTED, are specific gaps identified for fixing?

4. Criteria for define_artifacts step
   - Coverage: Every artifact from requirements has a path pattern defined
   - WORKFLOW_ACTIONS: If requirements declare action-driven steps, is
     WORKFLOW_ACTIONS artifact key included in the contract?
   - Placeholder validity: Correct use of {job_id}, {seq}, {slug}, {iter}
   - Path patterns: All paths relative, following conventions
   - SELF-VALIDATION: Does the step include Self-Validation checking
     WORKFLOW_ACTIONS conditional requirement?

5. Criteria for gatekeep_artifacts step
   - COVERAGE: Does the gatekeeper verify ALL required artifacts are declared?
   - ACTION ARTIFACTS: Does the gatekeeper verify WORKFLOW_ACTIONS exists
     if action steps are declared in requirements?
   - PLACEHOLDER COMPLETENESS: Does the gatekeeper validate placeholder usage?
   - PATH VALIDITY: Does the gatekeeper verify all paths are relative?
   - CHAIN INTEGRITY: Does the gatekeeper verify artifact flow from inputs
     to outputs is unbroken?

6. Criteria for design_steps step
   - Coverage: Step sequence implements ALL requirements
   - Artifact flow: Can trace complete chain from inputs to outputs
   - Routing validity: Every step has valid onsuccess, loops correct
   - Step type appropriateness: Prompt vs action classification is correct
   - Action consistency: Action names match requirements specifications
   - Review loop design: Proper on_reject_refine, loop_returns_to, max_iterations
   - SELF-VALIDATION: Does the step include Self-Validation checking
     routing validity and artifact flow?

7. Criteria for gatekeep_steps step
   - COVERAGE: Does the gatekeeper verify ALL requirements have corresponding steps?
   - DATA FLOW: Does the gatekeeper verify required_inputs are satisfied
     by prior produces?
   - ROUTING VALIDITY: Does the gatekeeper verify step routing is correct?
   - TYPE CONSISTENCY: Does the gatekeeper verify step types match task nature?
   - LOOP VALIDITY: Does the gatekeeper verify review/refine loops are
     properly configured?

8. Criteria for generate_package step
   - PRINCIPLES-BASED: Does generation follow principles-based approach
     (not fixed numbered task list)?
   - FILE COMPLETENESS: Are ALL files implied by {STEP_ARCHITECTURE} present?
   - actions.py: If action steps exist, is actions.py generated with
     complete @action implementations?
   - workflow.toml: Exact match with step architecture (names, routing, artifacts)
   - context_extensions.py: All artifact keys from contract registered
   - prompts/: One file per prompt-driven step, ASCII-only, bare placeholders
   - README.md: Complete with step reference, artifact keys
   - Conditional files: .env.sample and config.json.sample only if needed
   - SELF-VALIDATION: Does the step include Self-Validation checking
     file completeness and design fidelity?

9. Criteria for gatekeep_package step
   - FILE CHECKLIST: Does the gatekeeper verify ALL expected files exist?
   - ACTION COMPLETENESS: Does the gatekeeper verify actions.py exists
     and contains actual implementations (not stubs) if action steps declared?
   - DESIGN FIDELITY: Does the gatekeeper verify files match {STEP_ARCHITECTURE}
     and {ARTIFACT_CONTRACT} exactly?
   - PROMPT COMPLETENESS: Does the gatekeeper verify prompts/ has one
     file per prompt-driven step?
   - SCOPE CHECK: Does the gatekeeper detect scope shrink (dropped elements)
     or scope creep (added elements not in design)?

10. Criteria for validate_bundle step
    - Structural checks: TOML validity, routing, artifact registration
    - Semantic checks: Action code contains actual logic, not stubs
    - File completeness: All required files present, no extra files

11. Criteria for review_package step
    - Spec fulfillment: Does the workflow actually implement the spec objective?
    - Step-by-step verification: Does each step do what the spec describes?
    - Data flow: Does information flow correctly between steps?
    - No hallucinations: No extra configs, no wrong models, no unnecessary inputs
    - GATEKEEPER EFFECTIVENESS: Did the gatekeepers catch issues early, or
      did they reach final review?

12. Criteria for refine_package step
    - COMPLETENESS: Can refine fix ALL types of issues flagged in review?
    - actions.py HANDLING: Can refine add or update actions.py if flagged?
    - CONSISTENCY: Does refinement maintain cross-file consistency?

13. Prompt Quality Criteria (for prompt-driven steps)
    For each prompt-driven step in the spec, generate criteria that verify
    the prompt is clear and unambiguous enough for an LLM to follow correctly:
    - Output mechanism: does the prompt explicitly instruct the LLM to use
      file-writing tools to create actual files on disk? Does it clarify that
      the meta.json result field is for status/summary ONLY, not artifact data?
    - Ambiguity check: are there any phrases that could be misinterpreted?
      (e.g., "Write the output to: {ARTIFACT_KEY}" is ambiguous -- does it
      mean write to a file or put in the result field?)
    - Common LLM mistakes: does the prompt guard against known failure modes?
      (e.g., putting JSON data in result field instead of writing files,
      forgetting to archive processed inputs, skipping index file creation)
    - Completeness: does the prompt specify all required outputs, formats,
      and file naming conventions?
    - SELF-VALIDATION: Does the prompt include Self-Validation section
      checking output completeness before reporting APPROVED?

14. Audit Criteria (Conditional)
    Scan the spec for aspects that require specialized audit. For each
    identified aspect, generate specific audit criteria:

    a) Security Audit (trigger if spec involves API keys, authentication,
       credentials, secrets, or sensitive data):
       - Are API keys loaded from .env file, not hardcoded?
       - Are credentials passed securely (e.g., Bearer token in headers)?
       - Are there no credential values in generated files or logs?
       - Does the workflow handle authentication failures gracefully?

    b) Logic Audit (trigger if spec involves retry, error handling, state
       management, complex data flow, or conditional branching):
       - Does retry logic handle all relevant failure modes (timeout, 503,
         network error, rate limit)?
       - Are timeouts configured and reasonable?
       - Does error handling distinguish between recoverable and fatal errors?
       - Is state properly managed across step boundaries?

    c) Data Integrity Audit (trigger if spec involves file operations,
       archiving, index tracking, or batch processing):
       - Are file operations atomic (write complete file, not partial)?
       - Are indexes updated correctly and completely?
       - Is archiving done correctly (copy then remove, not move)?
       - Are batch operations tracked (which files processed, which failed)?
       - Is partial failure handled (some succeed, some fail)?

    If none of these aspects apply to the spec, state "No audit criteria
    required for this spec" and explain why.

Output Instructions

- Write the test criteria document to {TEST_CRITERIA}.
- Output must be ASCII-only.
- Include YAML frontmatter with at minimum:
  - doc_type: "test_criteria"
  - lifecycle_status: "draft"
  - effective_version: "{job_id}"
- Each criterion must be a specific, verifiable statement.
- Use numbered lists for criteria within each section.
- Mark negative criteria with "MUST NOT" prefix.
- Include gatekeeper criteria for each gatekeeper step (sections 3, 5, 7, 9).
- Include inference validation criteria for analyze_spec (section 2).

Forbidden Content

- Vague criteria like "must be correct" or "must work properly"
- Non-ASCII characters
- Criteria that cannot be verified by reading the generated files
