Objective

Validate that the step architecture is complete and will achieve the requirements.
This is a quality control checkpoint before the package generation phase.

The gatekeeper asks: "Will these steps actually work? Is the routing correct?
Will data flow properly through the pipeline?"

Reference Inputs

- Read the requirements: {WORKFLOW_REQUIREMENTS}
- Read the artifact contract: {ARTIFACT_CONTRACT}
- Read the step architecture: {STEP_ARCHITECTURE}
- Read the test criteria: {TEST_CRITERIA}

Validation Questions

Answer each question with specific evidence from the documents:

1. Coverage: Does every requirement from {WORKFLOW_REQUIREMENTS} have
   corresponding steps that implement it? Are there requirement gaps?

2. Step Type Appropriateness: Is each step correctly typed?
   - prompt-driven: requires LLM reasoning, judgment, or synthesis
   - action-driven: deterministic, code-implementable operations
   Are there steps that should be the other type?

3. Routing Validity: Does every step have a valid onsuccess target? Do
   review/refine loops properly route back? Is stepCompletion the final step?

4. Artifact Bindings: Does each step's required_inputs match artifacts
   produced by prior steps or declared as inputs? Are all produces artifacts
   declared in the contract?

5. Data Flow: Can you trace a complete path from initial inputs to final
   outputs through the step sequence? Are there broken chains?

6. Action Completeness: For action-driven steps, are action names unique?
   Are they descriptive? Will the action implementation be feasible?

7. Prompt Completeness: For prompt-driven steps, are role policies
   appropriate? Are there appropriate coder assignments for each task type?

8. Loop Design: Do review/refine loops have appropriate max_iterations?
   Are exhausted_failure_code and exhausted_failure_class specified?

9. Terminal Step: Is stepCompletion present with action = "step_completion"?

10. Downstream Feasibility: Can the generate_package step consume this
    architecture and produce valid workflow files?

Decision Rules

- APPROVED: The step architecture is complete and will achieve requirements.
  All validation questions have satisfactory answers.

- REJECTED: The architecture has gaps, incorrect routing, or will not work.
  Include specific findings for each failed validation question.

Output Instructions

- Write the gatekeeper report to {GATEKEEP_STEPS}.
- Include YAML frontmatter with doc_type: "gatekeep_report".
- Structure:
  1. Summary: Overall assessment (1-2 sentences)
  2. Validation Results: Table with columns: Question, Status (PASS/FAIL), Evidence
  3. Issues (if any): Numbered list of specific gaps found
  4. Recommendations: Specific suggestions to fix issues
  5. Verdict: APPROVED or REJECTED on its own line
- All content must be ASCII-only.
- The result field in meta.json must match the verdict exactly.

Forbidden Content

- Non-ASCII characters
- Vague findings without specific evidence
- Approving architectures with known gaps
