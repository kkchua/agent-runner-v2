Objective

Address the technical critique findings by updating the requirement document.
Read the critique document, analyze each finding, and revise the requirement
document to resolve the issues raised.

Layer Boundary

- This workflow belongs to Layer 3 and operates on top of the Layer 2 platform contract.
- Critique only the requirement document, not planning or implementation artifacts.
- Treat Layer 1 governance and Layer 2 platform constitution as read-only reference inputs.

Reference Inputs

- Read {REQ_FILE} (the requirement document to update).
- Read {CRITIQUE_FILE_SUGGESTED} (the critique findings to address).
- Read {INIT_FILE} (the upstream initiative document for traceability reference).
- Read codebase context from {CODEBASE_DOC_ROOT} to validate proposed changes.
- Read Layer 1 governance at {GOVERNANCE_RUNTIME_ROOT} for metadata requirements.
- Read Layer 2 platform constitution at {PLATFORM_RUNTIME_ROOT} for platform contract.

Address Critique Tasks

For each finding in the critique document:

1. **Read the finding carefully** -- understand what issue was raised and why.

2. **Evaluate the finding** -- determine if it is:
   a. Valid and should be addressed (most common)
   b. Already addressed in the document (cite where)
   c. Out of scope for a requirement document (belongs to planning/implementation)
   d. Incorrect or based on misunderstanding (provide counter-evidence)

3. **Address valid findings** by updating the relevant section of {REQ_FILE}:
   - If the critique identifies missing information, add it.
   - If the critique identifies incorrect information, correct it.
   - If the critique identifies unclear scope, clarify it.
   - If the critique identifies technical risks, add mitigation notes.
   - If the critique suggests better alternatives, evaluate and incorporate if appropriate.

4. **Document your changes** by adding a "Critique Resolution" section at the
   end of the requirement document (before Notes if present) with:
   - Each finding from the critique
   - Your resolution (what you changed, or why you did not change)
   - The section of the document that was affected

5. **Verify consistency** after making changes:
   - Ensure all sections still flow logically.
   - Ensure no contradictions were introduced.
   - Ensure the document still meets the required structure.

Output Instructions

- Update {REQ_FILE} in place with the revised content.
- Preserve the YAML frontmatter (do not change template_id, authority, etc.).
- Preserve all sections that do not need changes.
- Add a "Critique Resolution" section documenting how each finding was addressed.
- Use ASCII-only characters.
- Use plain text section headings.

Critique Resolution Section Format

Add this section before the Notes section (or at the end if no Notes):

```
## Critique Resolution

### Finding 1: [Brief description of the finding]
**Resolution:** [What was changed, or why no change was made]
**Affected section:** [Which section was updated]

### Finding 2: [Brief description of the finding]
**Resolution:** [What was changed, or why no change was made]
**Affected section:** [Which section was updated]

...
```

Self-Validation

Before reporting APPROVED, validate your output:

1. Completeness: Does the updated REQ_FILE address ALL findings from the critique?
2. Consistency: Are there any contradictions introduced by the changes?
3. Structure: Does the document still have all required sections?
4. Traceability: Can each resolution be traced to a specific critique finding?

If any check fails, revise the output before reporting APPROVED.

Forbidden Content

- Layer 1 governance redefinition or contradiction
- Layer 2 platform contract redefinition
- Implementation details or technical solutions (belongs to planning phase)
- Task breakdowns or scheduling
- Removing the Critique Resolution section
- Non-ASCII characters
