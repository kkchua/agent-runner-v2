Objective

Critique the validation report for evidence quality, coverage completeness, and methodological soundness before formal review.

Layer Boundary

- This workflow belongs to Layer 3 and operates on top of the Layer 2 platform contract.
- Critique only the validation report, not review or closure artifacts.
- Treat Layer 1 governance and Layer 2 platform constitution as read-only reference inputs.

Reference Inputs

- Read `VAL_FILE` (the validation report to critique).
- Read `EXEC_FILE` (approved execution document for traceability verification).
- Read codebase context from `docs/repo/codebase/current/` to validate results.
- Read Layer 1 governance at `GOVERNANCE_RUNTIME_ROOT` for metadata requirements.
- Read Layer 2 platform constitution at `PLATFORM_RUNTIME_ROOT` for platform contract.

Critique Criteria

Evaluate the validation report against these criteria:

1. **Evidence Quality**:
   - Is every acceptance criterion verified with actual evidence (not just "PASS" claims)?
   - Are evidence items concrete (test output, screenshots, logs) rather than assertions?
   - Can each piece of evidence be independently verified?

2. **Coverage Completeness**:
   - Are all test cases from the TASK test scope covered in the validation?
   - Are there gaps between task requirements and validation coverage?
   - Is every acceptance criterion from the implementation plan explicitly validated?

3. **Methodological Soundness**:
   - Are validation methods appropriate for what is being verified?
   - Are edge cases and boundary conditions tested?
   - Would the chosen validation methods detect real defects if present?

4. **Reproducibility**:
   - Is the validation reproducible by a third party?
   - Are test commands, environments, and preconditions documented?
   - Could another engineer re-run the validation and get the same results?

5. **Gap Analysis**:
   - Are there gaps between task requirements and validation coverage?
   - Are any acceptance criteria missing from the validation entirely?
   - Are implicit requirements (performance, error handling) addressed?

Critique Output

Generate a critique document with YAML frontmatter and the following sections:

YAML Frontmatter:
  template_id: "SYS-03-CR"
  version: "1.0.0"
  doc_type: "review_artifact"
  lifecycle_status: "draft"

Document Sections:
1. **Decision**: APPROVED or REJECTED
2. **Summary**: Brief overview of critique findings
3. **Findings**: Detailed list of issues (if any), categorized as:
   - **Critical**: Must fix (missing evidence for acceptance criteria, fabricated results)
   - **Major**: Should fix (coverage gaps, weak validation methods, missing edge cases)
   - **Minor**: Nice to fix (documentation clarity, minor reproducibility concerns)
4. **Recommendations**: Specific actions to address findings

If APPROVED:
- All acceptance criteria have concrete evidence
- Coverage is complete against task requirements
- Validation methods are sound and reproducible
- No significant gaps identified

If REJECTED:
- Provide specific, actionable feedback
- Cite exact acceptance criteria or sections that lack evidence
- Explain what must be fixed before formal review

Output Instructions

- Write the critique document to `CRITIQUE_FILE_SUGGESTED` path.
- Use ASCII-only characters (no em-dashes, curly quotes, or Unicode).
- Include YAML frontmatter with the fields specified above.
- Use plain text section headings (no backticks or formatting in headings).
- Provide direct citations to specific validation gaps when rejected.
- Be specific and actionable in feedback.
