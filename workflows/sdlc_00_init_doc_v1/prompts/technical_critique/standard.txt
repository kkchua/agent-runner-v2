Objective

Evaluate the initiative document for strategic value, problem validity, and high-level feasibility. This is an initiative-level review, NOT an implementation review.

Layer Boundary

- This workflow belongs to Layer 3 and operates on top of the Layer 2 platform contract.
- Critique only the initiative document, not planning or implementation artifacts.
- Treat Layer 1 governance and Layer 2 platform constitution as read-only reference inputs.

Reference Inputs

- Read `INIT_FILE` (the initiative document to critique).
- Read `DRAFT_INIT_FILE` (original draft for comparison).
- Read Layer 1 governance at `GOVERNANCE_RUNTIME_ROOT` for metadata requirements.
- Read Layer 2 platform constitution at `PLATFORM_RUNTIME_ROOT` for platform contract.

Critique Criteria

Evaluate the initiative against these criteria:

1. **Strategic Value**:
   - Is the objective clear and valuable?
   - Does the problem statement describe a real pain point?
   - Is this initiative worth pursuing now?

2. **Scope Definition**:
   - Is the scope well-defined with clear in-scope and out-of-scope boundaries?
   - Are the expected outcomes specific and measurable?
   - Are assumptions explicit and reasonable?

3. **High-Level Feasibility**:
   - Are there any fundamental technical blockers that make this impossible?
   - Does the initiative conflict with existing system capabilities at a conceptual level?
   - Are there any obvious dependencies that are missing?

4. **Design Direction**:
   - Is the proposed approach reasonable at a high level?
   - Are there obviously better alternatives that should be considered?

What NOT to Critique

Do NOT check implementation details at this stage. The following are NOT valid reasons to reject an initiative:
- Exact workflow names, CLI flag names, or API paths (these are resolved during planning)
- Specific file paths or directory structures (these are resolved during planning)
- Backend registration details or deployment prerequisites (these are resolved during planning)
- Code-level verification of referenced modules or functions (this is done during implementation)

Remember: An initiative document is a high-level proposal that says WHAT needs to be done and WHY. The HOW is resolved in later phases (requirements, planning, implementation).

Critique Output

Generate a critique document with YAML frontmatter and the following sections:

YAML Frontmatter:
  template_id: "SYS-03-CR"
  version: "1.0.0"
  doc_type: "review_artifact"
  lifecycle_status: "draft"

Document Sections:
1. **Decision**: APPROVED or REJECTED
2. **Summary**: Brief overview of critique findings
3. **Strategic Assessment**: Is this initiative valuable and worth pursuing?
4. **Scope Assessment**: Is the scope well-defined and achievable?
5. **High-Level Risks**: Any fundamental blockers or concerns?
6. **Recommendations**: Specific actions to strengthen the initiative (if APPROVED) or fix fundamental issues (if REJECTED)

Output Instructions

- Write the critique document to `CRITIQUE_FILE_SUGGESTED` path.
- Use ASCII-only characters.
- Include YAML frontmatter with the fields specified above.
- Use plain text section headings.
- Be specific and actionable in findings.
- APPROVE unless there are fundamental strategic or scope issues.
