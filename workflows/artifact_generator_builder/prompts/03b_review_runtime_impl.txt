# Objective

Review a runtime implementation design for implementability. Verify the design correctly follows the composition spec and can be used to generate the workflow package.

# Reference Inputs

- RUNTIME_IMPL_FILE: {RUNTIME_IMPL_FILE}
- COMPOSITION_SPEC_FILE: {COMPOSITION_SPEC_FILE}
- CODENAME: {CODENAME}

# Review Protocol

Follow these steps IN ORDER.

## Step 1: Accuracy Check

Compare the runtime impl against the composition spec. Look for:
- Algorithms that contradict the spec's transformation rules
- Step-to-prompt/action assignments inconsistent with the spec's step interfaces
- Data flow contradictions between the design and the spec

For each issue found, quote the specific text and explain the discrepancy.

## Step 2: Functional Viability

Ask: "If I were writing code from this design alone, could I do it?"

- Does every step have a clear prompt template or action function assignment?
- Can I trace the complete data flow from input loading through transformation to output generation?
- Are the algorithms specific enough to implement without guessing?
- Does the extension interface support adding `impls/{name}/impl.yaml` overrides?

If any answer is "no" or "I'd have to guess," that is a blocking defect.

## Step 3: Verdict

- **PASS** — The design is implementable. Minor observations may be noted but do not block the next phase.
- **REJECT** — The design has blocking defects (impossible algorithms, missing assignments, data flow gaps) that will cause package generation to fail. State what must be fixed.

# Output Instructions

Write to: {REVIEW_RUNTIME_IMPL_FILE}
Markdown with YAML frontmatter: doc_type: "review_runtime_impl", verdict: "PASS" or "REJECT", identity_locked: true. ASCII-only.

Structure your review as:
1. Accuracy Issues (blocking defects only, with quotes)
2. Functional Viability Assessment (pass/fail for each question)
3. Minor Observations (non-blocking, for awareness)
4. Final Verdict + reasoning

# Forbidden Content

- Do NOT reject for minor wording issues or theoretical concerns that would not cause implementation failure
- Do NOT invent requirements not present in the composition spec
- Do NOT include non-ASCII characters
