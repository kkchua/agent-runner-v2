# Objective

Review a requirement analysis document for accuracy and completeness. Verify it correctly captures the requirement doc and is usable as input to the next phase.

# Reference Inputs

- REQUIREMENT_ANALYSIS_FILE: {REQUIREMENT_ANALYSIS_FILE}
- REQUIREMENT_DOC: {REQUIREMENT_DOC}

# Review Protocol

Follow these steps IN ORDER.

## Step 1: Accuracy Check

Compare the analysis against the original requirement doc. Look for:
- Statements that contradict or misrepresent the requirement doc
- Invented requirements not present in the original doc
- Missing input or output content that the requirement doc explicitly mentions

For each issue found, quote the specific text and explain the discrepancy.

## Step 2: Usability Check

Ask: "If I were designing a composition spec from this analysis alone, could I do it?"

- Can I identify ALL inputs this generator consumes?
- Can I identify ALL outputs this generator produces?
- Can I describe the transformation from input to output without guessing?
- Are the constraints specific enough to implement?

If any answer is "no" or "I'd have to guess," that is a blocking defect.

## Step 3: Verdict

- **PASS** — The analysis is accurate and usable. Minor observations may be noted but do not block the next phase.
- **REJECT** — The analysis has blocking defects (contradictions, missing content, invented requirements) that will cause the next phase to fail. State what must be fixed.

# Output Instructions

Write to: {REVIEW_REQUIREMENT_FILE}
Markdown with YAML frontmatter: doc_type: "review_requirement", verdict: "PASS" or "REJECT", identity_locked: true. ASCII-only.

Structure your review as:
1. Accuracy Issues (blocking defects only, with quotes)
2. Usability Assessment (pass/fail for each question)
3. Minor Observations (non-blocking, for awareness)
4. Final Verdict + reasoning

# Forbidden Content

- Do NOT reject for minor wording issues or style preferences
- Do NOT invent requirements not present in the original doc
- Do NOT include non-ASCII characters
