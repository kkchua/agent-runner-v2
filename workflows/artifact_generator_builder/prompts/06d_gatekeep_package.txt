# Self-Challenge Protocol

## Step 1: Runtime Execution Test

Mentally execute the full workflow as the daemon would:
1. Parse workflow.toml — does it load? Are all step names, routing, and artifact bindings valid?
2. Start at init_step — follow the routing chain. Does it reach stepCompletion without cycles or dead ends?
3. For each step — resolve its prompt file path. Does the file exist? Check that all `{placeholder}` keys are provided by context_extensions.py.
4. For each action step — verify the action name matches a function in actions.py.
5. Check artifact flow — every step's required_inputs are produced by prior steps.
6. Check the override pattern — every step has `prompt` or `action` in workflow.toml. No `impls/default/` exists. If `impls/` has variants, each has valid `impl.yaml` with partial overrides.
7. Check implementation declarations — if `impls/` directories exist, each MUST have a matching `[[workflow.implementation]]` entry in workflow.toml. The `default` name MUST NOT appear in the declarations. Each `name` field MUST match an actual `impls/{name}/` directory.

Note every point where the simulation fails.

## Step 2: Devil's Advocate

Argue REJECT. Find the strongest case against approving this package:
- What cross-file references are broken (artifact keys mismatched between workflow.toml and context_extensions.py)?
- What prompt placeholders reference keys that do not exist?
- What action names do not match registered functions?
- Would the runtime fail at any step during execution?
- Is there builder identity leakage?

## Step 3: Review Feedback Check

Read the review ({REVIEW_PACKAGE_FILE}). Were all identified issues addressed? If the review said REJECT, are the specific defects fixed?

## Step 4: Verdict

After challenging, give your final verdict:
- **APPROVE** — The package survived all challenges. It is executable and ready for promotion.
- **REJECT** — The package has unresolved defects. State what must be fixed.
