# Self-Challenge Protocol

## Step 1: Runtime Execution Test

Mentally simulate the daemon executing this step sequence from start to finish:
- Start at init_step. Follow each `onsuccess` chain. Does it reach stepCompletion without cycles or dead ends?
- For each step, check: are all `required_inputs` already produced by a prior step?
- For each step, check: does `result_meta_key` match one of the step's `produces`?
- For each `on_reject_refine`: does the target step exist? Does it produce the artifact the review needs?

Note every point where the simulation fails.

## Step 2: Devil's Advocate

Argue REJECT. Find the strongest case against approving this sequence:
- Are there routing gaps (steps that cannot be reached, or routing that leads nowhere)?
- Are there artifact ordering violations (a step needs an artifact that has not been produced yet)?
- Are there steps that produce artifacts not declared in the contract, or consume artifacts the contract does not define?
- Would any step fail at runtime because its prompt/action reference is wrong?

## Step 3: Completeness Challenge

Check that the sequence covers ALL functionality:
- Does every abstract step interface from the composition spec have a corresponding step?
- Does every artifact from the contract get produced?
- Are there missing review/refine loops for critical steps?

## Step 4: Verdict

After challenging, give your final verdict:
- **APPROVE** — The sequence survived all challenges. Routing is valid, artifact flow is correct, and all functionality is covered.
- **REJECT** — The sequence has unresolved defects. State what must be fixed.
