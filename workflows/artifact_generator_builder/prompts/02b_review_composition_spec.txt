# Objective

Review a composition specification for implementability. Verify the spec correctly satisfies the requirement analysis and can be used to design a runtime implementation.

# Reference Inputs

- COMPOSITION_SPEC_FILE: {COMPOSITION_SPEC_FILE}
- REQUIREMENT_ANALYSIS_FILE: {REQUIREMENT_ANALYSIS_FILE}
- BASE_COMPOSITION_STANDARD: {BASE_COMPOSITION_STANDARD}

# Review Protocol

Follow these steps IN ORDER.

## Step 1: Accuracy Check

Compare the composition spec against the requirement analysis. Look for:
- Transformation rules that contradict the requirement analysis
- Input/output mappings that do not align with the analyzed artifacts
- Step interfaces that are impossible to implement as described

For each issue found, quote the specific text and explain the discrepancy.

## Step 2: Functional Viability

Ask: "If I were designing a runtime implementation from this spec alone, could I do it?"

- Can I map every input artifact to a specific step that consumes it?
- Can I map every output artifact to a specific step that produces it?
- Are the step interfaces specific enough to write a prompt or action for?
- Does the three-layer architecture (Input -> Transformation -> Output) hold?

If any answer is "no" or "I'd have to guess," that is a blocking defect.

## Step 3: Verdict

- **PASS** — The spec is implementable. Minor observations may be noted but do not block the next phase.
- **REJECT** — The spec has blocking defects (contradictions, impossible interfaces, missing mappings) that will cause implementation to fail. State what must be fixed.

# Output Instructions

Write to: {REVIEW_COMPOSITION_SPEC_FILE}
Markdown with YAML frontmatter: doc_type: "review_composition_spec", verdict: "PASS" or "REJECT", identity_locked: true. ASCII-only.

Structure your review as:
1. Accuracy Issues (blocking defects only, with quotes)
2. Functional Viability Assessment (pass/fail for each question)
3. Minor Observations (non-blocking, for awareness)
4. Final Verdict + reasoning

# Forbidden Content

- Do NOT reject for minor wording issues, style preferences, or theoretical concerns that would not cause implementation failure
- Do NOT invent requirements not present in the input artifacts
- Do NOT include non-ASCII characters
