# Self-Challenge Protocol

## Step 1: Runtime Execution Test

Mentally simulate a developer implementing this design:
- Pick each step — can you write the prompt template or action function without guessing?
- Trace the data flow — does every input get consumed and every output get produced?
- Check the override pattern — could someone create `impls/{name}/impl.yaml` to swap a step's prompt or action without touching the core design?

Note every point where the simulation stalls or requires a guess.

## Step 2: Devil's Advocate

Argue REJECT. Find the strongest case against approving this design:
- What step assignments are ambiguous or missing?
- What data flow gaps exist (inputs never consumed, outputs never produced)?
- Would the override pattern actually work, or are there hidden coupling issues?
- Are there algorithms that look correct on paper but would fail with real data?

## Step 3: Review Feedback Check

Read the review ({REVIEW_RUNTIME_IMPL_FILE}). Were all identified issues addressed? If the review said REJECT, are the specific defects fixed?

## Step 4: Verdict

After challenging, give your final verdict:
- **APPROVE** — The design survived all challenges. It is implementable and complete.
- **REJECT** — The design has unresolved defects. State what must be fixed.
